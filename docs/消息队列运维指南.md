# RabbitMQ 使用与运维说明

Redis 已经有业务 key、库存同步和演示接口。RabbitMQ 这边也不能只停留在“引了依赖、能发消息”，所以项目补了通知队列、发布确认、消费重试、死信队列和队列状态查询。

## 1. RabbitMQ 怎么启动

单独启动 RabbitMQ：

```bash
cd D:/A_project/crs/ClassroomReservationBoot
docker compose up -d rabbitmq
```

完整启动：

```bash
docker compose up -d --build
```

控制台：

```text
http://localhost:15672
guest / guest
```

对应配置：

```text
docker-compose.yml:38
src/main/resources/application.yml
```

## 2. 项目里有哪些 MQ 组件

统一定义在：

```text
src/main/java/com/xuan/boot/config/RabbitConfig.java
```

| 组件 | 名称 | 作用 |
| --- | --- | --- |
| Exchange | `classroom.reserve.exchange` | 预约业务通知交换机 |
| Routing Key | `reserve.notify` | 通知消息路由键 |
| Queue | `classroom.reserve.notify.queue` | 站内信通知消费队列 |
| DLX | `classroom.reserve.dlx` | 死信交换机 |
| DLQ | `classroom.reserve.notify.dlq` | 消费失败后的死信队列 |

如果你之前启动过旧版本，RabbitMQ 里可能已经存在没有死信参数的同名队列。RabbitMQ 不允许用不同参数重复声明同一个队列，演示前可以在控制台删除 `classroom.reserve.notify.queue`，再重启应用让它自动创建。

## 3. 消息链路怎么走

```text
预约 / 取消 / 签到 / 候补补位
  -> ReservationServiceImpl.publishNotify
  -> RabbitTemplate convertAndSend
  -> classroom.reserve.exchange
  -> classroom.reserve.notify.queue
  -> NotificationConsumer.handle
  -> NotificationMapper.insert
  -> tb_notification
```

关键代码：

```text

src/main/java/com/xuan/boot/service/impl/NotificationConsumer.java
src/main/java/com/xuan/boot/mapper/NotificationMapper.java

```

## 4. 可靠性配置做了什么

### 发布确认

```text
spring.rabbitmq.publisher-confirm-type=correlated
spring.rabbitmq.publisher-returns=true
spring.rabbitmq.template.mandatory=true
```

代码位置：

```text
src/main/resources/application.yml
src/main/java/com/xuan/boot/config/RabbitConfig.java
```

作用：

```text
消息到达 broker 后触发 confirm callback；
消息因为路由键错误无法路由到队列时触发 returns callback；
失败信息会写入日志，方便演示和排查。
```

### 消费重试

```text
spring.rabbitmq.listener.simple.retry.enabled=true
spring.rabbitmq.listener.simple.retry.max-attempts=3
spring.rabbitmq.listener.simple.default-requeue-rejected=false
```

作用：

```text
消费者异常时先在消费端重试；
超过最大重试次数后不再无限 requeue；
消息会被投递到死信队列，避免异常消息卡住主队列。
```

### 死信队列

主队列绑定了：

```text
x-dead-letter-exchange=classroom.reserve.dlx
x-dead-letter-routing-key=reserve.notify.dead
```

作用：

```text
失败消息不会静默丢失；
面试演示时可以在 RabbitMQ 控制台看到 DLQ；
后续可以做人工补偿或定时重放。
```

## 5. RabbitMQ 运维演示接口

登录后携带 `X-Token` 调用：

```text
GET /ops/mq/overview
```

返回内容包括：

```text
exchange
routingKey
deadLetterExchange
deadLetterRoutingKey
queue exists
queue messages
queue consumers
dlq messages
```

代码位置：

```text
src/main/java/com/xuan/boot/controller/MqOpsController.java
src/main/java/com/xuan/boot/service/impl/MqOpsServiceImpl.java
```

## 6. 控制台怎么验证

1. 打开 `http://localhost:15672`，使用 `guest / guest` 登录。
2. 在 Exchanges 中查看 `classroom.reserve.exchange` 和 `classroom.reserve.dlx`。
3. 在 Queues 中查看 `classroom.reserve.notify.queue`。
4. 正常预约一次，队列消息会被消费者快速消费，`tb_notification` 会新增站内信。
5. 如果模拟消费者异常，消息重试后会进入 `classroom.reserve.notify.dlq`。
6. 调用 `GET /ops/mq/overview`，查看主队列和死信队列积压数。

## 7. 面试说法

可以这样讲：

```text
通知不是预约主流程的强一致核心数据，所以我用 RabbitMQ 做异步解耦。
发送端开启 publisher confirm 和 returns，消费端配置最多 3 次重试；
超过重试次数后不再无限重新入队，而是进入死信队列。为了能现场演示
和排查，我还补了 /ops/mq/overview 接口，可以查看主队列、死信队列、
消息积压数和消费者数量。
```

也可以主动补充不足：

```text
现在 MQ 已经有确认、重试和死信队列，但预约事务和 MQ 消息发送之间
还不是严格事务一致。生产环境可以继续升级为 outbox 本地消息表，
由定时任务或 CDC 投递 MQ，保证通知最终可达。
```
