## 1. 项目定位与自我介绍

### 一句话介绍

这是一个面向学生、教师和管理员的教室预约与校规问答平台。管理员维护可预约教室时段，学生预约时段下的一个名额，满员后进入候补；系统支持签到、信用分管理、异步通知、实时消息和 RAG Agent。

### 30 秒介绍

> 我做的是智慧校园教室预约与校规问答平台。管理员维护教室可预约时段，学生预约每个时段下的单个名额，满员后进入 FIFO 候补队列；系统还支持签到、爽约扣信用分、候补补位、反馈工单和实时通知。热门时段抢约使用 Submit Token、Redis Lua、Redisson、MySQL 条件更新和唯一索引构建分层并发控制。消息方面使用 Outbox 配合 RabbitMQ 和 Kafka，分别处理业务通知和事件统计。Agent 方面使用 LangChain4j Tool Calling、Spring AI、Qdrant 和 PDFBox，实现教室检索、预约草稿和带来源的校规问答。

### 3 分钟介绍

项目的核心资源不是一间教室，而是某间教室在某天某时间段的 room_slot。教室表保存楼栋、房间号、容量和设备等静态信息，room_slot 保存开放状态、时间、容量、剩余名额、已预约人数和候补人数。

学生只占用一个名额，因此同一个 room_slot 可以有多个学生预约，数量不能超过 capacity。教师临时预约整间教室，需要管理员审批，审批通过后占用对应时段。

抢约请求先校验用户身份、一次性 Submit Token、信用资格和 room_slot 状态，然后执行 Redis Lua，在一次 Redis 原子脚本中完成库存、重复预约和同时间段冲突判断。Redis 预扣成功后，MySQL 使用条件更新扣减库存并插入订单；唯一索引防止重复记录，数据库失败时补偿 Redis。

名额不足时，候补记录写入 MySQL，按创建时间和 ID 实现 FIFO。取消预约、候补过期和未签到由 Spring 定时任务处理，候补补位使用 Redisson 锁和条件状态更新，避免重复补位。

预约、签到和信用分变化在本地事务中写入 Outbox。通知 Outbox 异步投递 RabbitMQ，领域事件 Outbox 投递 Kafka；RabbitMQ 消费者写通知表并通过 SSE 推送在线用户，Kafka 消费者更新预约数、签到率、爽约率和教室使用率。

Agent 只位于预约事务之上。LangChain4j 只暴露教室搜索、规则检索和本人预约查询等只读工具，用户提出预约需求时只生成待确认草稿，最终提交仍走原有预约接口。规则 PDF 用 PDFBox 提取文本，滑动窗口切片，Embedding 后写入 Qdrant，查询采用 MySQL 关键词召回和 Qdrant 向量召回，再使用 RRF 融合。

## 2. 业务模型

### 为什么学生预约名额而不是整间教室

学生自习通常只占一个座位。如果一个学生直接占用一间 180 人教室，会造成资源浪费，也无法合理实现库存、候补、签到和爽约治理。

正确关系是：

    room：教室静态信息
    room_slot：某教室某天某时段的可预约资源
    reservation：一个学生占用 room_slot 的一个名额

### 为什么 room_slot 是核心表

room 记录相对稳定的属性，room_slot 承载随时间变化的资源状态：

- 是否开放。
- 是否维护。
- 是否被教师整间占用。
- 当前剩余名额。
- 当前预约数量。
- 当前候补数量。
- 是否已经过期。

预约、候补、签到、教师审批和事件统计都通过 room_slot 关联，因此核心表是 room_slot，而不是单独的 reservation。

### room_slot 状态

    OPEN           开放给学生预约
    CLOSED         管理员关闭
    MAINTENANCE    维护中
    TEACHER_BOOKED 教师整间占用
    EXPIRED        时间已过期

状态流转：

    CLOSED -> OPEN
    OPEN -> CLOSED             没有学生预约和候补时
    OPEN -> MAINTENANCE        没有学生预约和候补时
    MAINTENANCE -> OPEN/CLOSED
    OPEN -> TEACHER_BOOKED     没有学生预约且审批通过
    OPEN -> EXPIRED            时间过期后

已有学生预约或候补的时段，第一版不允许直接关闭、维护或删除，避免破坏已经产生的业务承诺。

唯一索引保证同一教室、同一天、同一时间段不能重复创建 room_slot。状态和日期索引支持学生查询开放时段。

### reservation 表

同一用户重复预约同一个 room_slot 会被唯一索引拦截。同一用户同一时间段预约不同教室，当前主要由 Redis 用户时间 Key 和业务校验保证；普通唯一索引不能直接表达时间区间重叠。

## 4. 高并发预约实现

### 4.1 主链路

    JWT 识别用户
      -> 校验 Submit Token
      -> 校验日期、时间和信用分
      -> 查询 OPEN room_slot
      -> Redis Lua 原子校验和预扣
      -> MySQL 条件更新库存
      -> 插入 reservation
      -> 写入 Outbox
      -> 返回结果

### 4.2 JWT 和 Submit Token

JWT 解决“当前用户是谁”，Submit Token 解决“这次提交是否已经消费过”。

    public String createSubmitToken() {
        User user = UserContext.getRequired();
        String token = UUID.randomUUID().toString();
        String key = "reserve:submit:" + user.getId() + ":" + token;
        redisTemplate.opsForValue()
            .set(key, "1", Duration.ofMinutes(5));
        return token;
    }

## 补充代码示例 A1：签到接口

    @Transactional
    public void checkin(Long orderId, String signCode) {
        // 当前用户必须从登录上下文获取，不能相信前端传入的 userId。
        Long userId = UserContext.getRequired().getId();

        // 先查订单，确认订单存在且属于当前用户。
        ReservationOrder order = reservationOrderMapper.findById(orderId);
        if (order == null || !order.getUserId().equals(userId)) {
            throw new IllegalArgumentException("无权操作该预约");
        }

        // 签到码用于证明用户持有该预约的签到凭证。
        if (!Objects.equals(order.getSignCode(), signCode)) {
            throw new IllegalArgumentException("签到码错误");
        }

        // 开始前 15 分钟到开始后 15 分钟才允许签到。
        if (!isWithinSignWindow(order)) {
            throw new IllegalArgumentException("不在签到时间窗口");
        }

        // 条件更新防止两个并发请求重复签到。
        // 只有 status = RESERVED 的订单可以被更新。
        int updated = reservationOrderMapper.sign(
                orderId, userId, signCode);
        if (updated != 1) {
            throw new IllegalArgumentException("预约已处理");
        }

        // 只有订单状态更新成功，才插入签到记录。
        // 当前项目没有单独的 checkinMapper.insert。
        // reservationOrderMapper.sign 已经把订单状态改为已签到。
        // 当前版本使用 reservation.status 作为签到事实。

        // setBit 记录用户当月哪一天签到过。
        // 这是签到统计辅助数据，不代替订单状态。
        String signBitmapKey = RedisKeys.USER_SIGN
                + userId + ":" + YearMonth.now();
        stringRedisTemplate.opsForValue().setBit(
                signBitmapKey,
                LocalDate.now().getDayOfMonth() - 1,
                true);

        // 当前项目真实方法名是 rewardCheckin。
        // 它更新 credit_account、插入 credit_record，
        // 并记录 CREDIT_CHANGED 事件。
        creditService.rewardCheckin(
                userId,
                request.getOrderId());

        // 当前项目通过 publishNotify 写入通知 Outbox。
        // 这里不是直接发送 SSE。
        publishNotify(
                userId,
                "签到成功",
                "预约单 " + request.getOrderId() + " 已签到");

        // 当前项目通过 recordReservationEvent 写入 Kafka 事件 Outbox。
        // 后续定时任务再投递到 classroom.events。
        recordReservationEvent(
                "CHECKIN_SUCCESS",
                order);
    }

## 补充代码示例 A2：NO_SHOW 定时任务

    @Scheduled(fixedDelay = 60000)
    public void markNoShow() {
        // 分页查询已经超过签到截止时间的 RESERVED 订单。
        List<ReservationOrder> orders =
                reservationOrderMapper.listExpiredReserved(100);

        for (ReservationOrder order : orders) {
            // 只有真正从 RESERVED 改成 NO_SHOW 的任务才继续处理。
            // 重复执行时返回 0，不会重复扣分。
            int updated = reservationOrderMapper.markNoShow(order.getId());
            if (updated != 1) {
                continue;
            }

            // 使用 reservationId 作为业务幂等键扣除信用分。
            creditService.deductForNoShow(order);

            // 释放一个名额，并触发候补补位。
            roomSlotService.releaseOne(order.getRoomSlotId());
            waitlistService.promoteNext(order.getRoomSlotId());

            // 事件用于统计，通知用于告知用户。
            domainEventService.record("NO_SHOW", order);
            notificationOutboxService.enqueue(
                    order.getUserId(),
                    "未签到提醒",
                    "本次预约未在规定时间内签到");
        }
    }

## 补充代码示例 A3：Outbox

    @Transactional
    public void saveReservationEvent(ReservationOrder order) {
        EventOutbox event = new EventOutbox();

        // eventId 是事件的全局幂等标识。
        event.setEventId(UUID.randomUUID().toString());
        event.setEventType("RESERVATION_SUCCESS");
        event.setUserId(order.getUserId());
        event.setRoomSlotId(order.getRoomSlotId());
        event.setPayload(toJson(order));
        event.setStatus(OutboxStatus.PENDING);

        // 事件和订单在同一个数据库事务中提交。
        eventOutboxMapper.insert(event);
    }

    @Scheduled(fixedDelay = 5000)
    public void publishDueEvents() {
        // 查询到达重试时间的待投递事件。
        List<EventOutbox> events =
                eventOutboxMapper.findDueEvents(100);

        for (EventOutbox event : events) {
            try {
                // 通知类事件投递 RabbitMQ。
                if (isNotification(event)) {
                    rabbitTemplate.convertAndSend(
                            "classroom.notify.exchange",
                            event.getEventType(),
                            event.getPayload());
                } else {
                    // 统计类事件投递 Kafka。
                    kafkaTemplate.send(
                            "classroom.events",
                            event.getEventId(),
                            event.getPayload());
                }

                // 成功后才标记 SENT。
                eventOutboxMapper.markSent(event.getId());
            } catch (Exception ex) {
                // 失败记录次数、时间和异常，等待退避重试。
                eventOutboxMapper.markRetry(
                        event.getId(),
                        event.getRetryCount() + 1,
                        nextRetryTime(event),
                        ex.getMessage());
            }
        }
    }

## 补充代码示例 A5：SSE

    @GetMapping("/notifications/stream")
    public SseEmitter stream() {
        // 用户身份来自 JWT，不能从 URL 传 userId。
        Long userId = UserContext.getRequired().getId();
        return sseNotificationService.subscribe(userId);
    }

    public SseEmitter subscribe(Long userId) {
        // 设置超时时间，避免失效连接永久占用内存。
        SseEmitter emitter = new SseEmitter(30 * 60 * 1000L);

        // 一个用户可能打开多个标签页，因此保存多个连接。
        emitters.computeIfAbsent(
                userId,
                ignored -> ConcurrentHashMap.newKeySet())
                .add(emitter);

        // 连接结束、超时或异常时都要移除。
        emitter.onCompletion(() -> remove(userId, emitter));
        emitter.onTimeout(() -> remove(userId, emitter));
        emitter.onError(error -> remove(userId, emitter));
        return emitter;
    }

    public void push(Notification notification) {
        Set<SseEmitter> connections =
                emitters.get(notification.getUserId());
        if (connections == null) {
            // 用户不在线，但通知已经落库，不丢失。
            return;
        }

        for (SseEmitter emitter : connections) {
            try {
                // name 必须和前端 EventSource 监听的事件名一致。
                emitter.send(SseEmitter.event()
                        .name("notification")
                        .id(String.valueOf(notification.getId()))
                        .data(notification));
            } catch (IOException ex) {
                // 推送失败的连接应及时清理。
                remove(notification.getUserId(), emitter);
            }
        }
    }

## 补充代码示例 A6：Caffeine + Redis

    public Classroom getById(Long roomId) {
        String key = "cache:classroom:" + roomId;

        // 第一层：本机内存，访问速度最快。
        Classroom local = caffeine.getIfPresent(key);
        if (local != null) {
            return local;
        }

        // 第二层：Redis，多个应用实例可以共享。
        Classroom shared = redis.get(key, Classroom.class);
        if (shared != null) {
            // Redis 命中后回填本地缓存。
            caffeine.put(key, shared);
            return shared;
        }

        // 两级缓存都未命中，回源 MySQL。
        Classroom database = classroomMapper.findById(roomId);
        if (database == null) {
            // 空值短期缓存可减少缓存穿透。
            redis.set(key, EMPTY_VALUE, Duration.ofSeconds(30));
            return null;
        }

        // 数据库结果逐级回填。
        redis.set(key, database, Duration.ofMinutes(10));
        caffeine.put(key, database);
        return database;
    }

    @Transactional
    public void updateRoom(Classroom room) {
        // 先修改数据库，数据库成功后再删除缓存。
        classroomMapper.update(room);
        redis.delete("cache:classroom:" + room.getId());
        caffeine.invalidate("cache:classroom:" + room.getId());
    }

库存不能使用普通 Caffeine 缓存，因为一个实例扣减库存后，其他实例的本地缓存不会实时变化。库存必须使用 Redis Lua 和 MySQL 条件更新。

## 补充代码示例 A7：PDF 入库

    public void ingestPdf(Path pdfPath) {
        // PDFBox 从 PDF 中提取每一页的文本。
        List<PageText> pages = pdfBoxExtractor.extract(pdfPath);

        for (PageText page : pages) {
            // 清理页眉、页脚和多余空格，但保留页码和章节。
            String text = textCleaner.clean(page.getText());

            // 按约 650 字符切分，保留约 100 字符重叠。
            List<Chunk> chunks = splitter.split(text, 650, 100);

            for (Chunk chunk : chunks) {
                // 每个 chunk 单独生成向量。
                float[] vector =
                        embeddingService.embed(chunk.getContent());

                // 向量和来源元数据一起写入 Qdrant。
                qdrantService.upsert(
                        chunk.getId(),
                        vector,
                        Map.of(
                                "documentId", page.getDocumentId(),
                                "page", page.getPageNumber(),
                                "section", page.getSection(),
                                "content", chunk.getContent()
                        )
                );
            }
        }
    }

## 补充代码示例 A8：RAG 查询

    public List<KnowledgeHit> retrieve(String question) {
        // 关键词检索适合编号、术语和精确时间。
        List<KnowledgeHit> keywordHits =
                knowledgeMapper.searchByKeyword(question, 10);

        // 向量检索适合同义表达和自然语言问题。
        float[] queryVector = embeddingService.embed(question);
        List<KnowledgeHit> vectorHits =
                qdrantService.search(queryVector, 10);

        // RRF 根据两个检索结果中的排名进行融合。
        Map<String, Double> scores = new HashMap<>();
        addRrfScore(scores, keywordHits);
        addRrfScore(scores, vectorHits);

        // 去重后取 Top 3，作为模型上下文。
        return mergeHits(keywordHits, vectorHits, scores)
                .stream()
                .limit(3)
                .toList();
    }

    private void addRrfScore(
            Map<String, Double> scores,
            List<KnowledgeHit> hits) {
        for (int index = 0; index < hits.size(); index++) {
            // 排名从 1 开始，不能直接使用 index。
            int rank = index + 1;

            // 60 是平滑常数，避免第一名权重过大。
            double score = 1.0 / (60 + rank);
            scores.merge(
                    hits.get(index).getChunkId(),
                    score,
                    Double::sum);
        }
    }

### 4.3 Redis Lua

    local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
    local userId = ARGV[1]

返回值：

    0：预扣成功
    1：库存不足
    2：重复预约
    4：同一时间段已经预约其他教室
    9：库存未初始化

Redis 执行 Lua 脚本时会保证脚本内部命令原子执行，避免检查库存和扣库存之间出现并发间隙。

### 4.4 MySQL 条件更新

    UPDATE tb_room_slot
    SET available_capacity = available_capacity - 1,
        reserved_count = reserved_count + 1,
        update_time = NOW()
    WHERE id = ?
      AND status = 1
      AND available_capacity > 0;

Redis 是高并发入口，MySQL 是最终持久化防线。条件更新影响行数为 1 才代表数据库扣减成功；影响行数为 0 时需要补偿 Redis。

### 4.5 为什么需要三层防线

- Redis Lua：保护热点请求的原子竞争。
- MySQL 条件更新：保证持久化库存不会扣成负数。
- 唯一索引：防止重复订单写入。
- Redisson 锁：保护取消、候补补位等跨 Redis 和 MySQL 的复杂流程。

不要把所有请求加一把全局锁，否则不同教室的预约也会互相阻塞。锁应按用户、预约单或 room_slot 细粒度设置。

### 4.6 Redis 成功、MySQL 失败

    Redis 预扣成功
      -> MySQL 更新失败
      -> Redis INCR 恢复库存
      -> Redis SREM 删除用户标记
      -> 删除 user-time Key
      -> 记录日志并由对账任务修复

最终还要用 MySQL 的有效预约数重建 Redis，解决极端异常。

## 5. 候补、签到和信用分

### 5.1 候补加入

库存不足时插入 WAITING 候补记录。当前采用 MySQL FIFO，创建时间相同再用 ID 保证稳定顺序。候补插入使用幂等约束，避免同一用户重复加入同一时段。

### 5.2 候补补位

    @Scheduled(fixedDelay = 3000)
    public int promoteAvailableWaitlists() {
        WaitlistOrder waiter = waitlistMapper.firstWaiting(
            roomId, reserveDate, timeSlot);
        if (waiter == null) {
            return 0;
        }
    
        RLock lock = redissonClient.getLock(
            "lock:waitlist:slot:" + waiter.getRoomSlotId());
        lock.lock(8, TimeUnit.SECONDS);
        try {
            int changed = waitlistMapper.updateStatus(
                waiter.getId(), WAITING, PROMOTED);
            if (changed == 0) {
                return 0;
            }
            // 创建预约、扣减库存、写通知 Outbox
            return 1;
        } finally {
            lock.unlock();
        }
    }

关键点：

- 按时段加锁，避免两个线程补位同一时段。
- 状态更新带旧状态条件，保证幂等。
- 补位、扣库存和通知需要处于可追踪的业务流程中。

### 5.3 候补过期

Spring 定时任务扫描预约开始时间已经过去且状态仍是 WAITING 的记录：

    UPDATE tb_reserve_waitlist
    SET status = 4,
        update_time = NOW()
    WHERE id = ?
      AND status = 0;

只有 WAITING 才能变成 EXPIRED，避免用户取消或系统补位后又被过期任务覆盖。

### 5.4 签到

签到需要检查订单存在、订单属于当前用户、状态为 RESERVED、签到码正确，并且当前时间处于预约开始前 15 分钟到开始后 15 分钟。

    UPDATE tb_reserve_order
    SET status = 2,
        update_time = NOW()
    WHERE id = ?
      AND user_id = ?
      AND sign_code = ?
      AND status = 1;

影响行数为 0 时，表示订单不存在、用户不匹配、签到码错误或订单已经处理过。

### 5.5 未签到

    定时扫描超过签到截止时间且仍为 RESERVED 的订单
      -> RESERVED 条件更新为 NO_SHOW
      -> 扣减信用分
      -> 写入信用流水
      -> 释放 room_slot 名额
      -> 触发候补补位
      -> 写 RabbitMQ 通知和 Kafka 事件

预约状态必须从 RESERVED 条件更新到 NO_SHOW，防止定时任务重复扣分。

### 5.6 信用分

签到可以增加少量分数，未签到扣分并增加违约次数。信用分可以影响热门时段预约资格、当天预约次数和候补优先级。

## 6. Outbox、RabbitMQ、Kafka 和 SSE

### 6.1 Outbox 解决什么问题

直接先更新 MySQL、再发送消息存在双写问题：数据库提交成功但 MQ 发送失败，会导致通知或统计事件丢失。

当前流程：

    同一 MySQL 事务：
        更新预约、签到或信用表
        写 notification_outbox 或 event_outbox
    
    事务提交后：
        定时任务扫描待发送记录
        投递 RabbitMQ 或 Kafka
        成功标记 SENT
        失败增加 retry_count
        超过次数进入失败或死信状态

Outbox 保证数据库状态和待发送事件最终一致，但不能保证消息绝对只发送一次，所以消费者还要幂等。

### 6.2 RabbitMQ

RabbitMQ 处理业务动作和通知：

    预约成功通知
    预约开始前提醒
    候补补位通知
    爽约通知
    信用分变更通知
    反馈工单通知

消费者可以先写通知表，再推送 SSE：

    @RabbitListener(queues = RabbitConfig.NOTIFY_QUEUE)
    public void consume(NotificationMessage message) {
        if (notificationMapper.existsByOutboxId(message.getOutboxId())) {
            return;
        }
        notificationMapper.insert(message);
        sseNotificationService.push(
            message.getUserId(), message);
    }

### 6.3 Kafka

Kafka 记录已经发生的事件：

    RESERVATION_SUCCESS
    RESERVATION_CANCELLED
    CHECKIN_SUCCESS
    NO_SHOW
    WAITLIST_JOINED
    WAITLIST_PROMOTED
    CREDIT_CHANGED
    ROOM_VIEW
    ROOM_SEARCH

Kafka 不负责判断库存、决定预约是否成功、解决超卖或替代 MySQL 事务。

统计消费者按 eventId 幂等：

    @KafkaListener(
        topics = "classroom.events",
        groupId = "classroom-statistics-consumer")
    public void consume(String payload) {

            objectMapper.readValue(payload, ClassroomEvent.class);
        if (statisticsMapper.existsByEventId(event.getEventId())) {

### 6.4 SSE

当前主要是服务端到浏览器的单向通知，因此使用 SSE。后端维护用户到 SseEmitter 的映射，连接断开、超时或异常时移除。

RabbitMQ 负责可靠投递，SSE 负责在线传输，MySQL notification 表负责离线保存。用户不在线不会导致通知丢失。

### 8.3 为什么 Agent 不能直接预约

模型可能解析错日期或时间，模型响应期间库存也可能变化；另外，模型可能被重复调用或受到恶意提示词影响。

因此流程是：

    自然语言
      -> Agent 搜索候选
      -> 返回预约草稿
      -> 用户确认
      -> 生成 Submit Token
      -> 正式预约接口
      -> Redis Lua + MySQL 事务

### 8.4 PDF 处理

当前不是把 PDF 物理切成多个新 PDF，而是提取文字后切成可检索的 chunk：

    上传 PDF
      -> PDFBox 逐页读取文字层
      -> 清理空白和部分格式噪声
      -> 650 字符窗口切分
      -> 相邻 chunk 重叠 100 字符
      -> chunk 保存 MySQL
      -> 调用 Embedding
      -> 向量写入 Qdrant

参数：

    chunk_size = 650
    overlap = 100
    step = 650 - 100 = 550

示意：

    chunk 1：0    ~ 650
    chunk 2：550  ~ 1200
    chunk 3：1100 ~ 1750

滑动窗口可以避免一条规则的条件和结论刚好被切到两个片段。窗口太小会丢上下文，窗口太大会引入无关内容并增加 Embedding 和模型上下文成本。

### 8.5 关键词、向量和 RRF

关键词检索适合制度名称、数字、时间和条款编号；向量检索适合同义表达和口语表达。

两路分数不在同一量纲，因此按排名融合：

    RRF(d) = sum(1 / (k + rank_i(d)))

同一个 chunk 同时出现在关键词和向量结果中时，通常会得到更高融合排名。

### 8.6 RAG 降级

    Embedding API 失败
      -> 文本仍保存在 MySQL
      -> 退回关键词检索
    
    Qdrant 失败
      -> 捕获连接异常
      -> 使用 MySQL 关键词召回
    
    LLM 失败
      -> 本地意图解析和规则解析
      -> 不影响普通预约接口
    
    没有召回证据
      -> 明确提示知识库暂未命中
      -> 不允许模型凭常识编造

外部 PDF 使用 EXTERNAL_REFERENCE 分类，只能作为参考，不构成本系统生效校规。

    Recall@1 = 40.00%
    Recall@3 = 73.33%
    MRR@3    = 54.44%

### 高并发预约

## 12. 技术选型

### 为什么使用 Spring Boot

项目需要统一接入 MyBatis、Redis、RabbitMQ、Kafka、Actuator、Flyway 和测试配置。Spring Boot 自动配置和 Starter 降低接入成本。项目目前是单体，预约和候补有紧密事务关系，不需要为了微服务而过早拆分。

### 为什么使用 MySQL

预约、签到和信用分需要事务、条件更新、唯一约束和可追溯记录。Redis 负责高并发访问，不能替代核心事实库；ES 有近实时延迟，不能替代事务数据库。

### 为什么 Redis Lua 而不是 synchronized

synchronized 只能保护单 JVM，多个实例之间无效。Redis Lua 在 Redis 服务端原子执行，多个实例可以共享库存和用户占用状态。

### 为什么 Lua 和 Redisson 都使用

Lua 适合短小的 Redis 内原子判断；Redisson 适合取消、候补补位等跨 Redis、MySQL 和多个状态步骤的复杂流程。

### 为什么 RabbitMQ 和 Kafka 都使用

RabbitMQ 更适合业务任务、通知、确认、重试和死信；Kafka 更适合事件流、消费组、回放和统计。两者职责不同。

### 为什么 ES 不能决定预约成功

ES 索引可能延迟，搜索结果只能作为候选；预约提交时必须重新经过 Redis Lua 和 MySQL 条件更新。

### 为什么 SSE 而不是 WebSocket

当前主要是服务端向浏览器单向推送，SSE 原生支持且接入简单；只有需要双向实时协作或聊天时才考虑 WebSocket。

### 为什么 Qdrant 和 Elasticsearch 都需要

Qdrant 做向量相似度检索，Elasticsearch 做关键词、过滤和范围检索。它们都不承担核心预约事务。

## 13. 故障和降级

### Redis 不可用

核心抢约链路不能绕过 Redis 直接放量到 MySQL，否则容易把数据库热点行打爆。应保护性失败；查询类接口可以有限回退 MySQL。

### MySQL 不可用

不能只依据 Redis 返回预约成功。预约需要 MySQL 持久化成功；恢复后根据订单事实和 room_slot 进行对账。

### RabbitMQ 不可用

业务状态和通知 Outbox 仍可提交到 MySQL，后台重试投递，超过次数进入失败或死信状态。

### Kafka 不可用

预约和签到仍可成功，事件保存在 event_outbox，Kafka 恢复后继续发送；统计会延迟，但不影响业务事实。

### Qdrant 不可用

退回 MySQL 关键词检索，原文仍可用；恢复后从 MySQL chunk 重建向量。

### LLM 不可用

使用本地意图解析和规则解析，Agent 暂时不可用不影响普通预约接口。

## 16. 从请求到预约完成的完整时序

面试官如果问“用户点击预约之后到底发生了什么”，建议按下面顺序回答：

1. 前端先调用一次性令牌接口，服务端生成随机 token，并以用户 ID 和 token 为维度写入 Redis。
2. 前端提交 roomSlotId、用户 token 和必要的预约信息。服务端首先校验登录身份、参数格式和 token 是否存在。
3. 服务端查询 room_slot，确认记录存在、日期和时间有效、状态是 OPEN，并读取容量和当前预约数。
4. 服务端检查信用分。信用分过低、当天次数超限或用户已有冲突预约时，直接拒绝，不进入库存扣减。
5. Redis Lua 在一个原子脚本中完成三个判断：剩余名额是否大于零、用户是否已经预约本时段、用户是否已经预约同一时间段的其他教室。全部通过后扣减 Redis 库存，并写入用户占用标记。
6. 进入 MySQL 事务，使用条件 UPDATE 再扣一次数据库名额。这个 UPDATE 的返回行数必须为 1，否则说明数据库侧已经没有名额或时段已关闭。
7. 插入 reservation，并写入预约成功对应的 Outbox 事件。业务表和 Outbox 在同一个数据库事务中提交。
8. 事务提交后立即返回预约成功。RabbitMQ 通知、Kafka 事件和 SSE 推送都在异步链路处理，不阻塞用户拿到预约结果。
9. 如果 MySQL 插入失败，服务端执行 Redis 补偿：恢复库存、删除用户占用标记，并记录异常日志。补偿失败时由定时对账任务根据 MySQL 结果修复 Redis。
10. Redis 判断无库存时，不再伪造预约成功，而是以唯一约束插入 waitlist。插入成功后返回“已进入候补”，重复提交则返回已有候补记录。

这段回答要强调：Redis 是并发快速判断层，MySQL 是最终业务事实；Kafka 不参与成功或失败判断。

## 17. 代码级讲解：为什么要两次扣库存

核心 SQL 是：

    UPDATE tb_room_slot
    SET reserved_count = reserved_count + 1,
        available_capacity = available_capacity - 1
    WHERE id = ?
      AND status = 1
      AND reserved_count < total_capacity;

逐句解释：

- WHERE id = ?：只更新当前 room_slot，避免误更新其他日期或教室。
- status = 1：只允许 OPEN 时段继续接受学生预约。
- reserved_count < total_capacity：数据库层再次确认没有超过容量。
- reserved_count = reserved_count + 1：在数据库内部完成自增，避免先 SELECT 再 UPDATE 的竞态。
- 返回值为 0：说明状态不对、记录不存在或已经满员，业务必须回滚当前事务并处理 Redis 补偿。

Redis Lua 的作用是把“检查并扣减”合并成原子操作，减少大量失败请求直接冲击 MySQL。它不能替代 MySQL，因为 Redis 可能重启、网络可能中断，且预约记录最终必须落到关系数据库。

推荐的伪代码如下：

    public ReserveResult reserve(Long userId, ReserveCommand command) {
        validateSubmitToken(userId, command.getSubmitToken());
        RoomSlot slot = roomSlotMapper.selectById(command.getRoomSlotId());
        validateOpenSlot(slot, command);
        validateCredit(userId);
    
        LuaResult result = redisReservationScript.execute(
            slot.getId(), userId, slot.getReserveDate(),
            slot.getTimeSlot(), slot.getAvailableCapacity()
        );
        if (result.isConflict()) {
            return ReserveResult.conflict(result.message());
        }
        if (result.isSoldOut()) {
            return joinWaitlist(userId, slot);
        }
    
        try {
            transactionTemplate.executeWithoutResult(status -> {
                int updated = roomSlotMapper.incrementReservedCountIfAvailable(slot.getId());
                if (updated != 1) {
                    throw new StockChangedException();
                }
                reservationMapper.insert(buildReservation(userId, slot));
                eventOutboxService.saveReservationSuccessEvent(userId, slot);
            });
            return ReserveResult.success();
        } catch (RuntimeException ex) {
            redisReservationScript.compensate(slot.getId(), userId);
            throw ex;
        }
    }

这里的重点不是让面试官记住方法名，而是能说清楚每一步的责任边界：

- 参数和权限校验属于 Web/Service 层。
- Lua 属于高并发入口保护。
- 条件 UPDATE 属于数据库最终兜底。
- reservation 和 Outbox 必须处于同一事务。
- Redis 回滚属于失败补偿，不是数据库事务回滚。

## 18. 为什么压测中 1000 人最终是 80 条预约

capacity = 80 时，1000 个不同用户同时请求同一个 room_slot：

- 前 80 个成功请求占用 80 个名额。
- 后续请求发现 Redis 库存为零，进入候补或返回已满。
- 最终正式预约数不能由 JMeter 的 HTTP 成功数直接推断，必须查 MySQL。
- 预约数应满足 reserved_count <= total_capacity。
- active reservation 数应与 room_slot.reserved_count 一致。
- 同一用户的有效预约数量应通过 GROUP BY user_id 检查。

候补数量不一定等于 920，原因包括：JMeter 请求失败、token 失败、账号初始化失败、网络超时、重复用户、候补唯一约束冲突、接口超时后客户端重试，以及测试脚本的线程同步方式。面试时要把“1000 个请求”“80 条预约”“920 条候补”分别称为请求样本、正式名额和候补记录，不能混为一个指标。

验证 SQL：

    SELECT reserved_count, total_capacity, available_capacity
    FROM tb_room_slot
    WHERE id = ?;
    
    SELECT status, COUNT(*) AS total
    FROM tb_reserve_order
    WHERE room_slot_id = ?
    GROUP BY status;
    
    SELECT user_id, COUNT(*) AS total
    FROM tb_reserve_order
    WHERE room_slot_id = ?
      AND status IN (0, 1, 4)
    GROUP BY user_id
    HAVING COUNT(*) > 1;

最后一条没有结果，才能说明在有效状态下没有重复预约用户。

## 19. 事务、锁和唯一索引分别解决什么

### 19.1 Spring 事务

预约事务至少包含：

    room_slot 条件扣减
    reservation 插入
    event_outbox 插入

这三步中任何一步失败，MySQL 内的修改一起回滚。事务不能自动回滚 Redis 操作，因此 Redis 必须由补偿代码或对账任务修复。

### 19.2 Redisson 分布式锁

候补补位、取消预约和管理员关闭时段可能同时修改同一个 slot。可以按 roomSlotId 加锁：

    RLock lock = redissonClient.getLock("lock:room-slot:" + roomSlotId);
    lock.lock();
    try {
        cancelOrPromote(roomSlotId);
    } finally {
        lock.unlock();
    }

锁解决的是多个应用实例同时执行同一段业务流程的问题，不是所有一致性的最终保证。即使锁失效或超时，状态条件更新和唯一索引也必须能够阻止重复补位。

### 19.3 唯一索引

建议保留以下数据库约束：

    UNIQUE(user_id, room_slot_id)
    UNIQUE(user_id, reserve_date, time_slot)
    UNIQUE(user_id, room_id, reserve_date, time_slot)

第一条防止同一个学生重复预约同一 slot，第二条防止同一学生同一时间预约不同教室。具体采用哪一条取决于数据库字段和历史兼容性，但业务代码不能只依赖前置查询。

## 20. 候补队列的真实实现和异常场景

第一版候补是 MySQL FIFO，不是 Redis ZSet。查询第一名的条件是：

    SELECT *
    FROM tb_reserve_waitlist
    WHERE room_id = ?
      AND reserve_date = ?
      AND time_slot = ?
      AND status = 0
    ORDER BY create_time ASC, id ASC
    LIMIT 1;

create_time 保证先来先服务，id 是同一时间下的稳定排序兜底。Redis ZSet 当前用于热门教室榜，不应在面试中说成“候补使用 ZSet”，除非代码已经真的这样实现。

取消预约的正确顺序：

1. 条件更新 reservation：只有 RESERVED 才能变成 CANCELLED。
2. 释放 room_slot 的一个名额，并保证 available_capacity 不超过 total_capacity。
3. 选择一条 WAITING 候补，条件更新为 PROMOTED。
4. 创建新的正式 reservation 或生成待确认资格，避免直接把候补记录当预约记录。
5. 写入 Outbox，发送补位通知。
6. 候补用户在 expire_at 前确认；超时则变成 EXPIRED，再继续处理下一位。

为什么不能直接删除取消记录：

- 删除会破坏审计和用户历史。
- Kafka 统计无法区分“从未预约”和“预约后取消”。
- 信用规则可能需要知道用户是否频繁取消。
- room_slot 的 reserved_count 必须随着状态变化可重算。

因此取消是状态流转，不是物理删除。删除只适合管理员清理明确的测试数据，且要和预约、候补、Outbox、通知一起处理。

## 21. 签到、爽约和信用分追问

签到窗口是预约开始前 15 分钟到开始后 15 分钟。签到接口必须校验：

    当前登录用户 == reservation.user_id
    reservation.status == RESERVED
    当前时间位于签到窗口
    reservation 未被取消、未被标记 NO_SHOW

更新签到状态时使用条件 UPDATE：

    UPDATE tb_reserve_order
    SET status = 2, checkin_time = NOW()
    WHERE id = ?
      AND user_id = ?
      AND status = 0;

返回 1 才能继续插入 checkin 和信用流水。这样同一个预约被两个请求同时签到时，只有一个请求能把状态从 RESERVED 改为 CHECKED_IN。

未签到任务的处理：

    定时扫描 checkin_deadline < NOW()
    只处理 status = RESERVED
    条件更新为 NO_SHOW
    插入扣分 credit_record
    释放名额
    触发候补补位
    写入 RabbitMQ/Kafka Outbox

信用账户和流水要分开：

- credit_account 保存当前余额、累计加分、累计扣分和版本号，方便快速判断资格。
- credit_record 保存每一次加分或扣分的原因、关联 reservation、变化前后分值，方便审计。

信用分更新可以使用 version 乐观锁：

    UPDATE credit_account
    SET score = score + ?, version = version + 1
    WHERE user_id = ?
      AND version = ?;

面试官问“信用分扣了两次怎么办”，回答要点是：为 credit_record 设置业务幂等键，例如 NO_SHOW:reservationId，并建立唯一约束；重复消费时先查幂等记录，已处理则直接确认消息，不重复扣分。

## 22. Agent 的边界：它不是绕过业务系统的聊天机器人

当前 Agent 的定位是“受控的预约助手和校规问答入口”，不是让大模型直接操作数据库。这个边界非常重要。

### 22.1 当前工具

工具可以按下面三类解释：

    search_available_slots
    retrieve_policy_knowledge
    get_my_reservations

- search_available_slots：根据日期、时间段、人数、楼栋等条件查询开放时段。
- retrieve_policy_knowledge：从规则知识库召回相关片段，返回带来源的上下文。
- get_my_reservations：查询当前登录用户自己的预约。

当前 Agent 生成预约草稿或推荐结果，真正的预约仍然必须经过普通预约接口。这样可以复用 Submit Token、信用分、Redis Lua、MySQL 事务和权限校验。

### 22.2 为什么不把 reserve_room 直接开放给模型

模型输出存在不确定性，例如日期解析错误、重复调用工具、参数缺失和用户意图歧义。如果模型可以直接扣库存，错误就会进入核心事务。

更合理的分层是：

    用户自然语言
        -> Agent 解析意图和参数
        -> 只读工具查询
        -> 返回候选 room_slot
        -> 用户确认
        -> 前端调用正式预约接口
        -> Redis + MySQL 完成预约

面试时可以说：LLM 负责理解和编排，领域服务负责校验和写入；Agent 是交互层，不是一致性层。

### 22.3 LangChain4j 如何接入

典型结构可以表达为：

    @Tool("查询当前用户可预约的教室时段")
    public List<RoomSlotView> searchAvailableSlots(
            LocalDate date, String timeSlot, Integer people,
            String building) {
        return roomSlotService.searchOpenSlots(date, timeSlot, people, building);
    }
    
    interface ReservationAssistant {
        String chat(@MemoryId Long userId, String message);
    }
    
    ReservationAssistant assistant = AiServices.builder(ReservationAssistant.class)
        .chatLanguageModel(model)
        .tools(reservationAgentTools)
        .chatMemoryProvider(memoryProvider)
        .build();

代码含义：

- @Tool 把 Java 方法描述成模型可以调用的工具。
- 工具方法仍然调用已有 Service，而不是直接访问 Mapper。
- @MemoryId 把会话记忆按用户或会话隔离。
- chatLanguageModel 负责调用模型。
- chatMemoryProvider 管理短期对话上下文。
- 工具返回结构化结果，模型只负责组织自然语言。

当前项目是 LangChain4j Tool Calling，不是 LangGraph；没有使用 LangGraph 的 Functional API 或 State API。Spring AI 主要作为模型、Embedding 或生态适配层，不能把它说成已经使用了 LangGraph。

## 23. RAG 从 PDF 到答案的完整流程

### 23.1 PDF 不是直接向量化

PDF 首先要经过文本抽取：

    PDF 文件
      -> PDFBox 按页读取
      -> 清理页眉、页脚和多余空白
      -> 保留章节标题和页码元数据
      -> 文本切分
      -> Embedding
      -> Qdrant upsert

PDFBox 提供的是文档解析，不是向量数据库。Embedding 模型把文本变成向量，Qdrant 保存向量和 payload。

### 23.2 当前切分参数

当前采用字符级滑动窗口，chunk 大约 650 个字符，overlap 大约 100 个字符，步长约为 550 个字符。这里的“切分”是把一页或一段文本拆成多个检索片段，不是把原始 PDF 物理裁成很多小 PDF。

为什么要 overlap：

- 章节边界可能刚好落在切分点。
- 定义、条件和例外可能跨越两个 chunk。
- 没有重叠时，前半句和后半句分离会降低召回。

为什么不能无限增大 overlap：

- chunk 数会变多，Embedding 成本和向量库体积增加。
- 相邻 chunk 重复内容过多，召回结果多样性下降。
- 上下文注入模型时浪费 token。

为什么大约 650 字：

- 太短，规则条件不完整，命中后无法回答。
- 太长，向量语义变得混杂，召回粒度变粗。
- 650/100 是当前项目的工程折中，不是所有 PDF 的固定标准，换文档后应通过评测集调参。

每个向量建议携带：

    {
      "documentId": "student-rules",
      "documentType": "EXTERNAL_REFERENCE",
      "page": 37,
      "section": "第三章 学籍管理",
      "chunkId": "student-rules-p37-c04",
      "text": "..."
    }

回答时把 section、page 和原文片段一起返回，才能做到可解释引用。

### 23.3 混合检索和 RRF

只做向量检索可能漏掉精确的编号、时间和专有名词；只做关键词检索又可能理解不了同义表达。因此当前采用：

    MySQL 关键词检索
    Qdrant 向量检索
              -> RRF 融合
              -> 去重
              -> 取 Top K
              -> 注入模型上下文

RRF 的基本公式：

    RRF(d) = sum(1 / (k + rank_i(d)))

其中 rank_i 是文档在第 i 个检索器中的排名，k 是平滑常数。文档同时出现在关键词和向量结果中，会获得更高的融合分。

伪代码：

    Map<String, Double> scores = new HashMap<>();
    for (int rank = 0; rank < keywordHits.size(); rank++) {
        scores.merge(keywordHits.get(rank).chunkId(),
            1.0 / (60 + rank + 1), Double::sum);
    }
    for (int rank = 0; rank < vectorHits.size(); rank++) {
        scores.merge(vectorHits.get(rank).chunkId(),
            1.0 / (60 + rank + 1), Double::sum);
    }
    return sortByScore(scores).limit(3);

RRF 只负责排序，不能证明答案正确；生成答案前仍要限制上下文来源，并要求模型在证据不足时拒答。

### 23.4 外部 API 失败如何降级

- Embedding API 超时：新文档进入待处理状态，保留原文和失败原因；已有向量继续提供检索。
- Qdrant 不可用：退化到 MySQL 关键词检索，明确提示“语义检索暂不可用”。
- LLM 不可用：返回检索到的规则片段和来源，不伪造自然语言结论。
- 规则库没有命中：拒答并提示用户补充学校、日期或具体制度名称。
- 外部 API Key 缺失：启动时只关闭 Agent/RAG 模块，不影响预约主链路。

## 24. RAG 评测集到底怎么构建

### 24.1 20 条项目规则回归集

20 条是项目内部规则回归集，覆盖：

    预约日期限制
    时间段限制
    room_slot 状态
    容量和候补
    取消预约
    签到窗口
    NO_SHOW 和信用分
    教师整间教室审批

它主要回答“项目自己的规则是否还能被召回”，不是学校制度的泛化测试。当前采用 expectedTitle 做文档级排序判断，适合回归，但不能直接等同于外部知识库准确率。

### 24.2 60 条外部制度集

60 条是外部校园规章问题集，按照问题对应的章节和 chunk 建立 expectedAnchor。当前进一步划分：

- DEV 集 45 条：用于调 chunk 大小、overlap、Top K 和 RRF 参数。
- HOLDOUT 集 15 条：调参完成后只运行一次，用于报告最终泛化结果。

它和机器学习的训练集不完全相同。这里没有训练 Embedding 模型或 LLM，DEV 更像开发/调参集，HOLDOUT 更像最终测试集；不能把它称为“模型训练集”。

### 24.3 Recall@3 的 target 是什么

当前外部 60 条评测的 target 是正确的 chunk anchor，而不是只要命中同一份 document 就算正确。Top 3 返回结果中只要有一个 chunk 包含 expectedAnchor，就算该题 Recall@3 命中。

20 条回归集使用 document title 排名，属于 document-level；60 条外部集使用章节或原文锚点，属于 chunk-level。两者不能直接横向比较，面试时必须主动说明口径。

### 24.4 指标如何解释

    Recall@1 = Top 1 中命中正确 target 的问题数 / 总问题数
    Recall@3 = Top 3 中命中正确 target 的问题数 / 总问题数
    MRR@3 = 命中问题的 1 / 正确结果排名 的平均值

第一次单锚点评测中，精排前 RRF 的 HOLDOUT chunk-level Recall@3 为 73.33%，加入 Cross-Encoder 后为 80.00%。该结果暴露出评测假阴性后，项目升级了 qrels：允许多个经人工核验的等价证据，并统一 PDF 空白符。当前同一 qrels 版本内，固定 15 条历史 TEST 的 RRF Recall@3 为 93.33%，加入加权 Cross-Encoder 后为 100.00%，MRR@3 从 67.78% 提升到 78.89%。必须把“标签修复”和“算法提升”分开说明，且注明这是小规模 chunk-level 指标。

## 26. 消息、Outbox 和幂等追问

### 26.1 为什么不能直接在事务里发 RabbitMQ

数据库事务提交前发送消息，可能出现消息已消费但数据库回滚；数据库提交后发送消息，又可能因为进程宕机导致消息完全没发出去。Outbox 的做法是：

    本地事务：
      更新业务表
      插入 outbox
      commit
    
    异步任务：
      查询 PENDING
      投递 RabbitMQ/Kafka
      成功改 SENT
      失败记录 retry_count 和 next_retry_time

这样至少保证“业务已提交，就有一条待投递记录”。

### 26.2 消费者重复怎么办

消息系统通常只能提供至少一次投递，因此消费者必须幂等：

- 通知：notification 表以 eventId 或业务键去重。
- 信用分：credit_record 以 NO_SHOW:reservationId 唯一。
- 候补补位：waitlist 状态必须是 WAITING 才能转 PROMOTED。
- 统计：按 eventId 去重，或允许统计任务按日期重算。

消费者处理成功后再 ACK。处理失败不 ACK，交给重试或死信队列；永久失败的消息要报警，不能无限快速重试。

### 26.3 RabbitMQ 和 Kafka 为什么都用

RabbitMQ 关注“这件业务动作要被可靠处理”，适合通知、候补补位和提醒；Kafka 关注“已经发生了什么事件”，适合趋势统计、签到率和爽约率分析。两者可以由同一个 Outbox 事件分别投递，但消费者职责不同。

## 27. 按简历逐条追问与回答

### 问：这个项目最核心的业务对象是什么？

答：是 room_slot，表示某间教室在某一天某个时间段的可调度资源。管理员先维护和开放 slot，学生在 OPEN slot 下占用一个名额，教师审批通过后可以整间占用。预约、候补、签到和统计都通过 room_slot 关联，避免把“教室基础信息”和“某天某时间是否可用”混在一起。

### 问：为什么学生预约的是名额，不是教室？

答：自习场景下一个教室可以容纳多个学生，学生实际消费的是一个座位名额。这样 capacity 才有业务意义，也自然产生并发抢名额、候补、签到和爽约治理。教师讲座或课程需要整间教室，则走独立的 teacher_booking 审批流程，并在审批时检查对应 room_slot 是否已有学生预约。

### 问：Redis Lua 里面为什么要判断时间冲突？

答：仅判断某个 slot 是否重复还不够。一个学生可能去抢同一时间段的不同教室，所以还要用 user-time key 判断同一用户在日期、开始时间和结束时间维度是否已有有效预约。Lua 把库存、slot 级重复和时间段冲突放在一个原子脚本中，减少并发窗口。

### 问：Redis 扣成功了，MySQL 失败怎么办？

答：先在捕获异常后执行 Redis 补偿，恢复库存并删除用户占用标记；同时记录失败日志。若补偿本身失败，定时对账任务读取 MySQL 的有效 reservation 数量，重新修正 room_slot 和 Redis 库存。MySQL 是最终事实，Redis 是可修复的并发层。

### 问：为什么不只用数据库事务？

答：只用数据库可以保证正确性，但高并发时大量请求会竞争同一行，失败请求也会打到数据库。Redis Lua 先过滤大部分无资格请求，MySQL 条件 UPDATE 和唯一索引负责最终兜底。这是性能和正确性的分工，不是用缓存替代数据库。

### 问：为什么不只用 Redis？

答：Redis 不是预约订单的长期事实库，也不适合承担复杂查询、审计和事务关联。Redis 可能重启或发生网络故障，所以最终预约必须在 MySQL 落库，并通过 Outbox、补偿和对账解决跨组件一致性。

### 问：为什么预约接口失败率为 0% 仍然有候补？

答：错误率 0% 表示 JMeter 采样器收到的 HTTP 响应都符合脚本判定，不表示所有用户都预约成功。容量为 80 时，剩余用户的业务结果可能是“进入候补”或“名额已满”，这是正常业务分支。还要单独统计正式预约数、候补数和真正的异常数。

### 问：你的压测是 1000 并发吗？

答：命令使用 1000 个用户，并按 BarrierSize 分批同步发起。简历中应准确说“1000 名用户分 2 批、每批 500 人同步抢约”，不要笼统说成 1000 个线程在同一毫秒启动。报告还要注明单机、测试数据、容量和是否包含候补写入。

### 问：你的 QPS 为什么不是 1000 除以 30？

答：吞吐量由实际采样时间窗口和完成请求数决定，RampSeconds 是逐步启动用户的时间，不等于所有请求的完整执行窗口。应直接使用 JMeter HTML 报告或 JTL 的时间戳计算，并说明是预约接口吞吐量还是全场景吞吐量。

### 问：候补为什么用 MySQL FIFO，不用 Redis ZSet？

答：当前第一版优先保证业务可解释性和持久化，使用 create_time、id 排序实现 FIFO。Redis ZSet 当前用于热门教室榜。若候补规模很大、需要按信用分和等待时间动态排序，再引入 ZSet 或专门的优先级结构，但补位最终仍需通过 MySQL 条件更新确认。

### 问：取消预约为什么不删除数据？

答：取消是业务状态，必须保留历史，用于统计取消率、信用规则、审计和用户查看历史。取消后释放一个名额并触发候补补位；物理删除只适合清理明确的压测数据，不能作为正常业务取消逻辑。

### 问：RabbitMQ 消费失败怎么办？

答：消费者处理成功后 ACK；失败时不 ACK，交给有限次数重试和死信队列。通知类消息可以重试，超过次数后保留失败状态并告警。消费者使用 eventId 或业务幂等键去重，避免重复通知、重复扣信用分或重复补位。

### 问：Kafka 消费者停了会不会影响预约？

答：不会影响预约成功，因为预约主链路只依赖 Redis、MySQL 和本地事务。Kafka 消费者停机时，事件保留在 Kafka，恢复后继续消费；统计大屏会有延迟，但核心业务仍可用。

### 问：Kafka 如何统计签到率？

答：统计消费者消费 RESERVATION_SUCCESS、CHECKIN_SUCCESS 和 NO_SHOW 等事件，按 room_slot、room_id、楼栋和日期聚合。签到率可以定义为 CHECKIN_SUCCESS 除以正式预约数，爽约率可以定义为 NO_SHOW 除以应签到预约数。统计结果落到 event_statistics 或 Redis，查询接口不直接扫描全部订单。

### 问：缓存更新为什么删除而不是更新？

答：教室详情和搜索结果存在组合查询，直接更新所有缓存副本容易漏更新。写 MySQL 成功后删除 Caffeine 和 Redis，下一次读取回源并回填。Caffeine 只存在单实例内，Redis 支持实例共享；删除本地缓存时要考虑多实例，可以通过消息广播或较短 TTL 降低窗口。

### 问：ES 查询结果能直接用于预约吗？

答：不能。ES 适合关键词、设备、容量和标签等复杂搜索，但索引可能延迟，开放状态和剩余名额也可能过期。ES 只返回候选 room_slot，用户提交预约后必须重新查询 MySQL，并由 Redis Lua 和条件 UPDATE 判断最终结果。

### 问：RAG 的 Recall@3 为什么不是答案准确率？

答：Recall@3 只表示正确 target 是否出现在前三个召回片段中，属于检索指标。模型可能召回正确片段但理解错误，也可能回答没有忠实引用。因此还要评估引用正确率、答案忠实度、人工正确率和拒答准确率。

### 问：为什么外部 60 条数据要做 HOLDOUT？

答：如果用同一批问题调 chunk、overlap、Top K 和 RRF，再用它报告效果，会有调参偏差。DEV 集用于调参，HOLDOUT 集只在参数确定后评估。当前 HOLDOUT 只有 15 条，能作为项目验证证据，但不应包装成大规模通用 benchmark。

### 问：Agent 有长期记忆吗？

答：当前重点是短期会话记忆和用户预约查询，不应声称已经实现完整长期记忆。长期记忆需要明确的数据模型，例如用户偏好、记忆摘要、更新时间和删除策略，并且要区分用户授权与普通会话历史。面试时应如实说这是后续扩展方向。

## 一、第一优先级：高并发预约链路

这是你简历中最有含金量、也最容易被连续追问的部分。

### 必须掌握

1. 为什么学生预约的是名额，不是整间教室？
2. `room_slot` 如何表示教室、日期、时间段和容量？
3. 1000 人抢 80 个名额时，系统如何保证最多只有 80 条成功预约？
4. Redis Lua 具体做了哪些判断？
5. 为什么 Redis 和 MySQL 要同时使用？
6. Redis 扣库存成功，MySQL 写入失败怎么办？
7. 为什么还需要 MySQL 条件更新和唯一索引？
8. Submit Token 如何防止重复提交？
9. 一个用户同时抢两个教室，如何防止时间冲突？

### 必须能写出的 SQL

```
UPDATE tb_room_slot
SET reserved_count = reserved_count + 1,
    available_capacity = available_capacity - 1
WHERE id = ?
  AND status = 1
  AND reserved_count < total_capacity;
```

必须知道：

- 不能先查询库存，再执行普通更新。
- `reserved_count < total_capacity` 是数据库防超卖条件。
- 返回值为 1 才表示扣减成功。
- 返回值为 0 表示库存不足、状态不对或记录不存在。
- `reserved_count` 最终不能大于 `total_capacity`。

### 必须理解 Redis Lua

Lua 脚本中通常包括：

```
1. 判断库存是否大于 0
2. 判断用户是否已经预约当前 slot
3. 判断用户是否预约了同一时间段的其他教室
4. 扣减库存
5. 写入用户预约标记
6. 设置过期时间
```

面试官可能问：

> Redis Lua 能不能保证最终一致性？

正确回答：

不能。Lua 只能保证 Redis 内部操作的原子性。Redis 可能宕机、网络中断或与 MySQL 数据不一致，所以最终预约结果仍以 MySQL 为准，并通过 Redis 补偿和定时对账修复。

### 必须掌握 Redis 与 MySQL 不一致场景

例如：

```
Redis 扣减成功
MySQL 条件更新成功
reservation 插入失败
```

处理方式：

1. 回滚 Redis 库存。
2. 删除用户预约标记。
3. 记录异常日志。
4. 如果补偿失败，由定时对账任务根据 MySQL 有效预约记录修复 Redis。
5. 对账时 MySQL 是最终事实。

### 必须掌握唯一索引

至少要理解：

```
UNIQUE(user_id, room_slot_id)
```

防止同一个学生重复预约同一个时段。

```
UNIQUE(user_id, reserve_date, time_slot)
```

防止同一个学生同一时间预约多个教室。

面试官可能问：

> 代码中已经判断重复预约了，为什么还要唯一索引？

回答：

前置查询和插入之间存在并发窗口，两个请求可能同时查询到“未预约”。唯一索引属于数据库最终兜底，能在并发情况下阻止重复数据写入。

## 二、第二优先级：事务、锁和并发边界

### 必须掌握 Spring 事务

预约事务至少包括：

```
1. room_slot 条件扣减
2. reservation 插入
3. event_outbox 插入
```

这三步应该在同一个 MySQL 事务中。

面试官会问：

> `@Transactional` 能不能回滚 Redis？

不能。Spring 事务只管理数据库事务，Redis 操作必须单独补偿。

### 必须理解 Redisson 分布式锁

你的简历写了候补取消和补位使用 Redisson，所以要准备：

1. 为什么需要分布式锁？
2. 本地锁能不能解决？
3. 锁的 key 如何设计？
4. 锁超时怎么办？
5. 拿不到锁怎么办？
6. 只有锁够不够？

典型 key：

```
lock:room-slot:{slotId}
```

锁解决的是多个应用实例同时处理同一个 slot 的问题，例如：

```
用户取消预约
定时任务处理爽约
候补补位任务
管理员关闭 slot
```

但锁不是最终兜底，仍然需要：

- 状态条件更新
- 唯一索引
- 数据库事务
- 幂等处理

### 必须知道 `select for update` 的问题

面试官可能问：

> 为什么不用 `SELECT ... FOR UPDATE`？

可以回答：

`SELECT FOR UPDATE` 可以锁住数据库行，但高并发下所有请求会竞争同一行，吞吐量下降，并且大量失败请求仍然进入数据库。当前使用 Redis Lua 先过滤请求，再使用 MySQL 条件更新做最终确认，减少数据库压力。

## 三、第三优先级：候补队列

### 必须掌握候补状态机

```
WAITING -> PROMOTED -> CONFIRMED
WAITING -> CANCELLED
WAITING -> EXPIRED
```

取消预约或爽约释放名额后：

1. 查询最早的 `WAITING` 候补。
2. 条件更新为 `PROMOTED`。
3. 创建预约或生成待确认资格。
4. 设置确认截止时间。
5. 发送补位通知。
6. 超时后改为 `EXPIRED`。
7. 继续补给下一位。

### 必须知道当前 FIFO 的真实实现

你当前第一版候补使用 MySQL FIFO：

```
ORDER BY create_time ASC, id ASC
LIMIT 1
```

不要说成“候补使用 Redis ZSet”，因为你当前 Redis ZSet 主要维护热门教室排行榜。

面试官可能问：

> 为什么不用 Redis List 或 ZSet？

回答：

第一版优先保证候补数据持久化、可审计和实现简单，因此使用 MySQL FIFO。Redis ZSet 当前用于热门教室排行。后续如果候补需要按信用分、等待时间和违约次数动态排序，可以引入 ZSet，但最终补位仍要通过 MySQL 条件更新确认。

### 必须掌握为什么不能删除取消记录

取消预约不能直接删除：

- 需要保留用户历史。
- 需要统计取消率。
- 需要审计。
- 需要触发候补补位。
- 需要区分“未预约”和“预约后取消”。

正常业务应该修改状态，压测数据清理才考虑批量删除。

## 四、第四优先级：签到与信用分

### 签到流程必须能讲清楚

签到接口需要校验：

```
1. 当前用户是预约人
2. reservation.status = RESERVED
3. 当前时间位于签到窗口
4. 预约没有取消
5. 预约没有被标记为 NO_SHOW
```

签到状态更新：

```
UPDATE tb_reserve_order
SET status = 2,
    checkin_time = NOW()
WHERE id = ?
  AND user_id = ?
  AND status = 0;
```

只有更新行数为 1，才允许继续创建签到记录和信用流水。

### 必须掌握签到并发

如果两个请求同时签到：

- 第一个请求将状态从 `RESERVED` 改成 `CHECKED_IN`。
- 第二个请求因为 `status = 0` 条件不成立，更新行数为 0。
- 因此不会重复签到。

### 必须掌握爽约任务

定时任务扫描：

```
checkin_deadline < NOW()
AND status = RESERVED
```

然后：

1. 改为 `NO_SHOW`。
2. 插入信用扣分流水。
3. 释放 room_slot 名额。
4. 触发候补补位。
5. 写 Outbox 事件。
6. 发送通知和统计事件。

### 信用分账户和流水的区别

`credit_account`：

- 保存当前信用分。
- 用于快速判断能否预约。
- 可保存累计加分、扣分和版本号。

`credit_record`：

- 保存每次变更记录。
- 保存原因。
- 保存关联预约。
- 保存变更前后分值。
- 用于审计和申诉。

### 高频追问

> 信用分扣了两次怎么办？

回答：

给信用扣分记录设置业务幂等键，例如：

```
NO_SHOW:{reservationId}
```

并建立唯一约束。重复消费时发现流水已经存在，就不再扣分。

## 五、第五优先级：Outbox、RabbitMQ、Kafka

这是第二个很容易被问深的部分。

### 必须区分 RabbitMQ 和 Kafka

RabbitMQ：

- 预约提醒
- 候补补位通知
- 爽约通知
- 信用分变更通知
- 反馈工单通知

Kafka：

- 预约成功事件
- 取消预约事件
- 签到事件
- 爽约事件
- 候补事件
- 教室开放/关闭事件

一句话：

> RabbitMQ 负责业务动作，Kafka 负责事件流和统计分析。

### 必须掌握 Outbox

不能直接在数据库事务中随意发送消息，因为会出现：

```
数据库成功，消息发送失败
消息发送成功，数据库回滚
服务在数据库提交后、发送消息前宕机
```

正确流程：

```
本地事务：
  更新业务表
  写入 event_outbox
  提交事务

异步任务：
  扫描 PENDING
  投递 RabbitMQ 或 Kafka
  成功改为 SENT
  失败重试
```

### 必须掌握消费者重复消费

RabbitMQ 和 Kafka 都可能重复投递，因此消费者必须幂等。

例如：

```
eventId
reservationId
NO_SHOW:{reservationId}
WAITLIST_PROMOTED:{waitlistId}
```

消费者处理前先检查业务幂等记录，已经处理过就直接确认消息，不能再次扣分、补位或插入通知。

### 必须掌握消息积压

面试官可能问：

> RabbitMQ 或 Kafka 积压怎么办？

回答：

1. 监控队列长度和消费延迟。
2. 增加消费者实例或消费线程。
3. 限制生产速度或进行削峰。
4. 对通知类消息设置有限重试。
5. 失败消息进入死信队列。
6. 对关键消息告警。
7. 统计类数据允许延迟，不影响预约主链路。

### 必须掌握 Kafka 为什么不能防超卖

Kafka 是异步事件流，消息消费存在延迟，不能作为库存判断依据。预约成功必须在同步请求中完成，依赖：

```
Redis Lua
MySQL 条件更新
唯一索引
```

Kafka 只记录已经发生的预约事件。

## 六、第六优先级：缓存和 Redis ZSet

### Caffeine + Redis 二级缓存必须掌握

读取流程：

```
1. 查询 Caffeine
2. 未命中则查询 Redis
3. Redis 未命中则查询 MySQL
4. 回填 Redis
5. 回填 Caffeine
```

作用：

- Caffeine：减少单机网络访问。
- Redis：多个实例共享缓存。
- MySQL：最终数据来源。

### 为什么库存不能用 Caffeine

库存具有高并发和强一致要求，本地缓存无法在多实例之间实时同步。因此库存不能依赖 Caffeine，库存必须使用 Redis Lua 和 MySQL 条件更新。

### 缓存更新策略

修改教室后：

1. 更新 MySQL。
2. 删除 Redis 缓存。
3. 删除当前实例 Caffeine 缓存。
4. 其他实例通过消息广播或 TTL 最终失效。

面试官可能问：

> 为什么不直接更新缓存？

因为教室详情、设备、标签和搜索结果可能有多个缓存组合，逐个更新容易遗漏。删除后下一次读取回源并回填，实现更简单。

### Redis ZSet 当前用途

```
rank:room:hot
```

可以通过浏览次数、预约次数、签到次数更新分数：

```
ZINCRBY rank:room:hot 1 roomId
```

查询热门教室：

```
ZREVRANGE rank:room:hot 0 9 WITHSCORES
```

要说清楚：

- ZSet 用于热门排行。
- 当前候补是 MySQL FIFO。
- 不要把两个用途混为一谈。

## 七、第七优先级：Agent、LangChain4j 和 RAG

这是你简历中最容易被质疑真实性的部分，必须准备得特别准确。

### 必须先说清当前技术边界

你目前使用的是：

- Qdrant 向量数据库

不是：

- LangGraph
- LangGraph Functional API
- LangGraph State API
- 完整自动执行型 Agent

### 当前 Agent 具备哪些工具

主要是：

```
search_available_slots
retrieve_policy_knowledge
get_my_reservations
```

Agent 的流程：

```
用户自然语言
  -> 模型识别意图
  -> 调用只读 Tool
  -> 查询教室或规则
  -> 生成回答或预约草稿
  -> 用户确认
  -> 普通预约接口完成正式预约
```

面试官问：

> 为什么不让 Agent 直接调用预约接口？

回答：

模型可能出现参数解析错误、重复调用和日期理解错误。写操作必须经过普通业务接口，由后端重新执行权限、信用分、库存、时间冲突和 Submit Token 校验。Agent 负责理解和查询，领域服务负责最终写入。

### PDF RAG 流程必须会画

```
PDF
  -> PDFBox 提取文本
  -> 清理页眉页脚
  -> 保留页码和章节
  -> 滑动窗口切分
  -> Embedding
  -> 写入 Qdrant
  -> 用户提问
  -> MySQL 关键词检索
  -> Qdrant 向量检索
  -> RRF 融合
  -> Top K 片段
  -> LLM 生成答案
```

### 你当前的切分参数

- chunk：约 650 字符
- overlap：约 100 字符
- step：约 550 字符
- 字符级滑动窗口

必须知道为什么使用 overlap：

如果不重叠，规则的条件和例外可能被切到两个片段中，导致单个 chunk 信息不完整，降低召回率。

必须知道为什么不能无限增大 overlap：

- chunk 数量增加。
- Embedding 成本增加。
- 向量库膨胀。
- 结果重复度增加。
- 注入模型的上下文浪费。

### 必须理解 RRF

关键词检索和向量检索得到两个排序结果，RRF 根据各自排名融合：

```
RRF(d) = Σ 1 / (k + rank(d))
```

同一个 chunk 同时被两个检索器召回，就会获得更高融合分。

### 必须区分 document-level 和 chunk-level

20 条项目规则回归集：

- 主要是 document-level。
- 通过正确文档或标题判断是否命中。

60 条外部制度集：

- 主要是 chunk-level。
- 通过章节、锚点或正确片段判断是否命中。
- 分为 DEV 和 HOLDOUT。
- DEV 用于调参数。
- HOLDOUT 用于最终评估。

不能把两个 Recall 指标直接混为同一个结果。

## 八、第八优先级：Agent 评测

### 必须掌握 Recall@K

```
Recall@3 =
Top 3 中命中正确 chunk 的问题数 / 总问题数
```

Recall@3 只说明检索是否召回正确片段，不代表最终答案一定正确。

### 还需要理解这些指标

- MRR：正确结果排名越靠前，得分越高。
- Citation Accuracy：回答中的引用是否真的支持结论。
- Faithfulness：回答是否忠实于召回内容。
- Answer Accuracy：人工判断答案是否正确。
- Refusal Accuracy：没有证据时是否正确拒答。
- Tool Selection Accuracy：是否选择了正确工具。
- Tool Argument Accuracy：工具参数是否正确。

面试官问：

> 100% 的 Recall@3 是否说明系统已经没有问题？

正确回答：

不能。固定 15 条历史 TEST 已被查看并纠正过标签，所以它现在更适合作为回归集；20 条 BLIND_TEST 虽然冻结后只正式运行一次，但规模仍小，而且题目来自同一份规章。100% 只表示这 20 条题的目标证据 Chunk 都进入 Top 3，不代表生成答案必然正确，更不代表跨学校、跨文档的通用能力。因此还要单独评估引用正确率、忠实度、人工正确率、无依据回答比例和拒答准确率。

### 一次真实 Agent 故障复盘

第一次执行 65 条评测时，模型请求已基本完成，但最终汇总报错：

## 32. 整体架构如何讲

面试时不要一开始罗列中间件，应该先从一次预约操作出发：

    浏览器或 Agent 助手
              |
              v
    Spring Boot REST Controller
              |

              |
              v
    ReservationService
       |       |       |
       |       |       +--> Redis Lua、Redisson
       |       |
       |       +----------> MySQL、MyBatis
       |
       +------------------> Outbox
                                |
                  +-------------+-------------+
                  |                           |
                  v                           v
             RabbitMQ                      Kafka
                  |                           |
                  v                           v
              通知消费者                  统计消费者
                  |
                  v
       notification 表、SSE、前端通知中心

各组件的职责：

- Controller：接收请求、完成参数校验、返回统一响应。
- Security：识别用户身份并判断角色。
- Service：编排完整业务规则。
- Redis：处理热点状态、短期状态和高并发预判。
- MySQL：保存预约事实、状态和审计数据。
- Outbox：保存必须投递的异步事件。
- RabbitMQ：处理可靠的业务任务。
- Kafka：保存已经发生的事件并供统计消费。
- SSE：把已生成的通知推送给在线浏览器。
- Agent：负责自然语言理解和只读工具编排，不绕过 Service 写数据库。

当前采用单体架构是因为预约、候补、签到和信用分共享核心事务和数据模型。通过 Controller、Service、消息消费者和 Agent 工具边界保持模块化，后续可以优先拆分通知、统计和知识库服务，不必一开始拆分预约主链路。

## 33. room、room_slot、reservation 的关系

    room
      表示物理教室，例如计算机楼 106

    room_slot
      表示教室在某一天某个时间段的可调度资源

    reservation
      表示某个用户占用了 room_slot 的一个名额

示例：

    room:
      id = 1
      building = 计算机楼
      room_number = 106
      capacity = 180

    room_slot:
      id = 5896
      room_id = 1
      reserve_date = 2026-12-31
      time_slot = 18:00-20:00
      total_capacity = 80
      available_capacity = 80
      status = OPEN

    reservation:
      user_id = 1001
      room_id = 1
      room_slot_id = 5896
      status = RESERVED

room 的物理容量和 room_slot 的开放名额不是同一个概念。教室可以容纳 180 人，但管理员可以只开放 80 个自习名额。因此预约业务必须围绕 room_slot，而不是直接围绕 room。

## 34. room_slot 状态机

业务状态可以解释为：

    OPEN
      -> CLOSED
      -> MAINTENANCE
      -> TEACHER_BOOKED
      -> EXPIRED

主要规则：

- CLOSED -> OPEN：管理员重新开放。
- OPEN -> CLOSED：没有有效学生预约时允许关闭。
- OPEN -> MAINTENANCE：没有有效学生预约时允许维护。
- OPEN -> TEACHER_BOOKED：教师审批通过且没有学生预约时占用。
- OPEN -> EXPIRED：时段结束后由定时任务处理。
- 已有学生预约时，第一版不允许管理员直接关闭或维护。

关闭有预约的时段需要拒绝，因为系统已经向学生承诺了预约资格。直接关闭会带来改签、通知、库存和信用处理问题，而第一版没有完整的冲突处理流程。

## 35. reservation 状态机

    RESERVED -> CANCELLED
    RESERVED -> CHECKED_IN
    RESERVED -> NO_SHOW
    CHECKED_IN -> FINISHED

状态变化必须使用条件更新，而不能只在 Java 代码中判断：

    UPDATE tb_reserve_order
    SET status = 4,
        update_time = NOW()
    WHERE id = ?
      AND user_id = ?
      AND status = 1;

只有返回值为 1，才表示本次签到成功。返回 0 说明订单已经取消、签到或被其他请求处理。

状态机可以阻止以下非法变化：

    CANCELLED -> CHECKED_IN
    NO_SHOW -> CHECKED_IN
    CHECKED_IN -> CANCELLED

如果允许这些变化，签到率、爽约率和信用分都会失真。

## 36. 从点击预约到返回结果

一次正式预约的顺序是：

1. 用户登录，JWT 过滤器识别当前用户。
2. 用户获取一次性 Submit Token。
3. 后端校验日期和时间段格式。
4. 按用户 ID 获取 Redisson 用户锁。
5. 消费 Submit Token，防止重复提交。
6. 校验信用分和预约资格。
7. 查询 room_slot，确认存在且状态为 OPEN。
8. 初始化或读取 Redis 库存。
9. 执行 Redis Lua，检查库存和用户冲突。
10. Redis 预扣成功后进入 MySQL 事务。
11. MySQL 条件更新 room_slot 库存。
12. 插入 reservation。
13. 在同一个事务中写入 Outbox。
14. 提交事务并返回预约成功。
15. 异步发送 RabbitMQ 通知和 Kafka 事件。

如果 Redis 库存不足：

    joinWaitlist = true
        -> 写入候补记录
        -> 返回候补成功

    joinWaitlist = false
        -> 返回库存不足

这条链路中，只有第 10 到第 13 步属于数据库事务；Redis 不受 Spring 事务管理，需要补偿。

## 37. 为什么需要两次库存判断

Redis Lua 负责高并发入口：

    stock > 0
      -> 扣减 Redis stock
      -> 写入用户占用标记

MySQL 条件更新负责最终确认：

    UPDATE tb_room_slot
    SET available_capacity = available_capacity - 1,
        reserved_count = reserved_count + 1
    WHERE id = ?
      AND status = 1
      AND available_capacity > 0;

两者的作用不同：

- Redis Lua：减少数据库竞争，保证 Redis 内的检查和扣减原子化。
- MySQL 条件更新：以数据库事实为准，阻止最终超卖。
- 唯一索引：防止重复预约数据写入。

不能只用 Redis，因为 Redis 不是预约订单的最终事实库；也不能只用 MySQL，因为高并发失败请求会造成大量数据库行竞争。

## 38. Redis 和 MySQL 不一致怎么处理

典型失败：

    Redis 扣减成功
    MySQL 条件更新成功
    reservation 插入失败

如果不处理，Redis 会少一个名额。因此需要：

1. 恢复 Redis 库存。
2. 从 Redis 用户集合删除用户。
3. 删除用户时间占用 Key。
4. 记录异常日志。
5. 如果补偿失败，定时任务按 MySQL 有效预约数重新对账。

对账原则：

    MySQL 有效预约数
        = room_slot.reserved_count
        = total_capacity - available_capacity

Redis 是高性能并发层，MySQL 是最终业务事实。面试中不要说两者是强一致，只能说通过事务、补偿和对账达到最终一致。

## 39. 同一用户跨教室冲突

用户时间 Key 是：

    reserve:user-time:{userId}:{reserveDate}:{timeSlot}

例如：

    reserve:user-time:1001:2026-12-31:18:00-20:00

这个 Key 不包含 roomId，所以用户预约教室 1 后，再预约教室 2，仍然会命中同一个 Key。

Redis Lua 的判断顺序是：

    1. 检查库存
    2. 检查当前 slot 是否已经有该用户
    3. 检查用户时间 Key
    4. 扣库存并写入 Key

同时数据库中的 active_key 也使用用户、日期和时间段组成，并有唯一索引作为最终兜底。

> 通过不包含教室 ID 的 Redis 用户时间 Key，限制同一用户在相同日期和时间段内只能预约一个教室；结合用户级 Redisson 锁、有效预约业务校验和 MySQL active_key 唯一索引，防止并发请求造成跨教室重复预约。

不要只写：

> Redis 保证同一用户不能预约多个教室。

因为真正的保障是多层组合：

    Redisson 用户锁
    + Redis Lua
    + 用户时间 Key
    + MySQL 查询校验
    + active_key 唯一索引

# 第三部分：消息、缓存和 Agent 深挖

## 41. 候补补位的详细过程

容量为 1 时：

    用户 A -> 正式预约
    用户 B -> WAITING
    用户 A -> CANCELLED
    释放一个名额
    查询最早的 WAITING
    用户 B -> PROMOTED
    发送候补补位通知

当前 FIFO 查询思路：

    SELECT *
    FROM tb_reserve_waitlist
    WHERE room_id = ?
      AND reserve_date = ?
      AND time_slot = ?
      AND status = 0
    ORDER BY create_time ASC, id ASC
    LIMIT 1;

当前实现是 MySQL FIFO，不是信用分排序。信用分用于预约资格和违约治理，当前没有真正参与候补排序。

候补补位必须使用条件更新：

    UPDATE tb_reserve_waitlist
    SET status = 1,
        update_time = NOW()
    WHERE id = ?
      AND status = 0;

只有更新成功的线程才能继续补位。这样即使多个任务同时处理，也不会把同一条候补记录重复提升。

## 42. 候补为什么不直接删除

候补取消、过期和补位都应该修改状态：

    WAITING -> CANCELLED
    WAITING -> PROMOTED
    WAITING -> EXPIRED

不能直接删除，因为：

- 需要保留用户历史。
- 需要统计候补成功率。
- 需要审计谁在什么时候加入候补。
- 需要排查为什么没有补位。
- 需要支持用户查看历史记录。

只有压测清理才适合批量删除，而且要同时清理预约、候补、通知、Outbox 和缓存。

## 43. 信用分如何参与业务

当前信用分链路：

    用户预约
      -> 查询 credit_account
      -> 判断是否低于预约阈值
      -> 通过后继续预约

用户爽约：

    定时任务发现超过签到截止时间
      -> RESERVED 改为 NO_SHOW
      -> 写入 credit_record
      -> 扣减 credit_account
      -> 释放名额
      -> 触发候补
      -> 写通知和事件

信用记录必须有业务幂等键：

    NO_SHOW:{reservationId}

如果 RabbitMQ 重复投递，消费者先检查这个 key 或唯一索引，已经扣过分就直接确认消息，不再重复扣分。

当前应该如实表述：

    信用分用于预约资格校验和爽约处罚。
    当前候补仍然采用 FIFO。
    信用分排序属于后续扩展。

## 44. Outbox 的详细异常场景

场景一：业务失败，不能写 Outbox：

    room_slot 更新失败
    reservation 未插入
    Outbox 也不应该存在

场景二：业务成功，进程在发送消息前宕机：

    room_slot 更新成功
    reservation 插入成功
    Outbox 已提交
    RabbitMQ 还没发送

服务恢复后，定时任务可以重新扫描 Outbox，因此消息不会因为一次宕机直接丢失。

场景三：消息已经发送，但数据库状态还没改成 SENT：

    RabbitMQ 已收到
    服务在更新 Outbox 前宕机

服务恢复后可能再次发送，因此消费者必须幂等。这说明 Outbox 通常保证至少一次投递，而不是严格只发送一次。

## 45. RabbitMQ 重试和死信

建议按以下策略解释：

    PENDING -> SENT
    PENDING -> RETRYING
    RETRYING -> SENT
    RETRYING -> DEAD

失败时保存：

- retry_count
- next_retry_time
- last_error
- 更新时间

重试不能无限快速进行，否则消息失败时会持续打满队列。应该采用退避，例如：

    第一次：10 秒后
    第二次：30 秒后
    第三次：2 分钟后
    超过次数：死信

通知消息进入死信后，管理员需要能在运维页面看到积压和失败原因。

## 46. Kafka 统计为什么允许延迟

预约成功必须同步返回，所以预约事务不能等待 Kafka 消费完成：

    用户预约成功
       -> MySQL 提交
       -> 返回成功
       -> Outbox 异步投递 Kafka
       -> statistics-consumer 聚合

Kafka 统计可以延迟几秒甚至更久，因为它只影响：

- 管理员大屏刷新时间。
- 热门教室排行榜。
- 使用率统计。
- 爽约率统计。

它不影响：

- 是否还有库存。
- 是否允许预约。
- 是否允许签到。

因此面试中必须强调 Kafka 是旁路分析系统，而不是核心事务组件。

## 47. Caffeine 和 Redis 的两级缓存

读取教室详情的流程：

    Caffeine 命中
       -> 直接返回

    Caffeine 未命中
       -> Redis 命中
       -> 回填 Caffeine
       -> 返回

    Redis 未命中
       -> 查询 MySQL
       -> 回填 Redis
       -> 回填 Caffeine
       -> 返回

Caffeine 适合本机热点数据，因为访问速度快；Redis 适合多个应用实例共享缓存。

库存不能使用 Caffeine，因为一个实例扣减后，其他实例的本地缓存不会实时变化。库存必须走 Redis Lua 和 MySQL 条件更新。

## 48. 缓存穿透、击穿和雪崩

### 缓存穿透

用户查询不存在的教室，缓存和数据库都没有，每次请求都会打数据库。

处理：

- 缓存空值。
- 参数校验。
- 限制查询频率。
- 对非法 ID 快速拒绝。

### 缓存击穿

某个热点教室缓存刚好过期，大量请求同时回源。

处理：

- 互斥锁。
- 逻辑过期。
- 热点数据提前刷新。
- 随机 TTL。

### 缓存雪崩

大量 Key 同时过期，瞬间冲击数据库。

处理：

- TTL 增加随机值。
- 分批预热。
- 限流和熔断。
- 数据库连接池保护。

## 49. Agent 工具调用的真实边界

Agent 不是直接操作数据库的智能管理员。当前工具主要是：

    search_available_slots
    retrieve_policy_knowledge
    get_my_reservations

流程：

    用户自然语言
      -> 模型识别意图
      -> 调用只读工具
      -> 工具调用 Service
      -> 返回结构化结果
      -> 模型生成回答或预约草稿

正式预约仍然走普通预约接口：

    Submit Token
    -> 信用分校验
    -> Redis Lua
    -> MySQL 条件更新
    -> reservation 插入

这么做的原因是模型可能出现：

- 日期解析错误。
- 时间段参数缺失。
- 重复调用工具。
- 越权访问其他用户数据。
- 误触发写操作。

因此模型负责理解和编排，领域服务负责权限、一致性和最终写入。

## 50. LangChain4j 中 @Tool 的含义

工具方法可以抽象为：

    @Tool("查询当前用户可预约的教室时段")
    public List<RoomSlotView> searchAvailableSlots(
            LocalDate date,
            String timeSlot,
            Integer people,
            String building) {
        Long userId = UserContext.getRequired().getId();
        return roomSlotService.searchOpenSlots(
            date, timeSlot, people, building);
    }

说明：

- @Tool 是工具描述，模型根据名称和参数决定是否调用。
- 方法内部仍然调用 Service，不能绕过业务层访问数据库。
- userId 必须从登录上下文取得，不能信任模型传来的 userId。
- 参数仍然需要日期、时间段和人数校验。

当前项目使用 LangChain4j Tool Calling，不是 LangGraph，也没有使用 LangGraph Functional API 或 State API。

## 51. RAG 从 PDF 到答案

完整流程：

    PDF
      -> PDFBox 按页抽取文本
      -> 清理页眉、页脚和空白
      -> 保留页码和章节名
      -> 按滑动窗口切 chunk
      -> 调用 Embedding
      -> 写入 Qdrant
      -> 用户提问
      -> MySQL 关键词检索
      -> Qdrant 向量检索
      -> RRF 融合
      -> 取 RRF Top 30 候选
      -> qwen3-rerank Cross-Encoder 精排
      -> 取 Top 3 证据上下文
      -> LLM 生成答案

当前大约使用：

    chunkSize = 650 字符
    overlap = 100 字符
    step = 550 字符

例如长度 1600 的文本：

    chunk 1: [0, 650)
    chunk 2: [550, 1200)
    chunk 3: [1100, 1600)

overlap 的作用是保留相邻片段之间的上下文，避免一条规则的条件和例外刚好被切开。

## 52. 为什么不能把 PDF 直接转成一个向量

一整份 PDF 可能包含几百页、很多主题。整篇只生成一个向量会导致：

- 查询粒度太粗。
- 不同章节语义混杂。
- 无法准确定位页码。
- 注入上下文时内容过长。

切成 chunk 后，每个片段可以独立召回，并携带：

    documentId
    page
    section
    chunkId
    content

这样模型回答时可以说明证据来自哪一章哪一页。

## 53. 面试官问“为什么用 RRF”

关键词搜索适合精确术语、编号和时间，例如：

    第 37 条
    08:00-20:00
    NO_SHOW

向量搜索适合自然语言改写，例如：

    没有按时去教室会有什么后果

两个结果的原始分数通常不可直接比较，因此 RRF 只根据排名进行融合：

    RRF(d) = sum(1 / (k + rank(d)))

如果某个 chunk 同时被关键词和向量检索召回，它通常会得到更高的融合分。

但 RRF 不能保证答案正确。最终还要检查：

- 召回内容是否真的相关。
- 引用是否支持回答。
- 模型是否胡编。
- 没有证据时是否拒答。

## 54. Agent 外部 API 失败怎么降级

Embedding API 失败：

    保留原文
    标记知识库任务失败
    已有向量继续使用

Qdrant 不可用：

    降级到 MySQL 关键词检索

LLM 不可用：

    返回召回片段和来源
    不生成没有证据的结论

API Key 缺失：

    关闭 Agent 或 RAG 功能
    不影响预约主链路启动

工具调用超时：

    限制单轮工具次数
    设置超时
    返回可理解的失败提示

# 第四部分：每个功能的具体实现顺序

本部分按照“用户操作发生以后，后端实际先做什么、再做什么”的顺序整理。面试时可以直接按照步骤回答。

## 56. 注册功能

### 执行顺序

1. 前端提交用户名、密码和手机号。
2. Controller 接收请求并进行非空、长度和手机号格式校验。
3. Service 查询手机号是否已经注册。
4. 对密码进行 BCrypt 加密，不能保存明文密码。
5. 设置默认角色为 USER，设置账号状态为正常。
6. 插入用户表。
7. 初始化该用户的 credit_account，默认信用分为 100。
8. 返回注册成功。

### 关键校验

- 手机号必须符合规定格式。
- 用户名不能重复。
- 密码不能过短。
- 手机号唯一索引防止并发重复注册。
- 不能让注册请求直接指定 ADMIN 角色。

### 失败处理

- 手机号已存在：返回业务错误。
- 数据库唯一约束冲突：转换成“账号已存在”。
- 用户插入成功但信用账户初始化失败：放入同一数据库事务，整体回滚。

## 57. 登录功能

### 执行顺序

1. 前端提交用户名和密码。
2. Controller 接收参数。
3. Service 根据用户名查询用户。
4. 检查用户是否存在、状态是否正常。
5. 使用 BCrypt 比较明文密码和数据库密文。
6. 生成 JWT，写入用户 ID、角色和过期时间。
7. 可选地将 Token 状态写入 Redis。
8. 返回 Token、用户信息和角色。

### 请求后续流程

1. 浏览器保存 JWT。
2. 每次请求在 Authorization 中携带 JWT。
3. Security Filter 解析 JWT。
4. 校验签名和过期时间。
5. 将用户身份写入 SecurityContext 或 UserContext。
6. Controller 和 Service 根据角色判断权限。

### 追问重点

JWT 只是身份凭证，不等于业务权限。管理员接口仍然需要判断角色，学生查询自己的预约时还必须使用当前登录用户 ID，不能相信前端传入的 userId。

## 58. 教室创建功能

### 执行顺序

1. 管理员提交楼栋、教室号、容量、类型、设备和状态。
2. Security 检查当前用户角色为 ADMIN。
3. 校验楼栋和教室号不能为空。
4. 校验容量大于 0。
5. 校验设备格式。
6. 查询或依赖楼栋加教室号唯一索引判断是否重复。
7. 插入 room 表。
8. 插入设备和标签表。
9. 删除教室详情缓存和搜索缓存。
10. 返回教室信息。

### 修改教室

1. 根据 roomId 查询教室是否存在。
2. 判断容量修改是否小于已有开放时段名额。
3. 更新 MySQL。
4. 同步更新或删除设备标签。
5. 删除 Caffeine 和 Redis 缓存。
6. 发送教室信息变更事件，供 ES 同步。

### 修改为不可用

1. 查询教室。
2. 检查是否存在仍然有效的 room_slot 或预约。
3. 只修改 room.status，不删除 room 记录。
4. 管理员列表默认仍显示该教室，并显示“不可用”。
5. 学生可预约查询过滤不可用教室。

教室不可用后不能直接从数据库删除，否则历史预约会失去关联，也无法审计。

## 59. 管理员创建 room_slot

### 单个创建

1. 管理员提交 roomId、日期、时间段、开放名额、开放类型。
2. 校验教室存在且可用。
3. 校验日期必须满足预约时间规则。
4. 校验时间段格式为 HH:mm-HH:mm。
5. 校验时间段在允许范围内，例如 08:00 到 20:00。
6. 校验开始时间早于结束时间。
7. 校验开放名额不超过教室物理容量。
8. 检查相同 roomId、日期和时间段是否已存在。
9. 写入 room_slot。
10. 初始化 available_capacity 等于 total_capacity。
11. 删除相关查询缓存。
12. 返回创建结果。

### 批量创建

1. 管理员提交教室集合、日期范围和时间段集合。
2. 服务端展开成多个 roomId、日期和时间段组合。
3. 对每个组合执行参数校验。
4. 先检查数据库唯一约束和已有冲突。
5. 将没有冲突的记录批量插入。
6. 对重复记录返回跳过数量和原因。
7. 对成功创建的 OPEN slot 初始化 Redis 库存。
8. 记录管理员操作日志。

批量创建不能把一条失败记录吞掉后全部返回成功，应该返回成功数、跳过数和失败原因。

## 60. room_slot 开放、关闭和维护

### 开放

1. 根据 slotId 查询 room_slot。
2. 检查当前状态是否允许变更。
3. 检查日期和时间段是否已经过期。
4. 更新状态为 OPEN。
5. 初始化 Redis stock。
6. 删除教室和时段查询缓存。
7. 写入 ROOM_SLOT_OPENED 事件。

### 关闭或维护

1. 根据 slotId 查询记录。
2. 查询该 slot 的有效预约数量。
3. 如果有效预约数量大于 0，返回拒绝原因。
4. 如果存在未处理候补，也要按业务决定是否允许关闭。
5. 使用状态条件更新，避免并发修改覆盖。
6. 删除 Redis stock、用户集合和相关时间 Key。
7. 更新状态为 CLOSED 或 MAINTENANCE。
8. 写入事件和管理员操作日志。

### 为什么按钮点了没有反应

常见原因不是按钮本身，而是后端根据已有预约拒绝了关闭或维护。前端必须显示后端返回的具体原因，不能只把按钮置灰而不提示用户。

## 61. 学生查询可预约时段

### 执行顺序

1. 前端提交日期、时间段、人数、楼栋等筛选条件。
2. Controller 校验查询参数。
3. Service 只查询 room.status 正常且 room_slot.status 为 OPEN 的记录。
4. 过滤日期已过期的 slot。
5. 过滤 available_capacity 小于用户人数的 slot。
6. 读取缓存或查询 MySQL。
7. 返回教室信息、时间段、总名额、剩余名额和是否可预约。

查询结果只用于展示。用户点击预约后，必须重新走库存和状态校验，不能相信列表中的剩余名额。

## 62. 学生正式预约

### 执行顺序

1. 前端请求一次性 Submit Token。
2. 后端生成随机 token，写入 Redis，设置 5 分钟过期时间。
3. 用户提交 roomId、日期、时间段和 Submit Token。
4. Security 获取当前登录用户。
5. 校验日期和时间段格式。
6. 获取用户级 Redisson 锁。
7. 删除并消费 Submit Token。
8. 查询并校验信用分。
9. 查询 room_slot 是否存在且为 OPEN。
10. 初始化或读取 Redis stock。
11. 执行 Redis Lua。
12. Lua 判断库存、当前 slot 重复预约和用户时间冲突。
13. Lua 成功后扣减库存并写入占用标记。
14. 开启 MySQL 事务。
15. 使用条件 UPDATE 扣减 room_slot 数据库库存。
16. 创建 reservation，写入 active_key。
17. 写入预约成功 Outbox。
18. 提交事务。
19. 返回预约成功。
20. 异步发送通知和 Kafka 事件。

### Redis Lua 结果

    0：预扣成功
    1：库存不足
    2：已预约当前 slot
    3：Redis 库存 Key 不存在
    4：同一用户同一时间段已有其他教室预约

### 关键原则

Redis 预扣只是并发入口保护，MySQL 条件更新才是最终数据库确认；reservation 和 Outbox 必须在同一个数据库事务中。

## 63. 满员后加入候补

### 执行顺序

1. Redis Lua 返回库存不足。
2. 如果用户没有选择加入候补，直接返回名额已满。
3. 如果用户选择加入候补，查询是否已有同一 slot 的候补。
4. 构造 WAITING 状态的候补记录。
5. 依赖唯一索引或 insert ignore 防止重复加入。
6. 增加 room_slot.waitlist_count。
7. 写入候补事件。
8. 返回候补成功和当前候补状态。

当前候补顺序是：

    ORDER BY create_time ASC, id ASC

也就是 FIFO，不是信用分排序。

## 64. 取消预约

### 执行顺序

1. 根据 orderId 查询预约。
2. 校验当前用户是预约人，或当前用户是管理员。
3. 判断状态是否为可取消状态。
4. 使用条件 UPDATE 将状态改为 CANCELLED。
5. 清空 active_key。
6. 释放 room_slot 一个名额。
7. 删除或修正 Redis 用户集合、用户时间 Key 和库存。
8. 获取 room-slot 级 Redisson 锁。
9. 查询第一条 WAITING 候补。
10. 条件更新候补为 PROMOTED。
11. 创建待确认资格或正式补位记录。
12. 写入取消和候补补位 Outbox。
13. 返回取消成功。

取消不能直接 DELETE reservation，因为历史、统计、审计和信用治理都需要保留。

## 65. 候补自动补位

### 执行顺序

1. 取消预约或 NO_SHOW 释放名额。
2. 获取 lock:room-slot:{slotId}。
3. 查询最早的 WAITING 候补。
4. 检查候补用户是否已经有同一时间段有效预约。
5. 如果有冲突，将该候补标记为跳过或过期，继续下一位。
6. 条件更新候补状态为 PROMOTED。
7. 创建正式预约或待确认记录。
8. 更新 room_slot 计数。
9. 写入补位 Outbox。
10. 提交事务。
11. 发送候补补位通知。
12. 超过确认时间仍未确认，改为 EXPIRED，继续补位。

锁防止多个任务同时补同一位候补，状态条件更新防止锁失效后重复处理。

## 66. 学生签到

### 执行顺序

1. 学生输入订单号和签到码，或扫描二维码。
2. Security 获取当前用户。
3. 根据订单号查询预约。
4. 校验订单属于当前用户。
5. 校验订单状态为 RESERVED。
6. 校验签到码一致。
7. 计算预约开始时间。
8. 校验当前时间在开始前 15 分钟到开始后 15 分钟之间。
9. 使用条件 UPDATE 将订单改为 CHECKED_IN。
10. 插入 checkin 记录。
11. 写入正常签到信用流水，可选加分。
12. 写入签到通知 Outbox。
13. 写入 CHECKIN_SUCCESS Kafka 事件。
14. SSE 推送签到成功。
15. 返回签到成功。

第 9 步返回 0 时，说明订单已经被其他请求处理，不能重复插入签到记录。

## 67. NO_SHOW 定时处理

### 执行顺序

1. Spring 定时任务按批次查询已过签到截止时间的 RESERVED 订单。
2. 使用条件 UPDATE 将状态改为 NO_SHOW。
3. 只有更新成功的订单才继续扣信用分。
4. 使用 reservationId 作为幂等键插入信用流水。
5. 扣减用户信用分。
6. 释放 room_slot 名额。
7. 触发候补补位。
8. 写入 NO_SHOW Kafka 事件。
9. 写入 RabbitMQ 违约通知。
10. SSE 推送信用分变化。

定时任务必须分页，不能一次性扫描全部历史订单。任务重复执行时，状态条件和信用流水唯一约束保证不会重复处罚。

## 68. 教师整间教室预约

### 教师申请

1. 教师提交教室、日期、时间段和用途。
2. 校验教师身份。
3. 校验日期和时间段。
4. 查询是否存在冲突 room_slot。
5. 创建 teacher_booking，状态为 PENDING。
6. 通知管理员审批。

### 管理员审批通过

1. 查询 teacher_booking。
2. 检查审批人角色为 ADMIN。
3. 查询对应 room_slot。
4. 如果 slot 有学生有效预约，拒绝审批。
5. 如果 slot 不存在，创建 TEACHER_BOOKED 类型的 slot。
6. 如果存在且无学生预约，状态改为 TEACHER_BOOKED。
7. 更新 teacher_booking 为 APPROVED。
8. 写入审批事件和通知。

教师预约占用整间教室，因此不能和学生名额预约强行覆盖。

## 69. 反馈工单

### 学生提交反馈

1. 学生提交标题、内容和关联业务单号。
2. 校验内容长度。
3. 创建 feedback，状态为 OPEN。
4. 写入管理员通知 Outbox。
5. 返回工单编号。

### 管理员处理反馈

1. 管理员查询 OPEN 工单。
2. 查看学生、订单和相关 room_slot 信息。
3. Agent 可以生成问题分类和建议回复，但不能自动发送。
4. 管理员人工确认内容。
5. 写入回复记录。
6. 更新工单状态为 REPLIED 或 CLOSED。
7. 写入 notification 表对应的 Outbox。
8. SSE 通知学生。

Agent 生成建议不等于管理员回复，最终发送必须是管理员明确操作。

## 70. 通知功能

### 后端发送顺序

1. 预约、取消、补位、签到或反馈业务在事务中完成。
2. 同一个事务写入 notification_outbox。
3. 定时任务扫描 PENDING 记录。
4. 投递 RabbitMQ。
5. 消费者接收消息。
6. 以 eventId 或业务键检查是否重复。
7. 插入 tb_notification。
8. 如果用户在线，调用 SseEmitter 推送。
9. 投递成功后 ACK。
10. 用户阅读后更新 read_status。

### 前端行为

当前前端通过 EventSource 监听 SSE，收到通知后刷新通知列表、未读数量和相关数据。当前不是独立 Toast 弹窗，面试时应说“通知中心实时刷新”。

## 71. Elasticsearch 教室搜索

### 同步流程

1. 教室创建或修改成功。
2. 删除数据库缓存。
3. 写入 ES 同步事件或加入同步任务。
4. 组装 room、设备、标签、容量和用途字段。
5. 写入 classroom_index。
6. 搜索接口在 ES 中执行关键词和条件过滤。
7. 返回候选教室。
8. 用户预约时重新查询 MySQL 和 Redis。

ES 只负责搜索加速和复杂过滤，不负责最终库存和预约成功判断。

## 72. Caffeine + Redis 两级缓存

### 读流程

1. 生成稳定的缓存 Key。
2. 查询 Caffeine。
3. 命中则直接返回。
4. 未命中则查询 Redis。
5. Redis 命中后回填 Caffeine。
6. Redis 未命中则查询 MySQL。
7. MySQL 结果回填 Redis。
8. 再回填 Caffeine。
9. 返回结果。

### 写流程

1. 修改 MySQL。
2. 修改成功后删除 Redis。
3. 删除当前实例 Caffeine。
4. 通过 TTL、广播消息或下一次回源处理其他实例。

库存不走 Caffeine，因为本地缓存无法保证多个实例之间同步。

## 73. Kafka 统计大屏

### 事件产生

1. 预约、取消、签到、爽约或候补状态发生变化。
2. 在本地事务中写入 event_outbox。
3. Outbox 任务投递 classroom.events。
4. Kafka 保存事件。

### 统计消费

1. statistics-consumer 拉取事件。
2. 根据 eventId 去重。
3. 根据 eventType 分类。
4. 按 room_slot、roomId、日期聚合。
5. 更新 event_statistics 或 Redis。
6. 管理员大屏查询聚合结果。

Kafka 消费延迟只影响大屏，不影响预约事务。

# 第五部分：每个功能如何验证

## 74. 注册和登录验证

### 注册成功

1. 使用合法手机号和密码注册。
2. 查询用户表，确认密码是 BCrypt 密文。
3. 查询 credit_account，确认初始化信用分。
4. 使用相同手机号再次注册，确认返回重复提示。
5. 使用非法手机号注册，确认参数校验失败。

### 登录成功

1. 使用正确账号密码登录。
2. 复制返回 JWT。
3. 调用需要登录的接口并携带 JWT。
4. 不携带 JWT 调用，确认返回 401。
5. 使用学生 Token 调用管理员接口，确认返回 403。
6. 修改 Token 或等待过期，确认无法访问。

## 75. room_slot 管理验证

1. 管理员创建一个未来日期的 room_slot。
2. 查询列表，确认状态、容量和剩余名额正确。
3. 创建完全相同的教室、日期和时间段，确认唯一约束拦截。
4. 将没有预约的 OPEN slot 改为 CLOSED。
5. 再改回 OPEN，确认 Redis stock 重新初始化。
6. 为该 slot 创建一个学生预约。
7. 再尝试关闭或维护，确认后端拒绝并返回已有预约原因。
8. 修改教室为不可用，确认教室记录仍存在，学生搜索中不再返回。

## 76. 预约成功验证

1. 管理员创建容量为 1 的 OPEN slot。
2. 学生获取 Submit Token。
3. 使用 Token 提交预约。
4. 查询 room_slot，确认 available_capacity 减 1。
5. 查询 reservation，确认新增 RESERVED 记录。
6. 查询 Outbox，确认产生预约事件。

8. 查询 notification，确认通知落库。

## 77. 重复提交验证

1. 获取一个 Submit Token。
2. 使用同一个 Token 连续调用两次预约接口。
3. 第一次请求正常处理。
4. 第二次返回令牌无效或已使用。
5. 查询 reservation，确认没有因为两次请求创建两条订单。

之后再生成一个新 Token，验证数据库和 Redis 的重复预约拦截仍然生效。

## 78. 同一用户跨教室冲突验证

1. 创建教室 A 和教室 B。
2. 为两间教室创建相同日期和时间段的 OPEN slot。
3. 学生使用 Token 预约教室 A。
4. 再获取新 Token 预约教室 B。
5. 预期第二次返回同一时间段只能预约一个教室。
6. 查询 reservation，确认只有一条有效预约。
7. 查询 Redis 用户时间 Key，确认只存在一条时间占用标记。

如果先请求的 slot 已经满员，要注意当前代码可能先返回库存不足，再判断其他冲突。测试时应给两个 slot 都保留库存，专门验证跨教室冲突。

## 79. 候补验证

21. 记录 Embedding、Rerank、意图模型和生成模型返回的准确 Token usage，避免用字符数冒充 Token。

12. 查询候补数。
13. 查询重复用户。
14. 对比 room_slot 计数和有效 reservation 数量。

最终判断：

    reserved_count <= total_capacity
    available_capacity = total_capacity - reserved_count
    duplicate_users = 0

不要只看 JMeter 的 HTTP 成功数，必须结合数据库最终结果。

## 87. 一次完整的故障排查顺序

当用户说“预约失败”时，按以下顺序排查：

1. 看 HTTP 状态码。
2. 看响应中的业务 message。
3. 看后端日志中的 userId、roomId、日期和时间段。
4. 查 room_slot 是否存在。
5. 查 room_slot.status 是否为 OPEN。
6. 查 available_capacity。
7. 查 Redis stock。
8. 查 Redis 用户集合和用户时间 Key。
9. 查 Submit Token 是否存在或已被消费。
10. 查用户信用分。
11. 查 MySQL 条件 UPDATE 影响行数。
12. 查 reservation 是否插入。
13. 查数据库唯一键异常。
14. 查 Outbox 是否生成。
15. 查 RabbitMQ 或 Kafka 是否积压。

这样可以判断问题发生在：

    参数校验
    权限
    Submit Token
    Redis
    数据库库存
    唯一约束
    消息投递
    前端展示

而不是看到“预约失败”就直接修改库存代码。

    public LoginResponse login(LoginRequest request) {

                user.getUsername(),

        );

    }

    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain chain) throws IOException, ServletException {

        String token = resolveBearerToken(request);

        if (token != null && jwtTokenService.isValid(token)) {
            // 解析出用户身份，并放入当前请求上下文。
            Authentication authentication =
                    jwtTokenService.toAuthentication(token);
            SecurityContextHolder.getContext()
                    .setAuthentication(authentication);
        }

        // 无论是否有 Token，都要继续过滤器链；
        // 后面的权限配置决定该请求是否必须登录。
        chain.doFilter(request, response);
    }

        if (roomSlotMapper.exists(

                request.getTimeSlot())) {

        }

        slot.setRoomId(request.getRoomId());
        slot.setReserveDate(request.getReserveDate());
        slot.setTimeSlot(request.getTimeSlot());
        slot.setTotalCapacity(request.getCapacity());

        slot.setAvailableCapacity(request.getCapacity());

        roomSlotMapper.insert(slot);

        // 教室或时段变化后删除查询缓存，
        // 下一次读取会回源 MySQL 并重新回填。
        cacheService.evictRoomAndSearch(request.getRoomId());
        return slot;

## 91. Submit Token 带注释示例

    public String createSubmitToken(Long userId) {
        // 使用随机值，避免用户猜测其他 Token。
        String token = UUID.randomUUID()
                .toString()
                .replace("-", "");

        // Token 与用户 ID 绑定，其他用户拿到该值也不能使用。
        String key = "reserve:submit:" + userId + ":" + token;

        // 设置短 TTL，防止未提交 Token 永久留在 Redis。
        redis.opsForValue().set(
                key,
                "1",
                Duration.ofMinutes(5)
        );
        return token;
    }

    private void consumeSubmitToken(Long userId, String token) {
        if (token == null || token.trim().isEmpty()) {
            throw new IllegalArgumentException("缺少预约提交令牌");
        }

        String key = "reserve:submit:" + userId + ":" + token;

        // 删除成功表示 Token 存在并且是第一次使用。
        // 删除失败表示已过期、已使用或不属于该用户。
        Boolean deleted = redis.delete(key);
        if (!Boolean.TRUE.equals(deleted)) {
            throw new IllegalArgumentException("令牌无效或已使用");
        }
    }

## 92. Redis Lua 带注释示例

    -- KEYS[1] 是当前 room_slot 的 Redis 库存
    local stock = tonumber(redis.call('get', KEYS[1]))

    -- 库存 Key 不存在，说明还没有初始化，不能盲目预约
    if stock == nil then
        return 3
    end

    -- 库存为 0 时进入候补或返回名额不足
    if stock <= 0 then
        return 1
    end

    -- KEYS[2] 是当前 room_slot 的用户集合
    -- 防止同一个用户重复预约当前 slot
    if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then
        return 2
    end

    -- KEYS[3] 不包含 roomId，
    -- 所以可以阻止同一用户预约同一时间段的其他教室
    if redis.call('exists', KEYS[3]) == 1 then
        return 4
    end

    -- 以下操作在同一个 Lua 脚本中原子执行，
    -- 不会被另一个 Redis 请求插入到中间
    redis.call('decr', KEYS[1])
    redis.call('sadd', KEYS[2], ARGV[1])

    -- 保存用户时间占用标记，并设置过期时间
    redis.call('set', KEYS[3], ARGV[3], 'EX', ARGV[2])
    return 0

返回码的含义：

    0：预扣成功
    1：库存不足
    2：已经预约当前 slot
    3：库存 Key 不存在
    4：同一用户同一时间段已有其他教室预约

## 93. 预约 Service 带注释示例

    @Transactional
    public ReserveResponse reserve(
            ReserveRequest request,
            String submitToken) {

        // 当前用户必须从登录上下文取得，
        // 不能使用请求体里的 userId。
        User user = UserContext.getRequired();

        // 校验日期、时间段、预约时间范围。
        ReservationTimePolicy.validateReservable(
                request.getReserveDate(),
                request.getTimeSlot()
        );

        // 用户级锁用于串行处理同一个用户的并发预约。
        RLock lock = redissonClient.getLock(
                "lock:reserve:user:" + user.getId()
        );

        try {
            // tryLock 避免请求无限等待。
            if (!lock.tryLock(2, 8, TimeUnit.SECONDS)) {
                throw new IllegalArgumentException("请求处理中");
            }

            // Token 必须在预约主流程中消费，防止重复提交。
            consumeSubmitToken(user.getId(), submitToken);

            // 在扣库存前先判断信用分和预约资格。
            creditService.assertCanReserve(user.getId());

            // 查询数据库确认 slot 存在且为 OPEN，
            // 同时初始化 Redis stock。
            RoomSlot slot = loadOpenSlotAndInitRedisStock(request);

            // Redis Lua 负责高并发预扣和冲突判断。
            Long result = executeReserveScript(request, user.getId());

            if (result == 1) {
                // 满员时是否加入候补由用户选择。
                return request.isJoinWaitlist()
                        ? joinWaitlist(request, user, slot)
                        : ReserveResponse.soldOut();
            }
            if (result == 2) {
                throw new IllegalArgumentException("已经预约当前时段");
            }
            if (result == 4) {
                throw new IllegalArgumentException(
                        "同一时间段只能预约一个教室");
            }
            if (result != 0) {
                throw new IllegalArgumentException("库存初始化失败");
            }

            // 从这里开始，Redis 已经预扣成功，
            // 后续失败必须执行 Redis 补偿。
            try {
                // MySQL 使用条件更新做最终库存确认。
                int updated = roomSlotMapper.decreaseStockById(
                        slot.getId()
                );
                if (updated != 1) {
                    throw new StockChangedException();
                }

                ReservationOrder order = buildOrder(request, user);

                // active_key 由用户、日期和时间段组成，
                // 唯一索引防止并发插入重复有效预约。
                reservationOrderMapper.insert(order);

                // Outbox 和订单在同一个数据库事务内写入。
                // 即使 RabbitMQ 暂时不可用，事件也不会丢失。
                eventOutboxService.saveReservationSuccess(order);

                return ReserveResponse.success(order);
            } catch (RuntimeException ex) {
                // MySQL 或订单插入失败时恢复 Redis 预扣结果。
                rollbackRedisReservation(request, user.getId());
                throw ex;
            }
        } catch (InterruptedException ex) {
            // 恢复线程中断标记，避免吞掉中断信号。
            Thread.currentThread().interrupt();
            throw new IllegalArgumentException("请求被中断");
        } finally {
            // 只释放当前线程持有的锁。
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }

## 94. MySQL 条件扣库存带注释示例

    UPDATE tb_room_slot
    SET available_capacity = available_capacity - 1,
        reserved_count = reserved_count + 1,
        version = version + 1,
        update_time = NOW()
    WHERE id = ?
      AND status = 1
      AND available_capacity > 0;

逐句解释：

- id = ?：只更新目标 room_slot。
- status = 1：只有 OPEN 时段可预约。
- available_capacity > 0：数据库层再次确认库存。
- available_capacity - 1：在数据库内部完成扣减。
- reserved_count + 1：同步维护已预约数量。
- version + 1：为后续乐观锁或变更追踪保留版本。
- 返回 1：扣减成功。
- 返回 0：状态不对、库存不足或记录不存在。

不能改成：

    SELECT available_capacity;
    // Java 判断大于 0
    UPDATE available_capacity = available_capacity - 1;

因为多个请求可能同时读到相同库存，造成超卖。

## 97. 取消和补位带注释示例

    @Transactional
    public void cancel(Long orderId) {
        User current = UserContext.getRequired();
        ReservationOrder order = reservationOrderMapper.findById(orderId);

        // 只有本人或管理员可以取消。
        assertOwnerOrAdmin(current, order);

        // 条件更新保证订单只能从有效状态取消一次。
        int updated = reservationOrderMapper.cancelByUser(
                orderId,
                current.getId()
        );
        if (updated != 1) {
            throw new IllegalArgumentException("订单当前不可取消");
        }

        // 恢复一个数据库名额。
        roomSlotMapper.increaseStock(
                order.getRoomId(),
                order.getReserveDate(),
                order.getTimeSlot()
        );

        // Redis 也要恢复，删除该用户的占用标记。
        rollbackRedisReservation(
                order.getRoomId(),
                order.getReserveDate(),
                order.getTimeSlot(),
                order.getUserId()
        );

        // 取消释放名额后，尝试给第一位候补补位。
        promoteFirstWaiter(order);
    }

    private void promoteFirstWaiter(ReservationOrder order) {
        RLock lock = redissonClient.getLock(
                "lock:room-slot:" + order.getRoomSlotId()
        );
        lock.lock();
        try {
            // 当前项目 FIFO：先按创建时间，再按 ID。
            WaitlistOrder waiter = waitlistMapper.firstWaiting(
                    order.getRoomId(),
                    order.getReserveDate(),
                    order.getTimeSlot()
            );
            if (waiter == null) {
                return;
            }

            // 防止候补用户在等待期间已经预约了同一时间段。
            if (reservationOrderMapper.countActiveByUser(
                    waiter.getUserId(),
                    order.getReserveDate(),
                    order.getTimeSlot()) > 0) {
                waitlistMapper.skip(waiter.getId());
                promoteFirstWaiter(order);
                return;
            }

            // 只有 WAITING 状态才能转为 PROMOTED。
            if (waitlistMapper.promoteIfWaiting(waiter.getId()) != 1) {
                return;
            }

            // 实际项目还要根据确认机制创建资格或预约记录。
            notificationOutboxService.enqueue(
                    waiter.getUserId(),
                    "候补补位成功",
                    "请在规定时间内确认"
            );
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }

## 98. RAG 漏召回如何分层定位

当前项目提供：

```http
GET /agent/evaluations/external-policy/diagnostics?split=DEV
GET /agent/evaluations/external-policy/diagnostics?split=TEST
```

一次请求对每道题只执行一遍完整检索，在同一快照中记录五个有序列表：

1. `lexicalChunkIds`：MySQL 关键词粗召回结果。
2. `vectorChunkIds`：Embedding 查询 Qdrant 的语义召回结果。
3. `rrfChunkIds`：两路结果经过 RRF 融合后的顺序。
4. `rerankCandidateChunkIds`：实际送给 Cross-Encoder 的候选。
5. `finalChunkIds`：融合 RRF 与 Cross-Encoder 分数后的最终结果。

定位顺序如下：

```text
目标证据不存在于切分结果
  -> CHUNK_MISSING：检查 PDF 提取、乱码、空白符和切分边界

关键词与向量都没有召回目标
  -> ROUGH_RECALL_MISS：补充章节上下文、同义词或查询改写

单路命中但 RRF 后消失
  -> FUSION_MISS：检查去重键、RRF 构造及候选数量

RRF 命中但没有送入精排
  -> RRF_CANDIDATE_CUTOFF：在 DEV 上调整精排候选数

RRF Top3 命中但精排后掉出 Top3
  -> RERANK_DEGRADED：检查 hard negative、精排输入和权重

目标进入精排但最终仍在 Top3 外
  -> FINAL_RANK_MISS：改进标题/章节元数据或精排模型
```

## 99. 本次真实问题复盘：漏召回其实发生在评测层

第一次诊断在 45 条 DEV 中发现 P04、P07、P09 三条失败。逐条读取数据库 Chunk 后发现：

- P04 已返回校内申诉委员会、省级教育行政部门等具体申诉渠道，旧标签只认“提出申诉或者依法提起诉讼”。
- P07 已返回北大具体规定中的“课程零分并给予处分”，旧标签只认教育部通用规定中的“成绩无效”。
- P09 已返回北大转院系/转专业的具体条件和流程，旧标签只认“可以申请转专业”。

这说明检索没有漏掉正确答案，问题在于评测采用单一字符串作为唯一相关证据。修复方式不是调高模型分数，而是把评测集升级为 qrels 风格：每题保留一个主参考答案，同时允许多个经过人工核验的等价证据锚点；PDF 文本比较前还会去除提取时插入的空白符。

核心判断逻辑：

```java
// 一个问题可能对应通用规定、学校实施办法等多个同样有效的证据段。
List<String> normalizedAnchors = acceptedAnchors.stream()
        .map(this::normalizeEvidenceText)
        .filter(anchor -> !anchor.isBlank())
        .toList();

// 任意人工确认过的锚点出现在 Chunk 中，就把该 Chunk 视为 relevant。
return chunks.stream()
        .filter(chunk -> {
            String content = normalizeEvidenceText(chunk.getContent());
            return normalizedAnchors.stream().anyMatch(content::contains);
        })
        .map(AgentKnowledgeChunk::getId)
        .distinct()
        .toList();
```

面试时必须主动说明：这次 qrels 修复消除的是评测假阴性，不属于算法提升。真正的算法收益必须看固定集消融。

# 第七部分：DEV 驱动的 RAG 优化、完整复盘与面试追问

## 117. 为什么需要 DEV，而不是发现 Recall 低就直接改代码

RAG 优化不是“看到 Recall 低就换更贵的模型”。一次检索失败可能发生在不同层：

```text
原始 PDF
  -> 文本提取
  -> Chunk 切分
  -> Embedding 与向量入库
  -> 关键词粗召回 / 向量粗召回
  -> RRF 融合
  -> Cross-Encoder 精排
  -> Top K 上下文
  -> LLM 生成
  -> 引用与拒答
```

如果目标条款根本没有进入 Chunk，调 RRF 权重没有意义；如果正确 Chunk 已经排在第一，但评测仍判错，继续调模型会造成过拟合。因此项目把问题集划分为：

| 数据集 | 数量 | 作用 | 是否允许根据结果调参 |
| --- | ---: | --- | --- |
| 项目规则回归集 | 20 | 验证预约、签到、候补等自有规则没有回归 | 可以用于日常回归，但不用于对外泛化结论 |
| DEV | 45 | 定位失败层、修正无效标签、选择候选数和融合权重 | 允许 |
| 历史 TEST | 15 | 参数冻结后的阶段性验证 | 曾被查看和纠错，现在只作为回归集 |
| BLIND_TEST | 20 | 验证 DEV 上的方案能否迁移到未见问题 | 冻结后不允许修改；首次运行后不再是“未见” |
| REFUSAL | 5 | 验证没有依据时是否拒答 | 不应用来提高可回答题 Recall |

它和机器学习训练集的区别是：项目没有训练 Embedding、Rerank 或 LLM 参数。DEV 是检索工程的开发集，用来选择系统参数；BLIND_TEST 是一次性独立测试集。

  -> 查查询改写、章节标题、同义词、向量索引完整性和候选深度

核心不是记住枚举，而是能回答：“我先证明失败在哪一层，再修改对应层，不会用调权重掩盖数据错误。”

### 118.4 第四步：先检查 ground truth，再调算法

当前项目第一次诊断 P04、P07、P09 时，表面看是 DEV 漏召回，实际分别召回了更具体或同样有效的校级条款。旧评测只认一个 `expectedAnchor`，导致正确结果被判错。

修复原则：

1. 保留主参考锚点，便于解释题目最初依据。
2. 增加 `acceptedAnchors`，但每个锚点必须由人工对照 PDF 确认。
3. 任一有效锚点对应的 Chunk 都视为 relevant。
4. 匹配前去掉普通空格、换行、制表符和全角空格。
5. 记录 qrels 版本，标签变更后的指标不能直接和旧版比较。

带注释的简化实现：

```java
private List<Long> resolveTargetChunkIds(EvaluationCase item,
                                         List<AgentKnowledgeChunk> chunks) {
    // 一道题允许有多个经过人工确认的等价证据，而不是只认一个字符串。
    List<String> anchors = item.acceptedAnchors().stream()
            // PDFBox 提取后可能在中文字符之间插入换行或空格，先统一归一化。
            .map(this::normalizeEvidenceText)
            .filter(anchor -> !anchor.isBlank())
            .toList();

    return chunks.stream()
            .filter(chunk -> {
                String content = normalizeEvidenceText(chunk.getContent());
                // 只要 Chunk 包含任一人工认可锚点，就属于相关文档集合。
                return anchors.stream().anyMatch(content::contains);
            })
            .map(AgentKnowledgeChunk::getId)
            // overlap 可能让同一证据出现在相邻 Chunk，ID 需要去重。
            .distinct()
            .toList();
}

private String normalizeEvidenceText(String value) {
    if (value == null) {
        return "";
    }
    // 同时移除 ASCII 空白和中文全角空格，避免 PDF 排版造成假阴性。
    return value.replaceAll("[\\s\\u3000]+", "");
}
```

必须诚实说明：qrels 和空白归一化修复的是评测准确性，不是检索算法能力。只有在相同 qrels 版本下比较不同流水线，才叫算法消融。

## 119. 当前真正提高 Recall 的技术步骤

### 119.1 滑动窗口切分降低边界丢失

当前参数是 650 个 Java 字符、100 个字符 overlap。切分时优先向前寻找换行、中文句号或空格，尽量不从句子中间截断。

```java
private List<String> split(String content) {
    // 统一换行并压缩过多空行，减少纯排版噪声。
    String normalized = content.replace("\r", "")
            .replaceAll("\n{3,}", "\n\n")
            .trim();

    List<String> chunks = new ArrayList<>();
    int start = 0;
    final int size = 650;
    final int overlap = 100;

    while (start < normalized.length()) {
        int end = Math.min(start + size, normalized.length());

        if (end < normalized.length()) {
            // 在最大长度之前寻找自然边界，避免把条款前后句机械拆开。
            int cut = Math.max(
                    normalized.lastIndexOf('\n', end),
                    Math.max(normalized.lastIndexOf('。', end),
                             normalized.lastIndexOf(' ', end))
            );
            // 边界过早会产生很碎的 Chunk，因此只接受后半段的自然边界。
            if (cut > start + size / 2) {
                end = cut + 1;
            }
        }

        String part = normalized.substring(start, end).trim();
        if (!part.isEmpty()) {
            chunks.add(part);
        }

        if (end >= normalized.length()) {
            break;
        }
        // 保留上一块末尾 100 字，降低条款跨边界导致的漏召回。
        start = Math.max(end - overlap, start + 1);
    }
    return chunks.isEmpty() ? List.of(normalized) : chunks;
}
```

为什么不是固定按页切：PDF 页边界是排版边界，不一定是语义边界，一条规定可能跨两页。为什么 overlap 不是越大越好：overlap 越大，重复 Chunk、向量数量、入库费用和检索冗余越高，还会挤占 Top K。

### 119.2 关键词与向量双路召回互补

当前关键词路不是 Elasticsearch BM25，也不是分词器。真实实现是：从 MySQL 最多读取 400 个活动 Chunk，在 Java 内存里生成中文单字和双字词集合，按命中比例排序。

它擅长：条款号、处分名称、固定数字、明确制度术语。

它的局限：

- 每次扫描最多 400 个 Chunk，数据规模增大后可能漏掉后面的 Chunk。
- 没有 IDF、字段权重和专业中文分词。
- 不能把“不能毕业”和“不得授予学位”天然视为同义表达。

向量路把问题调用 `qwen3.7-text-embedding` 得到 1024 维向量，在 Qdrant 中按 cosine 相似度检索，并按知识分类过滤。它擅长口语化改写和同义表达，但对精确数字、相似条款和高频制度词可能排序不稳。

DEV 消融证明二者互补：固定 15 条历史 TEST 上，关键词 Recall@3 为 66.67%，向量为 80.00%。不能由此说向量“全面优于”关键词，因为 20 条盲测中关键词 Recall@3 反而是 100%，向量是 95%。

### 119.3 使用 RRF，而不是直接相加两路原始分数

关键词分数是命中比例，Qdrant 分数是向量相似度，两者不在同一标尺。直接相加会让数值范围较大的一路支配结果。RRF 只使用名次：

```text
RRF(d) = Σ 1 / (k + rank_i(d))
当前 k = 60
```

带注释实现：

```java
private void addRrfScores(Map<Long, Double> fusedScores,
                          List<ScoredChunk> rankedHits) {
    int rank = 1;
    int safeRrfK = Math.max(rrfK, 1);

    for (ScoredChunk hit : rankedHits) {
        // 同一 Chunk 同时被关键词和向量召回时会累加两路名次贡献。
        fusedScores.merge(
                hit.chunk.getId(),
                1D / (safeRrfK + rank),
                Double::sum
        );
        rank++;
    }
}
```

固定历史 TEST 上，RRF 将 Recall@3 从关键词的 66.67% 和向量的 80.00% 提升到 93.33%，说明融合确实补齐了单路遗漏。

### 119.4 Cross-Encoder 只精排候选，不负责全库召回

Cross-Encoder 同时读取 query 和完整 Chunk，能理解二者细粒度关系，准确度通常高于只比较独立向量。但计算量和 Token 消耗更大，所以只处理 RRF Top 30。

DEV 中曾比较过纯 Cross-Encoder 排序。它提高了部分 Top1，却把少量原本在 RRF Top3 的正确证据挤出，因此当前不是完全覆盖 RRF，而是先归一化再加权：

```text
finalScore = 0.35 * crossEncoderScore
           + 0.65 * normalizedRrfScore
```

```java
double maxRrf = candidates.stream()
        .mapToDouble(ScoredChunk::getScore)
        .max().orElse(1D);
double minRrf = candidates.stream()
        .mapToDouble(ScoredChunk::getScore)
        .min().orElse(0D);
double range = Math.max(maxRrf - minRrf, 0.0000001D);

for (int index = 0; index < candidates.size(); index++) {
    ScoredChunk candidate = candidates.get(index);

    // 先把 RRF 分数归一化到近似 0 到 1，才能与精排分数组合。
    double normalizedRrf = (candidate.score - minRrf) / range;
    double crossEncoder = rerankScores.getOrDefault(index, 0D);

    // 0.35 是在 DEV 上确定的折中：保留粗召回稳定性，同时利用语义精排。
    double finalScore = 0.35D * crossEncoder + 0.65D * normalizedRrf;
    rerankedResults.add(new ScoredChunk(candidate.chunk, finalScore));
}
```

固定历史 TEST 上，Cross-Encoder 把 RRF Recall@3 93.33% 提升到 100%，MRR@3 从 67.78% 提升到 78.89%。盲测 B17 中正确证据由向量第 10、RRF 第 5提升到最终第 3，是最直观的个例。

### 119.5 批量 Embedding 降低入库请求数，但不直接提高 Recall

索引 PDF 时，把 Chunk 按最多 20 条一批调用 Embedding API；Qdrant 每 64 个点批量 upsert。它减少网络往返、限流概率和费用统计噪声，但向量内容不变，因此主要优化吞吐和稳定性，不应包装为召回算法提升。

```java
int safeBatchSize = Math.min(Math.max(batchSize, 1), 20);
for (int start = 0; start < inputs.size(); start += safeBatchSize) {
    int end = Math.min(start + safeBatchSize, inputs.size());
    // 一次请求提交一批 Chunk，返回顺序与输入顺序对应。
    List<double[]> batch = invokeCompatibleApi(inputs.subList(start, end));
    for (int index = 0; index < batch.size(); index++) {
        result.set(start + index, batch.get(index));
    }
}
```

正确结论：

1. 向量召回提升 Top3 覆盖，但不保证 Top1 更高。
2. RRF 显著提升 Top3，说明两路候选互补。
3. Cross-Encoder 主要改善最终排序和 MRR，也补回最后一个 Top3 漏例。
4. 最终链路相对关键词基线更慢，平均从约 42ms 增加到约 495ms。
5. DEV 达到 100% 不能当最终结论，因此新增冻结盲测。

错误结论：

- “Cross-Encoder 让准确率从 66.67% 提升到 100%。”这里混合了关键词、向量、RRF 和精排多个变量。
- “修复 qrels 后算法提升了 20%。”标签变化不是算法变化。
- “Recall@3 100%，所以回答准确率 100%。”检索和生成是两个阶段。
- “向量检索一定比关键词好。”盲测结果已经给出反例。

## 121. 为什么新增冻结 BLIND_TEST

当 15 条 TEST 已经被查看、逐题分析并修正 qrels 后，它就受到人工信息泄漏影响。即使没有故意对它调参，也不能继续把它称为完全未见测试。因此新增 20 条问题并执行以下约束：

1. 从同一 PDF 中选择原 60 条没有覆盖的条款。
2. 先写问题和 accepted anchors，再运行检索。
3. 以 SHA-256 固化数据内容，防止看到结果后静默改题。
4. 冻结模型、Collection、650/100 切分、RRF k=60、Top30 和 0.35 权重。
5. 首次真实运行后保存完整 JSON，不删除失败题。

首次正式结果：

| 流水线 | Recall@1 | Recall@3 | MRR@3 | Avg | P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 关键词 | 90% | 100% | 95% | 41ms | 47ms |
| 向量 | 80% | 95% | 86.67% | 164ms | 260ms |
| RRF | 95% | 95% | 95% | 205ms | 300ms |
| 最终加权精排 | 95% | 100% | 96.67% | 485ms | 571ms |

候选召回率四路均为 100%。B17 是唯一明显困难样本，最终靠精排进入 Top3。运行后的 BLIND_TEST 以后只能作为固定回归集；若继续进行新一轮算法调优，需要再建立新的未见测试集。

## 122. Recall 之外必须评估什么

### 122.1 检索指标

```text
Recall@1 = Top1 命中的问题数 / 问题总数
Recall@3 = Top3 中至少一个 relevant Chunk 的问题数 / 问题总数
MRR@3    = Σ(1 / 首个 relevant Chunk 的名次) / 问题总数
```

当前 expected target 是 Chunk 集合，不是 Document。因为只有一份 189 页 PDF，如果“返回同一文档”就算命中，几乎所有查询都会成功，指标失去意义。

Candidate Recall 用来判断正确证据是否曾进入较深候选集。Candidate Recall 高但 Recall@3 低，说明主要是排序问题；Candidate Recall 低，说明必须先处理切分或粗召回。

### 122.2 引用正确率

回答出现 `[S1]` 不代表引用正确。需要检查 `[S1]` 指向的 Chunk 是否真的支持它旁边的结论。单条答案有多个事实时，理想做法是按 claim 粒度标注，而不是整段只给一个真假值。

当前自动代理要求引用来源包含目标 anchor，并检查关键事实；它适合持续回归，但不能替代人工审核。

### 122.3 忠实度

忠实度回答的是：“答案里的陈述能否从检索证据推出？”即使答案碰巧符合常识，只要证据没有支持，也不能判为忠实。

项目当前用双字词覆盖率和关键事实匹配作为启发式代理，阈值 50%。这个规则会有：

- 假阴性：同义改写正确，但字面重合不足。
- 假阳性：复制了大量证据词，却答错核心关系。

因此面试时要说“自动忠实度代理”，不能简称“忠实度 80%”或“答案准确率 80%”。

### 122.4 人工正确率

人工审核至少应填写：

```text
答案是否正确
答案是否完整
是否忠实于来源
引用是否支持对应结论
拒答是否合理
错误类型与备注
```

当前已经生成审核 CSV，但没有完成 65 条人工标注，所以人工正确率仍是 N/A。简历不能虚构该数字。

### 122.5 拒答准确率和无依据回答比例

REFUSAL 集包含知识库不存在答案的问题。正确行为是明确说明资料中没有依据，并避免凭模型常识补答案。当前 5 条拒答回归准确率为 100%，但样本很少，只能说明安全分支通过。

```text
Refusal Accuracy = 正确拒答数 / 应拒答问题数
Ungrounded Rate  = 无可靠依据仍给出确定答案的问题数 / 总问题数
```

### 122.6 延迟、Token 与费用

分阶段记录：

| 阶段 | 记录内容 |
| --- | --- |
| Embedding | 模型、输入 Token、耗时、成功/失败 |
| Qdrant | 检索耗时、候选数 |
| RRF | 融合耗时、候选数 |
| Rerank | 模型、候选数、输入 Token、耗时 |
| LLM | 模型、输入/输出 Token、生成耗时 |
| End-to-end | 完整耗时、降级状态、最终工具和来源 |

65 条较早端到端评测的记录为：端到端 Avg 3651ms、P50 3230ms、P95 4970ms；检索 Avg 788ms；Rerank Avg 296ms；生成 Avg 2504ms。P99 被一次约 19.37 秒的 Embedding 超时拉高。当前同步非流式模型不能测真实首 Token 时间，因此 TTFT 必须写 N/A。

Token 统计显示 Rerank 输入约占总 Token 的 88.6%，原因是每题最多把 30 个长 Chunk 送入精排。这给出清晰优化方向：先在 DEV 比较候选 30/20/15 的 Recall@3、MRR、P95 和费用，再决定是否减少候选，不能只为了省钱直接改生产参数。

## 123. 避免重复检索和重复外部 API 调用

早期流程可能先由业务代码检索规则，随后 LangChain4j Tool Calling 又调用一次规则检索，造成：

```text
同一问题重复 Embedding
重复 Qdrant 查询
重复 Cross-Encoder 精排
延迟增加
Token 和费用增加
两次排序结果可能因外部服务抖动而不同
```

当前处理方式是一次完整检索生成 `AgentRetrievalResult`，其中同时携带：

- 最终 `sources`，供前端显示引用。
- 完整 `evidenceTexts`，供 LLM 生成答案。
- `metrics`，供调用链和评测记录。
- 诊断模式下的各阶段 Chunk ID 快照。

后续阶段传递这个结果对象，不再围绕同一问题重新调用检索。消融也基于一次流水线快照计算，而不是分别运行四遍线上 API。

面试回答：

> 我把检索结果作为请求级中间状态向后传递，答案生成、来源展示和评测共享同一份快照。这样既控制调用成本，也保证指标是在同一批候选上比较。当前不是 LangGraph StateGraph，而是 Java 服务对象显式传递状态；项目使用 LangChain4j `@Tool` 做工具调用。

## 124. API Key、外部模型和费用的真实实现

### 124.1 API Key 如何进入项目

Key 没有写入 Java、YAML 默认值或文档。IDEA Run Configuration 中配置的环境变量由 Spring Boot 启动进程读取，再通过 `${ENV_NAME:default}` 注入配置：

```yaml
reservation:
  agent:
    embedding:
      enabled: ${CLASSROOM_AGENT_EMBEDDING_ENABLED:false}
      api-key: ${CLASSROOM_AGENT_EMBEDDING_API_KEY:}
      model: ${CLASSROOM_AGENT_EMBEDDING_MODEL:qwen3.7-text-embedding}
    rerank:
      enabled: ${CLASSROOM_AGENT_RERANK_ENABLED:false}
      api-key: ${CLASSROOM_AGENT_RERANK_API_KEY:${CLASSROOM_AGENT_EMBEDDING_API_KEY:}}
      model: ${CLASSROOM_AGENT_RERANK_MODEL:qwen3-rerank}
```

Spring `@Value` 再把配置注入服务。只有 IDEA 启动的那个 Java 进程能看到 IDEA 环境变量；在另一个 PowerShell 启动应用，不会自动继承 IDEA 配置。

### 124.2 为什么不能提交 Key

- Git 历史很难彻底删除。
- 即使仓库不公开，截图、日志、备份和协作工具也可能泄漏。
- 泄漏后可能被他人消费额度或访问数据。
- 正确做法是环境变量、Secret Manager 或部署平台 Secret。

用户曾在对话中粘贴过真实 Key。面试和正式部署都应视为已经暴露并轮换，文档中绝不能保留原值。

### 124.3 为什么“有免费额度”仍可能欠费

免费额度通常受模型、地域、账号、活动期限、并发方式和计费周期限制。项目一次 65 条评测不只是 65 次调用，还包含 Embedding、Rerank、意图分类和生成；Rerank Top30 会读取大量 Chunk Token。免费额度用尽、模型不在活动范围或地域不匹配时，供应商仍可能计费。

工程上应做：

1. 在供应商控制台确认模型、地域和剩余额度。
2. 配置预算告警和每日限额。
3. 评测接口仅管理员可调用，并增加二次确认。
4. 先跑 1 到 3 条 smoke test，再跑 DEV，最后才跑昂贵答案评测。
5. 每次调用记录 usage 和估算费用。
6. Embedding 入库使用批量请求，避免逐 Chunk 请求。

## 125. 外部依赖的降级矩阵

| 故障 | 当前/建议行为 | 核心预约是否受影响 |
| --- | --- | --- |
| Embedding API 失败 | 记录警告，向量路关闭，本次退回关键词召回 | 不受影响 |
| Qdrant 不可用 | 退回 MySQL 关键词检索 | 不受影响 |
| Rerank API 失败 | 保留 RRF 原排序 | 不受影响 |
| LLM API 失败 | 返回结构化本地检索结果或明确失败，不伪造答案 | 不受影响 |
| PDF 为扫描件 | 拒绝入库并提示先 OCR | 不受影响 |
| PDF 加密 | 拒绝上传 | 不受影响 |
| 部分 Chunk Embedding 失败 | 文档标为 `PARTIAL`，保留 MySQL Chunk，后续重建索引 | 不受影响 |
| Qdrant 与 MySQL Chunk 不一致 | 通过文档重建删除旧点并重新 upsert | 不受影响 |
| 供应商限流/超时 | 有界超时、记录模型调用指标并走上述降级 | 不受影响 |

“不影响核心预约”成立的原因是 Agent/RAG 是旁路能力，预约成功仍由 Redis Lua 和 MySQL 事务决定，模型、Qdrant 和 Kafka 都不在预约正确性链路中。

## 126. 已踩过的 RAG 和 Agent 坑

### 坑 1：自然语言日期正确解析，但数据库没有对应开放时段

用户输入“后天早上 8 点到 10 点”，Agent 正确解析出日期和 `08:00-10:00`，工具返回 0 条。问题不是 Agent 不会理解，而是管理员没有创建该日期的 OPEN `room_slot`。排查时要先看工具 trace 中的参数，再查业务数据。

### 坑 2：把没有命中误认为日期应该精确到秒

本项目资源粒度是管理员开放的固定时段，不是秒级会议系统。查询应把自然语言映射到某天和一个时段；当天预约还要检查开始时间是否已过去。提高时间精度不能创造不存在的 room_slot。

### 坑 3：PDF 空白符让正确证据被判为错误

PDFBox 可能把换行、缩进和全角空格插入锚点。直接 `content.contains(expectedAnchor)` 会产生假阴性。修复是匹配前统一空白，而不是盲目提高向量 Top K。

### 坑 4：单一 anchor 不能覆盖多份等价制度条款

通用学生管理规定和学校实施办法可能都能正确回答同一问题。旧标签只认其中一段，会把更具体的结果判错。修复是人工 qrels，而不是让答案包含指定字符串。

### 坑 5：看过 TEST 后继续称它为盲测

历史 TEST 经过逐题诊断和标签修正后已经泄漏。项目没有掩盖这一点，而是将它降级为回归集，重新冻结 20 条 BLIND_TEST 并记录哈希。

### 坑 6：只看最终 Recall，不知道是哪一层出错

只返回 Top3 无法判断目标曾否进入关键词、向量、RRF 或精排候选。新增诊断快照后，可以给每题标注 `primaryCause`。

### 坑 7：重复执行检索导致费用和延迟翻倍

业务预检索与 `@Tool` 二次检索曾可能叠加。当前通过请求级 `AgentRetrievalResult` 复用证据和指标，并让消融共享单次流水线。

### 坑 8：批量 SQL 或批量 API 的边界不符合供应商限制

Embedding 服务同步接口每批最多 20 条，因此代码把配置值钳制在 1 到 20；Qdrant upsert 再按 64 条分批。批量不是越大越好，超出限制会整批失败。

### 坑 9：外部 API 超时拉高 P99

一次 Embedding 等待约 19.37 秒，虽然最终降级成功，但把 65 条评测的 P99 拉到约 23.5 秒。只报平均值会掩盖问题，因此必须报告 P50/P95/P99，并区分正常样本和异常降级样本。

### 坑 10：把自动代理指标说成人工准确率

自动忠实度依赖字符串和双字词规则，会误判同义表达，也会放过表面词重合但核心答案错误的情况。当前人工审核为 0/65，因此明确标记 N/A。

### 坑 11：模型请求成功，但评测最终因数据库表缺失失败

升级 Spring Boot 后 Flyway 没有自动执行 V7，导致 `tb_agent_answer_evaluation` 不存在。修复为显式 Flyway Migration Bean，并在启动日志验证版本。AI 应用排障不能只盯模型响应，还要查持久化和汇总链路。

### 坑 12：启动时可选中间件连接失败产生大量错误日志

RabbitMQ、Kafka、ES、Qdrant 都应有启用开关。未启用的可选能力不应阻止应用登录和核心预约；启用后则应通过健康检查明确暴露状态，而不是在后台无限重连却让前端以为可用。

### 坑 13：把本地关键词检索说成 BM25 或 Elasticsearch

当前规则 RAG 的 lexical 路是真实的 Java 单字/双字命中比例，并扫描 MySQL 最多 400 个 Chunk。教室搜索用了 Elasticsearch，但规则知识检索没有用 ES。面试时必须按代码说，未来可迁移到 ES BM25，但不能说已经完成。

### 坑 14：把 LangChain4j 说成 LangGraph

当前是 Spring Boot Java 项目，使用 LangChain4j `@Tool` 工具调用和显式 Java 服务编排；没有 LangGraph，也没有 Functional API 或 StateGraph。请求级中间状态由 DTO 和 Service 传递。

### 坑 15：把会话称为长期记忆

当前会话主要用于短期上下文和 30 分钟 TTL。没有完整的用户偏好抽取、长期存储、召回、编辑和删除闭环，因此不能声称实现长期记忆。

## 127. 面试官围绕 DEV 和 Recall 的递进追问

### 问 1：你是怎么发现 Recall 失败原因的？

答：我没有只看最终 Top3，而是为每道 DEV 问题保存目标 Chunk、关键词候选、向量候选、RRF 候选、精排候选和最终顺序。根据目标首次消失的位置，把失败归类到切分、粗召回、融合截断或精排。实际第一次发现的三条失败不是检索失败，而是单锚点评测产生的假阴性。

### 问 2：为什么先检查标签，不先调模型？

答：指标等于“系统输出与 ground truth 的比较”。ground truth 本身错了，优化指标会把系统推向错误目标。先人工核验 qrels 是信息检索评测的前提，标签修复和算法提升必须分开报告。

### 问 3：你如何避免为了 DEV 过拟合？

答：DEV 只用于定位和选参数。参数确定后冻结 PDF 哈希、切分、模型、RRF、Top N、权重和 qrels；历史 TEST 因已查看降为回归集，另建 20 条 BLIND_TEST，先冻结并生成 SHA-256，再首次执行。盲测运行后也不再用于下一轮调参。

### 问 4：为什么 DEV 是 45 条，TEST 是 15 条？

答：60 条数据规模有限，45 条 DEV 能覆盖更多错误类型，15 条用于阶段性验证。但 15 条置信区间很宽，一个样本就影响 6.67 个百分点，所以我没有把它包装成生产 Benchmark，并补了 20 条盲测。更严谨的下一步是扩大到多文档、多类别并持续新增未见题。

### 问 5：Recall@3 的 expected target 是什么？

答：是一个或多个 relevant Chunk ID。这些 ID 由人工标注的 accepted anchors 在归一化 Chunk 正文中解析得到。不是 document ID，因为评测语料主要是一份长 PDF，文档级命中没有区分度。

### 问 6：一个问题为什么可以有多个 target Chunk？

答：滑动窗口会让同一条款出现在相邻 Chunk；此外通用规定和学校具体实施办法可能都是有效证据。qrels 的本质就是允许一个 query 对应多个 relevant documents/chunks。

### 问 7：为什么选择 Recall@3，不只看 Recall@1？

答：RAG 会向 LLM 提供多个证据片段，正确证据进入上下文比一定排第一更重要，所以 Recall@3 衡量可用证据覆盖。Recall@1 和 MRR 同时反映排序质量，防止用很大的 K 虚高召回。

### 问 8：Recall@3 100% 为什么答案质量仍可能只有 80%？

答：正确 Chunk 进入 Top3 只是检索成功。LLM 仍可能忽略证据、错误归纳、混合冲突条款或引用错位置。并且 100% 是修正 qrels 后的后续检索评测，80% 来自较早一轮端到端自动忠实度代理，两者时间和指标含义都不同，不能直接当作同一流水线的差值。

### 问 9：为什么不用 Accuracy？

答：检索返回的是排序列表，一道题可能有多个相关 Chunk。Recall@K 和 MRR 更符合排序检索；最终自然语言答案再用人工正确率、忠实度和引用正确率。

### 问 10：为什么 lexical Recall@1 比 vector 高？

答：这批规章题有明确处分名、数字和制度术语，字符级词面匹配很强；向量会把语义相近的多个条款排在一起，Top1 可能被近似条款占据。向量的价值主要是补口语改写，而不是所有数据上都优于关键词。

### 问 11：RRF 为什么会让某道题从向量第 10变成融合第 5，甚至掉出 Top3？

答：RRF 同时考虑两路排名。若一个干扰 Chunk 在两路都排名较高，它的累计分数会超过只在一路命中的目标。融合提高总体指标，不保证每个 query 单调提升，所以还要看逐题诊断和精排。

### 问 12：为什么 RRF 的 k 取 60？

答：60 是常见稳定起点，能减弱榜首名次差异，鼓励两路共同命中的候选。当前项目固定为 60，并没有宣称这是理论最优；若优化，应在 DEV 上比较多个 k，同时看 BLIND_TEST 泛化，不能在 TEST 上选 k。

### 问 13：为什么精排候选取 30？

答：候选过少会在精排前截掉正确证据，候选过多会线性增加 Cross-Encoder Token、延迟和费用。当前 30 保证 DEV candidate recall，同时成本记录显示它也是主要费用来源。下一步会在 DEV 做 30/20/15 消融，再冻结后验证新盲测。

### 问 14：0.35 的精排权重怎么来的？

答：在 DEV 上比较纯 RRF、纯 Cross-Encoder 和多组加权。纯精排提升部分 Top1，但会让原本稳定的正确 Top3 下降，因此保留 65% 归一化 RRF，使用 35% Cross-Encoder 做语义校正。回答时应强调这是项目数据上的经验参数，不是通用最优值。

### 问 15：为什么要归一化 RRF 分数？

答：RRF 分值通常很小，Cross-Encoder 分值范围由供应商定义。直接加权原始值没有可解释性，会导致某一路天然占优。项目对候选内 RRF 做 min-max，再与 Cross-Encoder 分数组合。

### 问 16：Cross-Encoder 和 Embedding 双塔有什么区别？

答：Embedding 分别编码 query 和 Chunk，可预计算文档向量并快速 ANN 全库召回；Cross-Encoder 将 query 与每个 Chunk 联合输入，能建模 token 级交互但不能低成本扫描全库。因此前者做粗召回，后者只排 Top30。

### 问 17：Qdrant 用来存什么？MySQL 又存什么？

答：MySQL 保存文档、Chunk 正文、索引状态和审计字段，是管理事实源；Qdrant 保存 Chunk 向量和检索 payload，负责 ANN 语义检索。Qdrant 返回候选后，最终来源仍带 MySQL 文档/Chunk 标识。向量库失败时 MySQL 文本仍可做 lexical fallback。

### 问 18：为什么选择 Qdrant，不直接用 Elasticsearch dense_vector？

答：Qdrant 专注向量检索，Collection、payload filter 和 cosine 配置直观，适合展示独立向量库能力；项目已有 ES 用于教室结构化搜索，职责分离更清晰。缺点是多一个组件和同步成本。小项目完全可以只用 ES 混合检索，当前选择不是唯一答案。

### 问 19：为什么当前关键词路不直接用 Elasticsearch BM25？

答：第一版为了让 RAG 模块与教室 ES 索引解耦，采用 MySQL Chunk + Java 字符 unigram/bigram，数据量小时容易实现和降级。但扫描上限 400、没有 IDF 是明确瓶颈。若知识库扩大，应建立独立 policy chunk 索引，用 BM25、字段权重和中文分析器替代内存扫描。

### 问 20：650/100 是怎么选的？

答：这是适配中文制度条款的工程起点。650 字能容纳一段条款及必要上下文，100 字 overlap 防止跨边界；切分还优先自然句界。更严谨做法是在 DEV 上比较 400/80、650/100、900/150，控制其他变量，联合观察 Recall、重复率、向量数量、精排 Token 和延迟。

### 问 21：为什么不按 Token 切分？

答：当前实现按 Java 字符，简单且中文字符密度相对稳定，但不同模型 tokenizer 下并不等价于 Token。生产化应使用目标 Embedding/LLM 的 tokenizer 控制上限，并优先按标题、条款和段落做结构化切分，再对超长段落滑窗。

### 问 22：扫描版 PDF 怎么办？

答：PDFBox 对纯图片无法提取文本，项目检测有效文本过短后拒绝，并提示先 OCR。当前没有集成 OCR，不能说支持所有 PDF。扩展可增加异步 OCR、页码保留、版面分析和低置信度人工复核。

### 问 23：如何保证向量入库完整？

答：文档记录 `chunkCount`、`vectorCount` 和 `indexStatus`。Embedding 分批返回，Qdrant 批量 upsert；如果向量数量少于 Chunk 数，标记 `PARTIAL`，保留错误并支持重建。还应增加按 documentId 的 MySQL/Qdrant 数量对账。

### 问 24：Embedding 请求失败一个批次怎么办？

答：当前该批向量置空并记录警告，其余批次继续；文档最终可能是 `PARTIAL`。文本 Chunk 仍保存在 MySQL，可走关键词检索。生产化可给失败批次建立重试任务和死信记录，避免依赖人工整库重建。

### 问 25：如何防止外部 PDF 污染系统规则？

答：知识有 category，外部规章标记为 `EXTERNAL_REFERENCE` 或评测专用类别；回答展示来源并明确外部资料不代表本系统规则。工具和正式预约仍由系统业务规则校验，RAG 文本不能改变权限、库存或数据库状态。

### 问 26：Agent 为什么只开放只读 Tool？

答：模型输出不确定，写工具容易被提示注入或参数误解触发真实状态变化。当前模型只搜索开放时段、查询本人预约和检索规则，生成待确认草稿；真正预约由用户确认后走 Submit Token、Redis Lua 和 MySQL 事务链路。

### 问 27：LangChain4j 在这里具体做什么？

答：它负责把 Java 方法通过 `@Tool` 暴露给 ChatModel，让模型按意图选择受控工具并填参数；Spring Bean 负责依赖注入和权限上下文。RAG 检索、评测、Qdrant 和精排主要是项目自己的 Java 服务编排，不应全部归功于 LangChain4j。

### 问 28：项目用了 Spring AI 吗？和 LangChain4j 是否重复？

答：项目主 Agent 编排使用 LangChain4j；Spring AI 作为可选的 Embedding 适配路径。两个框架并存增加认知和依赖成本，面试应讲清边界，不能笼统说“同时使用两个框架增强 Agent”。长期可统一供应商适配层。

### 问 29：有没有 LangGraph？

答：没有。当前没有 Functional API 或 StateGraph；工作流是 Spring Service + DTO 的显式编排。若未来存在长流程、暂停恢复、人工审批和复杂分支，再考虑图状态机。不能为了新技术标签把简单流程硬迁移。

### 问 30：有没有长短期记忆？

答：有请求/会话级短期上下文和 TTL；没有完整长期记忆。长期记忆至少要包括用户偏好抽取、持久化、按需召回、冲突更新、用户可见与可删除，以及敏感信息治理。

### 问 31：怎么防提示注入？

答：不信任 PDF 和用户输入中的“指令”；系统提示优先，Tool 白名单和后端 RBAC 是硬边界，写操作不向模型开放；检索内容只作为证据，不作为系统指令执行。即使模型被诱导，后端权限和业务校验仍必须拒绝越权。

### 问 32：模型服务挂了，Agent 还能做什么？

答：Embedding 挂了可做关键词检索，Rerank 挂了保留 RRF，LLM 挂了可以展示结构化候选和来源；普通页面查询、预约、取消、签到完全不依赖模型。降级状态要返回前端和监控，不能静默伪装成完整链路。

### 问 33：为什么不缓存问题 Embedding？

答：当前尚未实现，需要按真实流量判断。可用“模型名 + 归一化 query 的 SHA-256”作为 Key，并设置容量和 TTL；模型或预处理版本变化时必须换命名空间。对评测固定问题和高频规则问题收益较高，但要防缓存把旧知识版本长期保留。

### 问 34：下一步如何继续提高 Recall？

答：先对新的 DEV 失败按层统计。若 `CHUNK_MISSING` 多，做结构化条款切分和标题继承；若 lexical/vector 都漏，做 query rewrite 或扩展向量候选；若 candidate recall 高但 Top3 低，优化 hard negative 精排；知识量增大时把 lexical 路迁移到 ES BM25。每次只改一个变量，跑同版 DEV 消融，冻结后再建新盲测。

### 问 35：当前结果最有价值的地方是什么？

答：不是“20 条达到 100%”这个数字，而是建立了可重复的评测闭环：qrels、多阶段诊断、同快照消融、DEV 调参、数据冻结、盲测、延迟和成本记录、答案质量与检索指标分离，以及失败降级。

## 128. 一套可复现的本地验证流程

### 128.1 启动前检查

1. 启动 MySQL、Redis、Qdrant；需要测试消息时再启用 RabbitMQ、Kafka。
2. IDEA Run Configuration 配置 Embedding、Rerank、LLM 环境变量。
3. 重启应用，因为修改 IDEA 环境变量不会注入已经运行的 JVM。
4. 登录管理员账号，获取 JWT。
5. 调用状态接口确认没有静默降级。

```http
GET /agent/knowledge/status
X-Token: <管理员 JWT>
```

应核对：

```text
embeddingEnabled = true
vectorDatabase = Qdrant
rerankerEnabled = true
retrievalPipeline = lexical + vector + RRF + weighted Cross-Encoder
```

### 128.2 PDF 入库验证

1. 管理员上传 PDF。
2. 确认 MySQL 文档状态从 `PENDING` 变成 `INDEXED` 或 `PARTIAL`。
3. 核对 `chunkCount` 和 `vectorCount`。
4. 查询 Qdrant Collection 点数。
5. 随机抽查开头、中间和结尾 Chunk，防止 189 页 PDF 只有前 400 块能参与 lexical。
6. 对同一文档重建索引，确认先删除旧向量，不产生重复点。

### 128.3 DEV 诊断与消融

```http
GET /agent/evaluations/external-policy/diagnostics?split=DEV
X-Token: <管理员 JWT>
```

保存完整 JSON，并记录：

```text
数据集版本
配置快照
每层 Recall@1 / Recall@3 / MRR@3
每层 Avg / P50 / P95 / P99
失败问题 ID
primaryCause 分布
stageWarnings
模型名与 Token
```

不能只抄总数，至少人工查看所有 miss 和若干 hit，确认标签与证据。

### 128.4 历史 TEST 回归

```http
GET /agent/evaluations/external-policy/diagnostics?split=TEST
X-Token: <管理员 JWT>
```

它现在用于防止修改后回归，不再宣称完全未见。预期当前 qrels 版本最终 Recall@3 为 100%、MRR@3 为 78.89%。若下降，先检查外部服务是否降级、Collection 是否重建、qrels 版本是否相同。

### 128.5 新盲测原则

已有 BLIND_TEST 已经正式运行过，下一轮优化不能继续拿它选参数。应先新增另一批问题，冻结文件和 SHA-256，再运行一次。失败题必须保留在结果中，不能运行后改写问题让指标变好。

### 128.6 答案质量评测

昂贵的答案评测放在检索稳定之后：

1. 先用 1 到 3 条 smoke test 验证 LLM Key 和模型。
2. 运行可回答题与 REFUSAL。
3. 记录来源、回答、模型、检索/精排/生成耗时、Token 和估算费用。
4. 导出人工审核 CSV。
5. 至少人工复核 TEST/BLIND_TEST 和 REFUSAL；有条件时双人标注并计算一致性。
6. 自动忠实度与人工正确率分栏报告。

### 128.7 面试演示建议

演示顺序控制在五分钟：

1. 上传或展示已索引 PDF，说明 650/100 和批量 Embedding。
2. 输入一个口语化制度问题，展示答案与 `[S1]` 来源。
3. 展示诊断接口中 lexical/vector/RRF/final 的 rank 变化。
4. 输入知识库外问题，展示正确拒答。
5. 关闭 Rerank 或模拟失败，展示 RRF 降级。
6. 最后展示固定盲测表格，不现场重新烧完整付费评测。

## 129. 面试时可直接使用的完整复盘回答

> 我最初用 45 条 DEV 和 15 条保留题评估一份约 189 页的校园规章 PDF。第一版只看最终 Top3，无法判断漏召回在哪，所以我给每个问题增加了多阶段诊断快照，记录关键词、Qdrant 向量、RRF、精排候选和最终排名。逐题分析 DEV 后发现三条所谓漏召回其实已经返回了正确的校级具体规定，只是单一字符串标签只认另一段通用规定；我因此把标签升级为人工 qrels，并统一 PDF 空白符。这个修复只消除了评测假阴性，我没有把它算成算法提升。
>
> 在同一 qrels 版本下做消融，固定 15 条历史 TEST 的关键词 Recall@3 是 66.67%，向量是 80%，RRF 是 93.33%。之后只对 RRF Top30 使用 qwen3-rerank，并根据 DEV 采用 35% Cross-Encoder 与 65% 归一化 RRF 的加权，最终 Recall@3 是 100%，MRR@3 从 67.78% 提升到 78.89%，平均检索耗时由约 185ms 增至约 495ms。因为这 15 条已经被查看，我把它降为回归集，另冻结了 20 条未参与调参的问题并记录 SHA-256。首次盲测最终 Recall@1 95%、Recall@3 100%、MRR@3 96.67%、P95 571ms。
>
> 我不会把 Recall@3 解释成答案正确率。较早的 65 条端到端评测还分别记录了引用正确率、自动忠实度代理、拒答、无依据回答、检索与生成耗时、Token 和估算费用；人工正确率在没有完成审核前保持 N/A。系统对 Embedding、Qdrant、Rerank 和 LLM 分层降级，任何 Agent 故障都不影响 Redis Lua 与 MySQL 事务负责的核心预约链路。

## 130. 当前不足和下一轮最有价值的改进

按优先级排列：

1. 完成至少 15 条历史 TEST、20 条盲测和 5 条拒答的人工审核，报告人工正确率、忠实度和引用正确率。
2. 新建第二份不同学校或不同主题的长文档，构建跨文档 DEV 和全新 BLIND_TEST，验证不是只适配一份 PDF。
3. 将规则 lexical 检索从 MySQL 最多 400 Chunk 的内存扫描迁移到独立 Elasticsearch BM25 索引。
4. 做结构化 Chunk：继承文档名、章、节、条款号和页码；先按条款切分，超长条款再滑窗。
5. 在 DEV 比较 Rerank Top30/20/15，降低当前占比最高的 Rerank Token。
6. 增加 query rewrite，但必须限制改写次数并保留原查询，避免延迟和语义漂移。
7. 增加请求级 Embedding 缓存、超时和熔断指标。
8. 对 MySQL Chunk 数与 Qdrant point 数做定时对账和失败批次重试。
9. 使用流式模型后再真实测量 TTFT，当前同步模型不能虚构首 Token 指标。
10. 增加提示注入、恶意 PDF、越权 Tool、敏感信息泄露和超长输入的安全评测。

改进时仍遵守同一原则：先用新 DEV 定位失败层，只修改一个变量，做同版本消融；参数冻结后使用新的未见测试集验证，不能反复查看同一个 BLIND_TEST 来调参。
