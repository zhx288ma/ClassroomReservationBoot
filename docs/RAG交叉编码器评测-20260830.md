# RAG Cross-Encoder 精排改造与 60 条评测报告

## 1. 改造目标

原检索链路是 MySQL 关键词召回、Qdrant 向量召回和 RRF 融合。它适合快速扩大候选集，但 RRF 只看排名，不能判断候选片段是否直接回答问题。本次加入 `qwen3-rerank` Cross-Encoder，对粗召回候选做第二阶段精排；同时把知识库 Embedding 和 Qdrant 写入改成批量请求。

## 2. 最终检索链路

```text
用户问题
  -> MySQL 关键词召回
  -> qwen3.7-text-embedding 生成问题向量
  -> Qdrant 向量召回
  -> RRF 合并并取 Top 30
  -> qwen3-rerank 对 30 个 query-chunk 对联合打分
  -> 0.35 * Cross-Encoder + 0.65 * normalized RRF
  -> 返回 Top 3 证据
```

降级顺序：Cross-Encoder 失败时保留 RRF 顺序；Qdrant 或 Embedding 失败时退回关键词召回；这些故障不会进入预约写事务。

## 3. 批量索引

- PDF 仍使用约 650 字符窗口和 100 字符重叠切块。
- `AgentEmbeddingService.embedBatch` 每批最多发送 20 个 chunk，响应按 `index` 恢复输入顺序。
- `AgentVectorStoreService.upsertBatch` 每批最多写入 64 个 Qdrant point。
- 258 个 chunk 的长 PDF，Embedding 约 13 次请求，Qdrant 约 5 次写入。
- 本次重建 25 份活动文档耗时 13.91 秒，外部规章文档状态为 `INDEXED`，chunk/vector 为 258/258。

## 4. 评测集与判定

- 数据集：`pku-student-policy-golden-v1`。
- 总计 60 条人工问题和证据锚点。
- DEV 45 条，用于分析失败和选择融合策略。
- TEST 15 条，用于固定回归验证。
- expected target 是 chunk 内的锚点文本；Top K 中任一 chunk 含锚点即命中。
- 指标为 Recall@1、Recall@3、MRR@3 和检索耗时。

接口 `GET /agent/evaluations/external-policy/retrieval` 会对同一问题先运行无精排 RRF 基线，再运行精排链路，返回 `baselineRrf`、`crossEncoderReranked` 和逐题 `rankChange`。

## 5. 最终结果

| Split | Mode | Recall@1 | Recall@3 | MRR@3 | Avg | P95 | P99 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| DEV 45 | RRF | 51.11% | 84.44% | 65.56% | 203 ms | 322 ms | 436 ms |
| DEV 45 | weighted rerank | 53.33% | 86.67% | 68.52% | 488 ms | 649 ms | 685 ms |
| TEST 15 | RRF | 40.00% | 73.33% | 54.44% | 178 ms | 308 ms | 308 ms |
| TEST 15 | weighted rerank | 46.67% | 80.00% | 62.22% | 460 ms | 701 ms | 701 ms |

在全部 60 条中，46 条排名不变，7 条提升，3 条从未命中变为命中，3 条下降但仍命中，1 条从命中退化为未命中。最终 TEST Recall@1 和 Recall@3 均提升 6.67 个百分点，MRR@3 提升 7.78 个百分点。

## 6. 为什么没有使用纯 Cross-Encoder

第一次实验直接用 Cross-Encoder 完全替换 RRF 排名。TEST Recall@1 从 40.00% 提升到 53.33%，MRR@3 从 54.44% 提升到 58.89%，但 Recall@3 从 73.33% 降到 66.67%。这说明模型更擅长把少数高相关结果推到第一名，但也会把部分边界证据挤出 Top 3。

因此最终采用分数融合，而不是盲目相信单一模型。这个复盘比只展示一个提升数字更有面试价值：离线评测发现退化，分析排名变化，再通过保留粗排信号解决质量问题。

## 7. 复现步骤

1. 启动 MySQL、Redis、RabbitMQ 和 Qdrant：`docker compose up -d`。
2. 配置 Embedding、Qdrant 和 Rerank 环境变量。
3. 启动应用，以管理员身份登录 Swagger。
4. 调用 `GET /agent/knowledge/status`，确认 Qdrant、Embedding 和 Reranker 均启用。
5. 调用 `POST /agent/knowledge/rebuild`，确认长文档为 258/258、状态 `INDEXED`。
6. 调用 `GET /agent/evaluations/external-policy/retrieval`。
7. 分别记录 `baselineRrf` 和 `crossEncoderReranked` 的 DEV/TEST 指标，并检查逐题 `rankChange`。

## 8. 面试表达

可以表述为：项目采用关键词与 Qdrant 向量双路召回，经 RRF 融合后使用 qwen3-rerank 对 Top 30 候选精排。纯精排实验曾造成 Recall@3 退化，因此改用 Cross-Encoder 与归一化 RRF 加权融合。在 60 条人工锚点规章集上，固定 15 条测试集 Recall@3 从 73.33% 提升到 80.00%，MRR@3 从 54.44% 提升到 62.22%，平均检索耗时由 178 ms 增至 460 ms。知识索引采用 20 条 Embedding 和 64 个 Qdrant point 的批处理，减少外部 API 往返。

不能表述为“准确率 80%”或“生产可用率 80%”。Recall@3 是证据召回指标，不等于最终回答正确率；回答质量仍需引用正确率、忠实度和人工正确率评测。
