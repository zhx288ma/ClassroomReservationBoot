# 简历项目指标怎么写

简历上的指标要满足两个原则：

1. 必须是你能复现或解释来源的实测数据。
2. 不能只写 TPS，还要写业务正确性指标，否则教室抢约这种项目很容易被问“有没有超卖、有没有重复预约”。

## 1. 这个项目适合写哪些指标

### 性能指标

| 指标 | 怎么获得 | 简历价值 |
| --- | --- | --- |
| 并发线程数 | JMeter Thread Group | 说明压测规模 |
| 预约接口 TPS/QPS | JMeter Summary Report | 说明吞吐能力 |
| 平均响应时间 | JMeter Summary Report | 说明整体响应速度 |
| P95/P99 响应时间 | JMeter HTML Report | 说明尾延迟 |
| HTTP 5xx 错误率 | JMeter Summary Report | 说明系统稳定性 |

### 业务正确性指标

| 指标 | 怎么获得 | 简历价值 |
| --- | --- | --- |
| 是否超卖 | 查 MySQL 成功预约数是否超过库存 | 证明 Redis Lua + MySQL 兜底有效 |
| Redis 库存是否为负 | `/ops/redis/stock` | 证明缓存侧预扣库存正确 |
| 重复预约数 | 查 `active_key` 或同用户同时间段活跃订单 | 证明一人一约兜底有效 |
| 候补入队数 | 查 `tb_reserve_waitlist` | 证明库存不足时业务降级正常 |
| MQ 积压数 | `/ops/mq/overview` | 证明通知链路可消费 |

这些业务正确性指标比单纯 “TPS 很高” 更适合面试，因为你的项目亮点是防超卖、候补补位、异步通知，而不是普通查询接口。

## 2. 压测前准备

启动项目：

```bash
cd D:/A_project/crs/ClassroomReservationBoot
docker compose up -d --build
```

初始化 200 个压测用户：

```powershell
Get-Content -Raw .\jmeter\loadtest-users.sql | docker exec -i classroom-mysql mysql -uroot -p123456 classroom_reservation
```

压测用户：

```text
18800000001 ~ 18800000200
密码: 123456
```

## 3. 执行压测

```powershell
.\jmeter\run-load-test.ps1 -InitUsers -ReserveDate 2026-06-01 -TimeSlot "18:00-20:00"
```

查看报告：

```text
jmeter/report-时间戳/index.html
```

当前脚本场景：

```text
200 个不同用户
20 秒 ramp-up
每人提交 1 次预约
抢同一个 roomId=1、reserveDate=2026-06-01、timeSlot=18:00-20:00
```

这个场景主要验证“热点资源并发抢约是否超卖”。如果要压普通接口吞吐，可以另做查询类脚本，不要把两类结果混在一起。

## 4. 压测后怎么查正确性

### Redis 库存

登录后携带 `X-Token` 调用：

```text
GET /ops/redis/stock?roomId=1&reserveDate=2026-06-01&timeSlot=18:00-20:00
```

重点看：

```text
redisStock 不应小于 0
mysqlAvailableCapacity 不应小于 0
reservedUsers 是实际进入 Redis Set 的用户
```

### RabbitMQ 积压

登录后携带 `X-Token` 调用：

```text
GET /ops/mq/overview
```

重点看：

```text
classroom.reserve.notify.queue messages 是否能回落到 0
classroom.reserve.notify.dlq 是否有异常消息
```

### MySQL 预约结果

进入 MySQL 容器：

```bash
docker exec -it classroom-mysql mysql -uroot -p123456 classroom_reservation
```

检查成功预约数：

```sql
SELECT status, COUNT(*) 
FROM tb_reserve_order 
WHERE room_id = 1 
  AND reserve_date = '2026-06-01' 
  AND time_slot = '18:00-20:00'
GROUP BY status;
```

检查候补数：

```sql
SELECT status, COUNT(*) 
FROM tb_reserve_waitlist
WHERE room_id = 1 
  AND reserve_date = '2026-06-01' 
  AND time_slot = '18:00-20:00'
GROUP BY status;
```

检查是否有重复活跃预约：

```sql
SELECT active_key, COUNT(*)
FROM tb_reserve_order
WHERE active_key IS NOT NULL
GROUP BY active_key
HAVING COUNT(*) > 1;
```

正常结果应该是空。

## 5. 结果怎么填进报告

把实测数据填到：

```text
docs/性能测试报告.md
```

建议至少填这些：

```text
并发线程数
预约接口 TPS
平均响应时间
P95 响应时间
P99 响应时间
HTTP 5xx 错误率
是否超卖
Redis 库存是否为负
MQ 积压是否归零
```

## 6. 简历写法模板

没有实测前不要写具体数字，可以先写技术和验证方式：

```text
使用 JMeter 构造 200 用户热点教室抢约场景，验证 Redis Lua 预扣库存、
MySQL 条件更新和唯一索引兜底下无超卖、无重复预约，结合 Redis/MQ
运维接口检查库存一致性和通知队列积压。
```

有实测后再写数字：

```text
使用 JMeter 对热点教室预约链路进行 200 并发压测，预约接口 P95 响应
时间为 xx ms，HTTP 5xx 错误率为 xx%，MySQL 成功预约数不超过库存，
Redis 库存无负数，RabbitMQ 通知队列最终积压为 0。
```

如果测出来数字一般，也可以这样写，重点放在正确性：

```text
针对热门教室抢约场景做 200 并发一致性压测，验证系统在高竞争下
不超卖、不重复预约；通过 Redis Lua 原子预扣库存、MySQL 条件更新和
active_key 唯一索引完成多层兜底，RabbitMQ 异步通知最终消费无积压。
```

## 7. 面试时怎么解释“错误率”

抢约场景下，很多请求失败是正常的，因为库存有限。你要区分：

```text
业务失败：库存不足、进入候补、重复预约，这些不是系统错误。
系统失败：HTTP 500、连接超时、数据库异常，这些才是错误。
```

面试可以这样说：

```text
压测时我没有把所有业务失败都算成系统错误，因为热点资源库存有限，
大量请求进入候补或被拒绝是符合预期的。我重点看的是 HTTP 5xx、
库存是否为负、MySQL 是否超卖、MQ 是否堆积。
```
