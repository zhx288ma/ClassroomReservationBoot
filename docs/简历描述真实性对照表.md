# 简历指标口径表：哪些能写，哪些不能写

你给的例子属于“强指标型项目描述”：

```text
接口响应耗时从 15ms 优化至 2ms
本地缓存命中率 80%
整体命中率 95%
QPS 由 500 提升至 2000
性能提升 300%
```

这种写法可以很加分，但前提是你真的有代码、压测脚本、压测报告、指标来源。否则面试官问一句“怎么测的、测了几轮、机器配置是什么、P95 还是平均值”，就会很难接。

## 1. 当前项目可以支撑的描述

当前项目已经实现了这些能力：

| 能力 | 当前是否实现 | 代码或文档 |
| --- | --- | --- |
| Redis Lua 原子扣库存 | 已实现 | `ReservationServiceImpl.java` |
| Redisson 分布式锁 | 已实现 | `ReservationServiceImpl.java` |
| MySQL 条件更新防超卖 | 已实现 | `RoomSlotMapper.java` |
| 唯一索引兜底一人一约 | 已实现 | `schema.sql` |
| RabbitMQ 异步通知 | 已实现 | `RabbitConfig.java`、`NotificationConsumer.java` |
| RabbitMQ 重试和死信队列 | 已实现 | `RabbitConfig.java`、`application.yml` |
| Redis 运维检查接口 | 已实现 | `RedisOpsController.java` |
| MQ 运维检查接口 | 已实现 | `MqOpsController.java` |
| JMeter 热点预约压测脚本 | 已实现 | `jmeter/classroom-reservation-load-test.jmx` |
| 200 个压测用户初始化 | 已实现 | `jmeter/loadtest-users.sql` |

所以现在可以写的方向是：

```text
围绕热门教室抢约场景，使用 Redis Lua 完成库存和重复预约的原子校验，
结合 MySQL 条件更新与唯一索引防止超卖和重复预约；使用 Redisson 锁
保护取消预约与候补补位流程，并通过 RabbitMQ 异步生成站内信通知。
```

如果你跑了 JMeter，并填了真实数据，可以升级成：

```text
使用 JMeter 构造 200 用户热点教室抢约场景，预约链路 P95 响应时间为
xx ms，HTTP 5xx 错误率 xx%，压测后 MySQL 成功预约数不超过库存，
Redis 库存无负数，RabbitMQ 通知队列最终无积压。
```

这里的 `xx` 必须来自真实压测报告。

## 2. 当前还不能照抄的描述

> 2026-05-17 更新：项目已经接入 Caffeine + Redis 二级缓存、Prometheus/Grafana、Flyway、Testcontainers 测试类、Spring Security + JWT。  
> 因此“使用 Caffeine + Redis 二级缓存”“接入 Prometheus/Grafana 可观测”“使用 Flyway 管理数据库版本”“引入 Testcontainers 做集成测试”这些技术事实可以写。  
> 但“命中率 80%/95%”“QPS 从 500 到 2000”“接口从 15ms 到 2ms”这种数字仍然必须等真实压测报告出来后再写。

下面这些话现在不能直接写，因为当前代码还没有完整实现或还没有实测数据。

| 简历话术 | 现在能不能写 | 原因 |
| --- | --- | --- |
| `RabbitMQ 异步削峰，解决数据库压力` | 谨慎写 | 当前 MQ 用于异步通知，预约订单仍同步落库，不是完整异步下单削峰 |
| `接口响应耗时从 15ms 优化至 2ms` | 不能写 | 没有基准版本和优化版本的实测报告 |
| `Caffeine 本地 + Redis 分布式二级缓存` | 可以写 | 已接入 `TwoLevelCacheService`，覆盖教室详情、教室列表、推荐结果和 Redis 概览 |
| `本地缓存命中率 80%，整体命中率 95%` | 不能写 | 已有 Caffeine stats，但还没有正式压测报告支撑具体命中率数字 |
| `布隆过滤器防缓存穿透` | 不能写 | 当前还没有 Bloom Filter |
| `逻辑过期 + 异步重建解决热点 Key 击穿` | 不能写 | 当前教室缓存是普通 TTL，不是逻辑过期异步重建 |
| `QPS 由 500 提升至 2000，提升 300%` | 不能写 | 没有 DB 直连基准脚本和二级缓存优化脚本的对比报告 |

## 3. 当前项目更适合写成什么样

不要把“黑马点评秒杀商品”原样搬到“教室预约系统”。更自然的简历写法应该贴合本项目场景：

```text
热点教室抢约优化：针对热门教室同一时间段并发预约场景，使用 Redis Lua
原子完成库存预扣和重复预约校验，结合 MySQL 条件更新与 active_key 唯一
索引防止超卖和一人多约；取消预约时使用 Redisson 锁保护状态流转并触发
候补补位，RabbitMQ 异步生成站内信通知。通过 JMeter 构造 200 用户抢约
压测，验证库存不为负、无超卖、无重复活跃预约。
```

如果实测数据出来后，可以改成：

```text
热点教室抢约优化：针对热门教室同一时间段并发预约场景，使用 Redis Lua
原子预扣库存，结合 MySQL 条件更新和唯一索引防止超卖；通过 Redisson
锁保证取消和候补补位幂等，RabbitMQ 异步通知。JMeter 200 并发压测下，
预约接口 P95 响应时间 xx ms，HTTP 5xx 错误率 xx%，压测后库存无负数、
无超卖、通知队列最终积压为 0。
```

## 4. 如果想写“多级缓存指标”，还需要补什么

要写类似：

```text
Caffeine 本地 + Redis 分布式二级缓存
本地缓存命中率 80%
整体命中率 95%
QPS 从 500 提升到 2000
```

至少要补这些东西：

| 需要补的内容 | 目的 |
| --- | --- |
| Caffeine 依赖 | 做本地缓存 |
| 教室详情二级缓存逻辑 | 先查 Caffeine，再查 Redis，再查 MySQL |
| 缓存命中率统计接口 | 能看到 local hit、redis hit、db fallback |
| Bloom Filter | 防止不存在的 roomId 穿透到 DB |
| 逻辑过期字段 | 热点 Key 过期时先返回旧值 |
| 异步重建线程池 | 缓存逻辑过期后后台重建 |
| DB 直连压测脚本 | 得到基准 QPS |
| 二级缓存压测脚本 | 得到优化后 QPS |
| 对比报告 | 支撑“提升 xx%” |

这部分做完以后，才能写多级缓存相关指标。

## 5. 如果想写“RabbitMQ 异步削峰”，还需要补什么

当前预约流程是：

```text
请求进入
  -> Redis Lua 预扣库存
  -> MySQL 同步落预约单
  -> RabbitMQ 异步通知
```

这能说明：

```text
RabbitMQ 异步通知，降低主流程耦合。
```

但还不能严格说：

```text
RabbitMQ 异步削峰下单。
```

如果要写异步削峰，需要改成：

```text
请求进入
  -> Redis Lua 预扣库存
  -> 生成预约请求消息
  -> 立即返回排队中
  -> RabbitMQ 消费者异步写 MySQL 预约单
```

还需要补：

| 需要补的内容 | 目的 |
| --- | --- |
| 异步预约请求队列 | 承接高并发请求 |
| 预约消息 DTO | 传递 userId、roomId、日期、时间段 |
| 异步消费者落库 | 削峰写 MySQL |
| 预约结果查询接口 | 前端查询排队结果 |
| 消息幂等表或唯一索引 | 防止重复消费 |
| DLQ 和补偿机制 | 处理消费失败 |

做完这部分后，才能写“RabbitMQ 异步削峰”。

## 6. 数字应该怎么来

不要写“感觉上”的数字。建议用三类数据：

### 第一类：JMeter 性能数据

来自：

```text
jmeter/report/index.html
```

可写：

```text
平均响应时间
P95 响应时间
P99 响应时间
TPS/QPS
HTTP 5xx 错误率
```

### 第二类：业务一致性数据

来自 MySQL、Redis、MQ 运维接口。

可写：

```text
无超卖
无重复预约
Redis 库存不为负
MQ 最终无积压
DLQ 无异常消息
```

### 第三类：优化前后对比

只有同时测了“优化前”和“优化后”，才能写：

```text
从 xx ms 优化到 xx ms
QPS 从 xx 提升到 xx
性能提升 xx%
```

计算方式：

```text
提升百分比 = (优化后 QPS - 优化前 QPS) / 优化前 QPS * 100%
```

例如：

```text
(2000 - 500) / 500 * 100% = 300%
```

## 7. 当前最稳妥的简历版本

在还没有真实压测数字之前，建议先这样写：

```text
智慧教室预约系统：将传统 SSM/JSP 教室预约 CRUD 重构为 Spring Boot
REST 服务，围绕热门教室抢约设计时间段库存模型。使用 Redis Lua 原子
校验库存与重复预约，结合 MySQL 条件更新和唯一索引防止超卖、一人多约；
使用 Redisson 分布式锁保护取消预约与候补补位流程，RabbitMQ 异步生成
站内信通知，并补充 Swagger、Docker Compose、JMeter 压测脚本和 Redis/MQ
运维接口，支持压测后验证库存一致性与队列积压情况。
```

等你跑出数字后，再把最后一句换成：

```text
JMeter 200 并发压测下，预约接口 P95 响应时间 xx ms，HTTP 5xx 错误率
xx%，压测后 MySQL 成功预约数不超过库存、Redis 库存无负数、RabbitMQ
通知队列最终积压为 0。
```

## 8. 最后一句实话

目前项目已经可以写“高并发预约一致性优化”，但还不能写“Caffeine + Redis 二级缓存命中率 95%”或“RabbitMQ 异步削峰下单从 15ms 到 2ms”。

如果你想把简历写成更强的指标型版本，下一步应该做两件事：

1. 先跑现有 JMeter，拿到真实预约链路指标。
2. 再补二级缓存和异步预约削峰，分别产出缓存查询压测报告和异步预约压测报告。
