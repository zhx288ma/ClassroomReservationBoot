# 面试脱颖而出升级说明

本轮升级把项目从“教室预约 CRUD + 中间件演示”继续往“高并发预约履约平台”包装。重点不是继续堆技术名词，而是让每个技术点都能回答：解决了什么业务风险、怎么实现、怎么验证。

## 1. 可靠消息 Outbox

### 解决的问题

原先预约成功后直接调用 RabbitMQ 发送通知。面试官追问时容易出现一个经典问题：数据库事务成功但 MQ 投递失败怎么办？或者事务回滚了但消息已经发出怎么办？

本轮引入 Outbox 表，把“要发送的通知”先作为业务事件落库，再在事务提交后投递 MQ。如果 MQ 临时不可用，定时任务会补偿重试，超过最大次数进入 dead 状态。

### 核心实现

- Outbox 表：`src/main/resources/schema.sql:84`
- Outbox 实体：`src/main/java/com/xuan/boot/domain/NotificationOutbox.java`
- Outbox Mapper：`src/main/java/com/xuan/boot/mapper/NotificationOutboxMapper.java`
- 可靠消息服务：`src/main/java/com/xuan/boot/service/impl/NotificationOutboxServiceImpl.java:25`
- 事务提交后投递：`src/main/java/com/xuan/boot/service/impl/NotificationOutboxServiceImpl.java:44`
- 定时补偿投递：`src/main/java/com/xuan/boot/service/impl/NotificationOutboxServiceImpl.java:68`
- MQ 运维看板新增 Outbox 状态：`src/main/java/com/xuan/boot/service/impl/MqOpsServiceImpl.java:36`

### 面试说法

可以这样讲：

> 我没有只是在业务代码里直接发 RabbitMQ，而是做了一个轻量级事务 Outbox。预约、取消、候补补位这些动作先在同一个数据库事务里写入 Outbox 事件，事务提交后再投递 MQ。如果 RabbitMQ 不可用，事件不会丢，定时任务会扫描 pending/retrying 事件并按退避策略补偿投递。消费者用事件 id 作为站内信 id，重复消息会被幂等忽略。

### 验证方式

1. 正常预约或取消一次。
2. 管理员访问：

```text
GET /ops/mq/overview
GET /ops/mq/outbox
```

预期：`outbox.sent` 增加，站内信能被消费。

断网/故障验证：

1. 暂停 RabbitMQ 容器。
2. 执行一次取消或预约。
3. 查看 `GET /ops/mq/overview`，Outbox 会出现 `pending` 或 `retrying`。
4. 恢复 RabbitMQ。
5. 等待 3 秒或调用：

```text
POST /ops/mq/outbox/publish
```

预期：消息重新投递，状态变为 `sent`。

## 2. 接口审计与 TraceId

### 解决的问题

原先页面有前端日志，但后端缺少可观测链路。面试官问“线上接口慢了怎么定位”“谁操作了取消预约”“请求失败怎么排查”时，项目缺少落点。

本轮新增后端审计日志，对接口请求记录 traceId、用户、角色、URI、状态码、耗时、客户端 IP 和异常信息。

### 核心实现

- 审计表：`src/main/resources/schema.sql:99`
- 审计实体：`src/main/java/com/xuan/boot/domain/AuditLog.java`
- 审计 Mapper：`src/main/java/com/xuan/boot/mapper/AuditLogMapper.java`
- 审计拦截器：`src/main/java/com/xuan/boot/config/AuditInterceptor.java:15`
- 响应头返回 `X-Trace-Id`：`src/main/java/com/xuan/boot/config/AuditInterceptor.java:33`
- 审计管理接口：`src/main/java/com/xuan/boot/controller/AuditOpsController.java`
- 前端管理员日志页：`src/main/resources/static/index.html:477`
- 前端拉取审计日志：`src/main/resources/static/app.js:612`

### 面试说法

可以这样讲：

> 我给所有 API 请求加了审计拦截器，每次请求都会生成或透传 X-Trace-Id，并落库记录用户、角色、路径、状态码和耗时。管理员端可以查看最近接口调用。这个设计解决了两个问题：一是排查线上问题时可以通过 traceId 定位单次请求；二是取消预约、教室维护等操作具备可追溯性。

### 验证方式

1. 用管理员账号登录。
2. 刷新控制台、查看预约、进入中间件运维页面。
3. 打开“联调日志”页面。
4. 查看“后端接口审计”列表。
5. 或通过 Swagger 调用：

```text
GET /ops/audit/logs
GET /ops/audit/overview
```

预期：能看到最近接口、耗时、状态码、角色和 traceId。

## 3. 现在简历可以怎么写

下面这些说法更稳，不要在没有压测证据时乱写夸张指标：

> 基于 Spring Boot + MyBatis 重构教室预约系统，引入 Redis Lua 脚本完成库存预扣减，结合 Redisson 分布式锁实现同一用户同一时间段一人一单；通过 RabbitMQ 异步发送预约、取消、候补补位通知，并引入事务 Outbox 表和定时补偿任务，解决数据库事务与消息投递不一致问题。

> 构建管理员运维与观测能力：提供 Redis 库存视图、RabbitMQ 队列/死信队列/Outbox 状态、接口审计日志和 traceId 追踪；管理员端与学生端页面隔离，后端使用角色注解进行接口级权限校验，避免只靠前端隐藏菜单。

## 4. 后续还能继续升级的方向

优先级从高到低：

1. 多库存压测模型：支持 M 个学生抢 N 个教室库存，生成更真实的成功数、候补数、超卖数、平均响应时间。
2. Prometheus + Grafana：把接口 QPS、P95、Outbox 积压、MQ 积压做成图表。
3. 教室可用性日历：按日期和时间段展示可用库存热力图。
4. 用户信用分：迟到/未签到降低信用，影响预约优先级。
5. 候补公平性策略：FIFO、信用分、课程优先级组合排序，并解释为什么这样排序。
6. WebSocket/SSE 通知：候补补位后实时推送到前端。
