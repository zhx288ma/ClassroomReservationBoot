# 智慧教室预约与资源调度平台：面试准备底稿

> 这是一份个人项目面试底稿。所有压测数据均来自本机 Docker 中间件 + 本地 Spring Boot 测试环境，不能表述为生产指标。
>
> 最后校准：2026-08-24。Tomcat 最大线程调整为 200 后，1000 个总用户按每批 300 人抢约的测试也实现了零错误；但该轮 `1000/300` 不是整除批次，报告吞吐量不用于横向对比。简历性能数值优先使用批次整除、零错误的 200 人稳定档；300 人档用于说明调优后的稳定并发能力。

## 1. 一句话定位

这是一个面向校园自习场景的教室时段资源调度平台：管理员维护可开放的教室时段 `room_slot`，学生预约一个时段中的一个名额，满员进入候补；系统围绕抢约时的防超卖、重复提交、签到与未签到信用分、异步通知及事件统计展开。

## 2. 30 秒项目介绍

这是一个基于 Spring Boot 的校园教室时段预约与资源调度平台。管理员维护教室时段和容量，学生预约时段名额而不是整间教室，满员后进入候补，并支持签到、取消和信用分管理。我负责预约核心链路、表结构与 Redis Key 设计，以及 RabbitMQ、Kafka、SSE 和 JMeter 压测接入。热门时段抢约通过 Redis Lua 做库存、重复预约和时间冲突的原子校验，MySQL 条件更新及唯一约束兜底。在本地测试环境中，以 1000 个总用户、每批 300 人抢约 80 个名额，预约接口 1000 次请求全部成功；库存、订单和候补数据一致，无超卖、无重复预约。

## 3. 3 分钟项目介绍

项目面向学生、教师和管理员。第一版没有引入复杂的课程表导入，而是由管理员直接创建、开放、关闭或维护 `room_slot`，即“教室 + 日期 + 时间段 + 容量”的资源单元；这更接近可落地的运营方式，也使后续课程表模块能平滑接入。

学生预约的是 `room_slot` 中一个名额，多个学生可以预约同一个时段；同一学生不能重复预约同一时段，也不能预约时间重叠的另一个教室。教师申请整间教室需要审批，管理员不能直接关闭已有学生预约的时段。预约成功后学生在规定窗口签到，超时未签到会被定时任务标记为爽约并扣信用分，取消和未签到释放名额后会触发候补补位。

我主要负责预约、候补、签到的事务链路和中间件工程化。请求先校验一次性提交 Token；Redis Lua 以原子方式扣减库存、判断同一时段冲突和重复预约；随后在 MySQL 事务中通过条件更新扣减库存、插入预约记录，并由唯一索引兜底。事务中的通知和领域事件分别写入 Outbox，定时发布到 RabbitMQ 和 Kafka，避免业务提交成功但消息发送失败。RabbitMQ 消费者写站内信并通过 SSE 推送在线用户；Kafka 消费者更新预约、签到、爽约等统计。教室搜索可选 ES，ES 只返回候选列表，最终预约仍回到 Redis 与 MySQL 校验。

性能方面，我按 100、200、300、400、1000 个同步放行用户做了容量曲线测试。Tomcat 最大线程从 120 调整为 200 后，1000 个总用户按每批 300 人抢约的预约链路达到 1000/1000 成功，数据库核对为 80 条正式预约和 920 条候补，无超卖、无重复预约。因该轮 `1000/300` 的最后一批人数不足，吞吐量不作横向对比。简历中的响应时间和吞吐量采用批次整除的 200 人稳定档：平均 241.08ms、P95 815ms、P99 1031.87ms、JMeter 统计吞吐量 41.31 req/s。极限 1000 人同步放行时曾出现 49.3% TCP 连接拒绝，反映的是调优前本地单实例入口容量边界，不能包装成稳定生产吞吐。

## 5. 核心链路：学生抢约

1. 前端先调用创建一次性 Token 接口，提交时携带 `X-Submit-Token`。
2. `ReservationServiceImpl.reserve` 校验当前登录用户、时间规则和 Token；Token 使用后立即失效，避免重复点击。
3. 查询并确认 `room_slot` 为 OPEN，使用 `SETNX` 初始化 Redis 剩余库存。
4. 执行 Lua：判断库存、该用户是否已预约该 slot、该用户是否已占用相同时间段；三项通过后扣库存并写入标记。
5. 在 MySQL 事务内使用 `available_capacity > 0` 的条件更新扣减库存，再插入预约单；数据库索引是最终兜底。
6. 成功后写通知 Outbox、Kafka 事件 Outbox，返回预约成功；库存不足时按 FIFO 进入候补。
7. 若 MySQL 落库失败，事务回滚回调补偿 Redis 标记和库存。

代码入口：

- `src/main/java/com/xuan/boot/service/impl/ReservationServiceImpl.java:57`：Lua 脚本。
- `src/main/java/com/xuan/boot/service/impl/ReservationServiceImpl.java:109`：预约事务主流程。
- `src/main/java/com/xuan/boot/service/impl/ReservationServiceImpl.java:406`：执行 Lua。
- `src/main/java/com/xuan/boot/mapper/RoomSlotMapper.java:39`：MySQL 条件扣减库存。

## 6. 高频技术选型回答

### 为什么核心模型是 room_slot？

教室本身是静态资源，但“某间教室在某天某时段是否开放、剩余多少名额”才是可交易资源。`room_slot` 统一承载学生开放、关闭、维护和教师整间占用等状态，也让库存、候补、签到和统计都能按同一个资源维度关联。

### 为什么学生预约名额，教师预约整间？

学生自习通常只占一个座位，按教室容量开放才有真实的库存、候补、签到与爽约治理场景；教师上课、考试或活动需要整间教室，因此采用申请审批，通过后占用整个时段。这样既符合实际，又避免把普通学生预约设计成不合理的“独占教室”。

### 为什么 Redis Lua、MySQL 条件更新和唯一索引要同时存在？

Redis Lua 在单次脚本中完成库存、重复预约、时间冲突判断，减少并发下多次往返并保护热点库存；MySQL 条件更新保证持久化层不会把库存扣成负数；唯一索引防止应用缺陷、补偿重试或 Redis 异常时写出重复数据。它们是不同层次的防线，不是重复堆料。

### 为什么还要 Redisson 锁？

Lua 只保护 Redis 内的原子操作，无法覆盖取消预约、候补补位、状态转换这种跨 Redis 和 MySQL 的多步骤流程。这里的锁按预约单或时段细粒度设置，保护同一资源的复杂状态流转，不能把所有预约都锁成全局串行。

### RabbitMQ 和 Kafka 都使用，职责怎样划分？

RabbitMQ 用于“需要被执行的业务任务”：预约成功、候补补位、爽约、工单等通知。Kafka 用于“已经发生的业务事件”：预约、取消、签到、爽约等，通过消费者做趋势、热度和使用率统计。Kafka 不参与预约是否成功的判断，也不解决超卖。

### Outbox 解决什么问题？

如果先提交 MySQL 再直接发消息，消息发送失败会造成数据库状态已经成功但通知/统计丢失；反过来先发消息又会出现消费到不存在的业务数据。项目在本地事务内同时写业务表和 Outbox，由定时任务扫描并投递，成功后标记 SENT，失败记录重试次数并进入失败状态。

### Elasticsearch 为什么不能作为预约成功依据？

ES 用于多条件搜索和筛选，索引同步存在延迟；预约属于库存和状态强一致事务，最终必须以 MySQL + Redis 校验为准。ES 返回的是候选教室，不是库存承诺。

### SSE 和 RabbitMQ 的关系是什么？

RabbitMQ 把后端异步任务可靠送到通知消费者；消费者落库到通知表后，通过 SSE 给在线用户推送。用户不在线仍可从通知表读取，SSE 本身不承担可靠消息存储。

## 7. 一次真实问题复盘：把“管理和统计”移出抢约热路径

**问题背景**：首版预约实现把一些非核心工作混进了每一次抢约请求：请求线程需要兜底初始化时段库存，并在竞争路径中查询/同步预约人数、候补人数等展示型计数。这样做功能上能跑通，但热门时段下每个用户都可能额外访问 MySQL 或 Redis，数据库读写放大，多个请求还会竞争同一条 `room_slot` 记录。

**为什么这是代码设计问题：** 抢约主链路真正需要回答的只有四件事：时段是否开放、用户是否重复/冲突、是否还有名额、预约是否成功落库。候补数量、管理看板的统计数和资源初始化不决定本次预约的结果，把它们放在同步请求里会拉长事务和连接占用时间，也让压测结果混入无关开销。

**改造方案：**

1. 将 `room_slot` 明确为管理员预先创建和开放的资源；抢约时只查询已存在且为 OPEN 的时段，不在高并发请求中创建时段。
2. Redis 库存仅在 Key 不存在时通过 `SETNX` 以 `room_slot.available_capacity` 初始化；随后由 Lua 一次完成库存、重复预约、时间冲突和用户标记写入。
3. MySQL 主路径只保留带 `available_capacity > 0` 条件的扣减和预约单插入，唯一索引兜底重复数据。
4. 候补单使用 `insert ignore` 保证幂等；`waitlist_count` 不再在每个满员请求中同步更新。当前通过管理员重算接口从候补表对账，后续可定时化，避免热点行额外写竞争。
5. 通知、Kafka 事件和统计通过 Outbox 在事务后异步处理，不阻塞预约成功的同步返回。

**代码定位：**

- `ReservationServiceImpl.loadOpenSlotAndInitRedisStock`：只加载已开放时段并用 `SETNX` 初始化 Redis 库存。
- `ReservationServiceImpl.executeReserveScript`：一次 Lua 调用完成库存和用户维度的原子判断。
- `ReservationServiceImpl.reserve`：MySQL 条件扣减、订单落库和事务回滚 Redis 补偿。
- `ReservationServiceImpl.joinWaitlist`：候补计数不进入抢约热路径，改为后续对账。
- `RoomSlotController.reconcileCounters`：管理员触发从预约/候补事实表重算 `room_slot` 展示计数。

**验证结果：** 在容量为 80 的 `room_slot` 上，1000 个总用户分批抢约后，最终 MySQL 核对为 80 条正式预约、920 条候补，`available_capacity=0`、重复用户数为 0。说明将展示型计数移出热路径后，主链路仍保持正确的库存边界、候补落库和重复预约约束。性能数值仅采用批次整除、零错误的稳定档报告，避免把不同压测模型混为一次优化前后对比。

**可复盘的经验：** 热点接口不要为了“页面上的实时数字”在同步事务里维护所有派生字段。先保证交易事实正确，再让看板、候补计数、通知和统计走异步聚合或定时对账；代价是这些展示数据可能短暂最终一致，但不会影响预约正确性。

## 9. 高频追问速答

1. **Redis 宕机怎么办？** 当前关键链路依赖 Redis Lua，Redis 不可用时应快速失败而不是绕过库存校验；生产环境可部署 Redis 高可用并补偿对账。MySQL 条件更新和唯一索引可以兜底数据正确性，但不能直接替代高并发下的热点流量削峰。
2. **Lua 扣了库存，MySQL 失败怎么办？** 注册事务完成回调；只有事务回滚时才执行 Redis 库存和用户标记补偿，后续还可通过 Redis/MySQL 对账任务修复异常。
3. **消息重复消费怎么办？** 通知表和事件统计均以业务 ID/事件 ID 做幂等约束或幂等判断；消费者要允许至少一次投递，不能假设 MQ 恰好一次。
4. **候补如何补位？** 第一版 FIFO；取消、未签到或补偿后由定时任务扫描可补位时段，以时段锁串行处理候补状态，再把候补转换为预约并通知用户。
5. **为什么不直接用数据库事务和 `select for update`？** 可以实现，但热门时段会把锁竞争集中到单行，吞吐下降。当前先用 Redis Lua 在缓存层做并发裁决，MySQL 只承担最终条件更新和持久化。
6. **Token 和 JWT 有什么区别？** JWT 是身份认证凭证，用于识别当前用户；Submit Token 是一次性幂等令牌，用于防表单重复提交，生命周期和用途不同。
7. **Caffeine + Redis 二级缓存怎样一致？** 本地缓存用于减少 Redis 网络访问，Redis 用于多实例共享。教室信息更新时先更新数据库，再删除 Redis 和本地缓存；允许短暂不一致，核心库存不走该缓存。
8. **Flyway 的价值？** 用版本化 SQL 管理表结构演进，开发、测试、部署环境按相同顺序迁移，避免手动改库造成结构漂移。
9. **如何观察系统？** Actuator 暴露健康、指标和 Prometheus 端点；MySQL 看连接数与慢 SQL，Redis 看命中和内存，RabbitMQ 看队列积压与 DLQ，Kafka 看消费者延迟。
10. **单机 300 人为什么会出现 Connection refused？** 这是 TCP 建连阶段的拒绝，请求没进入 Controller；JMeter、单 Spring Boot 实例和 Docker 中间件共享同一台 Windows 主机时，Tomcat 线程、连接队列、CPU 调度和下游连接占用会共同限制入口。把 Tomcat 最大线程从 120 调到 200 后，该轮 300 人批次错误率降为 0%，但这只是本机调参验证，不能推导为生产容量。生产应使用网关限流、负载均衡、多实例和可观测性指标做容量规划。
11. **如果重做会优先改什么？** 先完成 300、400、500 人批次的等比例复测，并采集 Tomcat、Hikari、CPU 与 Redis/MQ 指标；再增加网关限流和排队策略，将候补确认改为带确认时限的状态机；随后补多实例 Redis、消息幂等唯一约束和更完整的集成测试。

## 10. 技术选型辩护：为什么选它，不选另一个

回答模板始终是四步：**先说业务问题，再给选择，再说替代方案，最后讲边界。** 不要回答“因为它流行”或“教程就是这样写的”。

### 10.1 为什么采用 Spring Boot

**可直接回答：** 项目需要统一管理 Redis、RabbitMQ、Kafka、Actuator、Flyway 和测试配置。Spring Boot 的自动配置、Starter 依赖管理、Profile 和 Actuator 能降低这些基础设施的接入和运维成本，因此我把它作为单体 REST 服务的工程底座。

**为什么不是 Spring Cloud：** 项目目前是单体，预约、候补、签到之间有强事务关联。过早拆微服务会引入远程调用、分布式事务、链路追踪和部署复杂度，不能提升核心预约正确性。只有教室搜索、通知、统计出现独立扩容需求时，才考虑逐步拆分。

**追问边界：** Spring Boot 不是天然高并发；吞吐仍受 Tomcat、连接池、Redis、MySQL 和机器资源共同限制。

### 10.2 MySQL，而不是 Redis / Elasticsearch / MongoDB

**选择原因：** 预约、签到、信用分都需要事务、唯一约束、条件更新和可追溯的持久化记录。MySQL 是唯一的核心事实库，`room_slot`、`reservation`、`waitlist` 等状态最终都落在 MySQL。

**为什么 Redis 不能替代：** Redis 擅长热点并发裁决，但缓存可能丢失、过期或与数据库不一致；它不能作为预约历史、信用记录和管理员审计的最终依据。

**为什么 Elasticsearch 不能替代：** ES 索引是近实时同步，适合搜索候选集，不保证库存强一致；用 ES 判断“还能不能预约”会导致陈旧库存和超卖风险。

**为什么不是 MongoDB：** 当前业务是关系明确的事务模型，重点是条件更新、唯一约束和关联核对。若后续存大量非结构化反馈附件或行为日志，可考虑将其作为补充存储，而非替换核心关系库。

### 10.3 Redis Lua，而不是 JVM `synchronized` / 只用数据库锁

**选择原因：** 热门 `room_slot` 抢约需要在一次原子操作中完成“库存是否大于零、是否重复预约、同一时段是否冲突、扣减库存、写入标记”。Lua 在 Redis 服务端串行执行，避免这些步骤分散为多次网络往返后发生竞态。

**为什么不是 `synchronized`：** JVM 锁只覆盖当前进程；一旦多实例部署，各实例互相不知道对方的锁，无法保护共享库存。

**为什么不只用 MySQL `SELECT ... FOR UPDATE`：** 它能保证正确性，但热门单行会出现大量锁等待，数据库承受所有失败请求。当前由 Redis 先快速裁决并挡住大部分竞争，MySQL 只做最终持久化和条件更新。

**边界和兜底：** Lua 不能跨 Redis 与 MySQL 保证全局事务，所以 MySQL 仍有 `available_capacity > 0` 条件更新和唯一索引；事务回滚时补偿 Redis，并可通过对账任务修复极端不一致。

### 10.4 Redisson，而不是手写 `SETNX` 分布式锁

**选择原因：** 对预约、候补补位、取消和状态转换这类跨 Redis/MySQL 的多步骤流程，需要按用户、预约单或时段做细粒度互斥。Redisson 封装了可重入锁、看门狗续期和安全释放，降低手写锁误删、超时提前释放等风险。

**为什么 Lua 之后还需要锁：** Lua 仅保证单次 Redis 脚本原子；候补补位、取消预约等还包含数据库更新、状态机判断和消息 Outbox 写入，属于更长的临界区。

**边界：** 锁不是越多越好。抢约主路径不使用全局锁，避免把并发请求串行化；锁只保护复杂状态流转，且数据库约束仍是最后防线。

### 10.5 Caffeine + Redis，而不是只用 Redis / 只用本地缓存

**选择原因：** 教室基础信息、热门榜和搜索推荐属于读多写少数据。Caffeine 在本机内存命中，避免每次访问 Redis 的网络开销；Redis 使多实例之间共享缓存结果。更新教室信息时，先更新 MySQL，再删除 Redis 与本地缓存，允许短暂最终一致。

**为什么不用它缓存库存：** 库存和预约状态要求强一致，不能依赖本地缓存的过期与异步刷新；库存仍走 Redis Lua + MySQL。

**为什么不是 Guava Cache：** Guava Cache 能满足基础需求，但 Caffeine 的并发性能、淘汰策略和统计能力更适合高频本地缓存场景。

### 10.6 RabbitMQ，而不是 Kafka / 异步线程池

**选择原因：** 预约成功、候补补位、爽约、工单等属于“必须被执行”的业务任务，通常要重试、死信和按消费者处理。RabbitMQ 的确认、路由、TTL/死信队列适合做通知和延迟提醒任务。

**为什么不是 Kafka：** Kafka 更适合高吞吐事件流和可回放消费，不适合把每个用户通知当作任务队列来做精细重试、延迟和死信处理。Kafka 在项目中只记录已经发生的领域事件。

**为什么不是 `@Async` 线程池：** 进程内线程池随应用重启会丢任务，也不支持跨实例可靠消费；它可以用于非关键的本地并行计算，不能承担预约通知等可靠异步任务。

**边界：** RabbitMQ 不决定预约是否成功。先完成 MySQL 事务并写 Outbox，后续异步投递，消息失败不会回滚已确认的预约。

### 10.7 Kafka，而不是让 RabbitMQ 兼做统计

**选择原因：** 预约、取消、签到、爽约等事件需要按时间回放，供统计消费者持续计算热门时段、签到率、爽约率和管理员大屏。Kafka 的 Topic、分区、消费者组和保留策略更适合事件流和独立扩展的统计消费者。

**为什么不能用 Kafka 解决超卖：** Kafka 消费是异步的，生产后不代表数据库库存已扣减；把库存判断放到 Kafka 消费端会让请求无法同步返回、引入乱序和重复消费处理，不能替代 Redis Lua + MySQL 事务。

**为什么不只用 RabbitMQ：** RabbitMQ 可以消费事件，但在保留、重复回放、多消费者独立消费和流式统计上不如 Kafka 自然。项目保留 RabbitMQ 做业务动作，Kafka 做分析，职责单一。

**边界：** 当前 Kafka/统计模块通过开关配置启用，面试必须如实说是单机 Docker 验证的实现，不宣称已有生产级集群吞吐。

### 10.8 Outbox，而不是“事务后直接发消息”或 2PC

**选择原因：** 数据库提交和 MQ/Kafka 发送是两个独立操作。直接在业务代码中发消息会出现“数据库成功、消息失败”或“消息先到、数据未提交”的双写问题。项目将业务状态和 Outbox 记录写入同一个 MySQL 事务，扫描任务只投递已提交事件，成功后再标记 SENT。

**为什么不是分布式事务 / 2PC：** 对本项目来说，2PC 复杂、性能代价大且会把数据库与消息系统强耦合。Outbox 加至少一次投递和消费者幂等是更常见、可落地的最终一致方案。

**追问：会不会重复投递？** 会，所以消费者按事件 ID 或业务唯一键做幂等；设计目标是“至少一次 + 幂等”，不是不现实的端到端恰好一次。

### 10.9 SSE，而不是 WebSocket / 轮询

**选择原因：** 当前通知是服务端单向推送：候补补位、信用分变动、管理员回复、预约提醒。SSE 基于 HTTP，前端接入简单、自带自动重连，适合这一类单向事件通知。

**为什么不是 WebSocket：** WebSocket 支持双向长连接，更适合聊天室、实时协作或客户端需要频繁上行消息的场景；本项目首版没有这类需求，SSE 的实现和运维复杂度更低。

**为什么不是短轮询：** 轮询实现简单，但会制造无效请求且通知延迟受轮询间隔影响。通知仍先落 `notification` 表，SSE 只负责在线实时体验，不承担可靠存储。

### 10.10 Elasticsearch，而不是 MySQL `LIKE`

**选择原因：** 教室查询需要关键词、楼栋、容量范围、设备、用途和开放时段等多条件组合筛选。ES 对全文检索、倒排索引和聚合更合适，可提升复杂搜索体验。

**为什么 MySQL 仍保留查询：** 管理后台和强一致详情可以直接查 MySQL；ES 不可用或索引延迟时可降级到 MySQL 条件查询。预约成功永远以 Redis + MySQL 为准。

**为什么首版不引入 Canal：** 首版数据规模和变更频率有限，采用业务同步/定时同步即可验证索引链路。数据规模上升或多服务写入后，再用 Canal/CDC 解耦 MySQL Binlog 同步。

### 10.11 Spring Security + JWT，而不是自定义拦截器 + Session

**选择原因：** Spring Security 提供标准过滤器链、认证失败处理、路径授权和方法级授权能力；JWT 适合前后端分离和多实例无状态鉴权。项目按角色区分学生、教师和管理员，并让每个请求携带认证凭证。

**为什么不是 Session：** Session 适合传统服务端渲染项目，但多实例需要共享 Session 或粘性会话；JWT 让认证状态不保存在单个应用内存中，部署扩展更直接。

**边界：** JWT 不是天然可撤销。当前通过 Redis 会话/黑名单或过期时间控制；高安全场景需要短 Access Token + Refresh Token、设备管理和主动失效策略。

### 10.12 Flyway、Testcontainers、Prometheus：工程化而非“堆技术”

| 组件 | 解决的问题 | 为什么不是手工方式 |
| --- | --- | --- |
| Flyway | 用版本化 SQL 管理表结构演进。 | 手改数据库难以在开发、测试、部署环境复现，容易结构漂移。 |
| Testcontainers | 测试中启动接近真实的 MySQL、Redis、RabbitMQ 容器。 | Mockito 只能验证单元逻辑，不能发现 SQL、序列化、MQ 配置和中间件兼容问题。 |
| Actuator + Micrometer + Prometheus | 暴露健康、请求耗时、连接池、JVM 和业务指标。 | 看控制台日志无法持续回答 QPS、P95、队列积压和资源瓶颈。 |
| Docker Compose | 将 MySQL、Redis、RabbitMQ 等依赖声明化。 | 手动安装和配置环境不可复现，新机器启动成本高。 |

## 11. 进一步的架构判断题

1. **为什么没有上 ShardingSphere 分库分表？** 当前压测与数据规模没有证明单库单表到达瓶颈。提前分片会增加全局唯一 ID、跨分片查询和事务复杂度；先通过索引、冷热分离、归档和读写优化解决，达到明确量级后再分片。
2. **为什么没有上 Sentinel？** 目前已通过压测找到了本地入口容量边界，但限流规则与网关还未正式落地。若进入多实例部署，Sentinel 或网关限流可按用户、IP、接口和 `room_slot` 热点做限流/排队；不能假装项目已经具备完整生产限流体系。
3. **为什么不用布隆过滤器防缓存穿透？** 教室 ID 和时段主要由后台创建、数据量可控，当前先用参数校验、空值缓存与数据库索引即可。若开放任意 ID 高频查询并出现恶意穿透，再引入 RedisBloom 或本地布隆过滤器。
4. **为什么不做“逻辑过期 + 异步重建”保护库存？** 逻辑过期适合教室详情、热榜等允许短暂旧数据的读缓存；库存不允许返回旧值作为预约依据，因此不适用。
5. **为什么不做课程表自动导入？** 第一版让管理员维护开放时段，可独立落地且覆盖真实运营。二期再以 `course_schedule` 生成或拦截冲突的 `room_slot`，避免把排课系统集成变成预约核心链路的前置依赖。

## 12. JavaGuide 常见项目追问：结合本项目的回答

这一节不是要求逐字背诵。每题先用两三句话说结论；面试官继续追问时，再落到后面的表、索引、代码和配置。凡是标有“当前限制”的内容，都应如实说明，不要把设计方案说成已验证的生产能力。

### 12.1 业务和架构

#### 项目最重要的业务链路是什么？

核心链路是“学生抢约一个开放 `room_slot` 名额”。管理员先维护“教室 + 日期 + 时间段 + 容量”的 `room_slot`，学生携带 JWT 和一次性 Submit Token 发起预约；服务端通过 Redis Lua 判断库存、重复预约和时间冲突，再用 MySQL 条件更新和唯一索引完成最终落库。满员时进入候补，取消或爽约释放名额后再补位。

**证据位置：** `ReservationServiceImpl.reserve`、`RoomSlotMapper.decreaseStockById`、`tb_room_slot`、`tb_reserve_order`、`tb_reserve_waitlist`。

#### 系统里哪个环节最容易出问题？

最容易出问题的是 Redis 与 MySQL 的双写边界：Lua 已扣减 Redis 库存后，MySQL 条件更新或订单插入可能失败。项目的做法是 MySQL 事务回滚时补偿 Redis 库存和用户标记；MySQL 的条件更新和唯一索引保证即使缓存异常也不会写出超卖或重复订单。极端宕机或人工修复场景仍需要 Redis/MySQL 对账任务。

第二个高风险点是候补补位，它涉及释放库存、候补状态更新、创建预约和通知。项目按时段/候补加 Redisson 细粒度锁，候补写入使用唯一约束或 `insert ignore` 保证幂等。

#### 如果流量增加到当前的几倍，最先出现瓶颈的可能在哪里？

不是先假设 Redis 一定慢，而是先看指标。当前单机压测下，最先需要关注的是 HTTP 入口排队、Tomcat 工作线程、Hikari 连接池和热门 `room_slot` 的 MySQL 条件更新竞争；随后才是 Redis 单 Key 热点、RabbitMQ 积压和 Kafka 消费延迟。当前配置中 Tomcat 最大线程为 200，Hikari 最大连接数为 40，这两个参数不能脱离 CPU、数据库最大连接数和 SQL 耗时单独调大。

**当前限制：** 项目尚未做多实例横向扩容和网关限流实测。若流量继续上升，我会先按 `room_slot`、用户和接口设置网关限流/排队，再增加应用实例并监控连接池、Redis 延迟、数据库慢 SQL 和 MQ 积压，而不是只继续增大 Tomcat 线程。

#### 单体和微服务如何选择？拆分以后增加哪些成本？

当前采用单体，因为预约、取消、候补、签到和信用分之间强关联，单体内本地事务和代码调试成本更低。RabbitMQ、Kafka、SSE 已经把通知和统计在逻辑上解耦，未来可优先拆出通知或统计消费者，而不必拆分抢约核心。

拆分后的成本包括：接口契约和版本管理、网络超时与重试、分布式链路追踪、数据一致性和消息幂等、服务发现/配置管理、灰度发布以及更多监控告警。微服务不是并发优化按钮，抢约库存的正确性仍要依赖 Redis 和 MySQL。

### 12.2 数据库和缓存

#### 核心表如何设计？为什么选择这个主键和索引？

| 表 | 作用与主键 | 关键索引 / 约束 | 回答重点 |
| --- | --- | --- | --- |
| `tb_room_slot` | 可交易资源；自增 `id` 适合单库关联和条件更新。 | `uk_room_slot(room_id, reserve_date, time_slot)`；`idx_slot_date(reserve_date, time_slot)`。 | 同一教室同一时段只能有一个资源行，库存以该行的 `available_capacity` 为准。 |
| `tb_reserve_order` | 预约事实；使用业务生成的 `BIGINT id`。 | `uk_active_key`；`idx_user_time`、`idx_room_time`、`idx_status_time`。 | `active_key` 用于限制有效预约，用户/房间时间索引支持我的预约、管理员查询和冲突核对。 |
| `tb_reserve_waitlist` | 满员后的候补事实。 | `uk_waiting_user_slot`；`idx_wait_slot(room_id, reserve_date, time_slot, status, create_time)`。 | 防止同一用户重复候补，并按时段、状态、创建时间做 FIFO 补位。 |
| `tb_notification_outbox` / `tb_event_outbox` | 可靠消息待发送记录。 | `(status, next_retry_time)`；事件表还有 `uk_event_id`。 | 定时扫描待发送/重试记录，避免全表扫描，并用事件 ID 支撑幂等。 |

`room_slot` 采用自增主键是因为当前是单库单体；预约/候补等业务单号由应用层生成，便于对外暴露且不依赖数据库自增回填。若未来分库分表，再统一引入雪花算法或号段服务，不能只因为“高并发”就提前分片。

**证据位置：** `src/main/resources/db/migration/V1__init_schema.sql`、`V4__room_slot_capacity_and_event_architecture.sql`。

#### 慢 SQL 是怎么发现的？执行计划里看了哪些字段？

当前本地项目没有一条经过生产流量验证的“真实慢 SQL”，因此不能编造慢 SQL 优化故事。我的排查路径是：先通过 Actuator/Micrometer 和审计日志定位高耗时接口，再从 MySQL 慢查询日志或 `performance_schema` 找 SQL，最后执行 `EXPLAIN` / `EXPLAIN ANALYZE`。

对预约相关 SQL 主要看：`type` 是否从 `ALL` 降到 `ref/range`，`possible_keys` 与 `key` 是否命中预期复合索引，`rows` 预估扫描行数，`Extra` 是否出现 `Using filesort`、`Using temporary`，以及实际执行耗时和锁等待。比如候补查询应命中 `idx_wait_slot`，教室时段查询应命中 `uk_room_slot`，不能在高频接口中按无索引条件扫全表。

#### 哪些数据放入缓存？缓存失效后如何处理？

教室基础信息、热门教室榜和推荐结果可使用 Caffeine + Redis 二级缓存：Caffeine 处理单机热点，Redis 供多实例共享；默认 Redis TTL 为 30 分钟，本地 TTL 为 5 分钟。教室信息更新后先更新 MySQL，再删除本地与 Redis 缓存，让后续读请求回源重建。

预约库存不使用 Caffeine。`reserve:stock:*`、用户预约标记和同时间段标记属于并发控制状态，Redis Key 不存在时以 MySQL `available_capacity` 初始化，之后由 Lua 原子维护；缺失或异常时不允许绕过校验直接写库。

#### 缓存和数据库不一致时，业务可以接受多长时间？

教室详情、设备标签、热门榜等展示数据可接受分钟级短暂不一致，当前上限由本地 5 分钟和 Redis 30 分钟 TTL 约束，更新操作主动删除缓存通常会更快恢复。库存、预约状态、信用分资格不接受读旧缓存作为写入依据，必须回到 Redis Lua 和 MySQL 事务校验。

**追问加分点：** 缓存删除失败不是“绝对零风险”。项目可用重试/定时刷新兜底；高要求场景再引入消息驱动失效、版本号或 CDC。不要承诺缓存永远强一致。

### 12.3 消息和一致性

#### 为什么要发送这条消息，同步调用是否可行？

预约成功通知、候补补位、爽约信用分通知、反馈工单提醒不影响“本次预约是否成功”，若同步发通知会拉长用户接口，并把 MQ 或通知服务故障传递到抢约主链路。因此主事务只写业务数据和 Outbox，后续由 RabbitMQ 执行业务通知；Kafka 则消费“已发生事件”做统计。同步调用在强依赖、必须实时返回的库存校验中才使用，即 Redis Lua 与 MySQL 条件更新。

#### 生产者发送失败、消费者重复处理和消息积压分别怎么办？

| 场景 | 当前实现 | 进一步措施 |
| --- | --- | --- |
| 生产者发送失败 | Outbox 保留 `PENDING/RETRY` 记录，定时任务按 `next_retry_time` 重发；最多重试 5 次，最终标记失败/死信。 | 告警 `retrying/dead` 数量，并提供运营补发或人工处理。 |
| 消费者重复 | 以通知/事件 ID、业务单号或唯一键做幂等判断；接受“至少一次投递”。 | 对统计表设置 `(stat_date, stat_type, stat_key)` 唯一约束，重要消费者记录已消费事件 ID。 |
| 消息积压 | RabbitMQ 有重试和死信队列配置，Kafka 用消费者组消费。 | 监控队列深度、未确认消息、Kafka lag；扩消费者或限流，但先定位慢消费者、毒消息和下游数据库瓶颈。 |

**证据位置：** `NotificationOutboxServiceImpl`、`DomainEventServiceImpl`、`application.yml` 中 RabbitMQ 重试、Publisher Confirm 和 Kafka `acks=all` 配置。

#### 本地事务提交成功但消息发送失败如何处理？

不在事务提交后直接“尽力发送”。业务表更新和 Outbox 插入同属一个 MySQL 本地事务；提交成功但 MQ/Kafka 发送失败时，Outbox 仍处于可扫描状态，定时发布器重试。发送成功才把 Outbox 标为 `SENT`。因此系统接受通知和统计的最终一致，而不丢失待发送事实。

#### 接口幂等依赖什么业务唯一标识？

防重复提交有三层：Submit Token 用 `submit_token:{userId}:{token}` 做一次性删除；Redis Lua 的 `reserved_users` 与 `reserved:user_time` 拦截重复/冲突；MySQL 通过 `tb_reserve_order.active_key` 和候补唯一约束兜底。消息侧使用 Outbox `event_id` 或业务单号做消费者幂等。它们分别覆盖 HTTP 重试、缓存并发、数据库落库和异步消费，不能只靠一个 UUID。

### 12.4 并发和稳定性

#### 线程池参数根据什么设置？队列满了会发生什么？

当前没有为预约主链路额外创建业务线程池，它运行在 Tomcat 请求线程中；`server.tomcat.threads.max=200`、`accept-count=2000`、`max-connections=3000`，Hikari 最大连接数为 40。参数关系是：请求线程不会都同时占一个数据库连接，连接池必须结合 SQL 耗时、数据库最大连接数、CPU 核数和压测 P95 设定，不能简单把两者都无限增大。

Tomcat 工作线程耗尽时，请求会进入 Connector 的接受队列；接受队列与连接上限也满后，新连接可能被拒绝或客户端超时。当前压测已观察过这种本机单实例入口边界。消息消费线程的重试由 RabbitMQ Listener 配置管理；`@Scheduled` 扫描任务应避免执行重活，后续可配置独立任务调度线程池并监控执行延迟。

#### 下游接口变慢时，超时、重试、限流和熔断怎么配合？

预约主链路不做对 MQ/Kafka 的同步 RPC，避免通知下游拖慢抢约。Redis 客户端超时当前为 3 秒，Hikari 获取连接超时为 30 秒；这在生产中需要结合 SLO 进一步压缩，防止线程长时间堆积。重试只用于 Outbox 等可幂等异步任务，并采用退避和最大次数；不能对“扣库存”这种同步写请求盲目重试。

当前项目尚未落地 Sentinel/网关熔断，这是明确限制。生产化顺序是：先在网关或入口按用户/热点时段限流和排队；下游异常时快速失败或降级展示查询；对通知、统计这类异步链路重试并进入死信；最后通过指标触发告警和扩容。

#### Redis、数据库或消息队列不可用时，项目还能提供哪些能力？

| 依赖不可用 | 当前行为 | 可提供 / 不可提供的能力 |
| --- | --- | --- |
| Redis | 抢约快速失败，不能绕过 Lua 直接预约。 | 可在数据库仍可用时提供部分非缓存管理查询；不能保证热点预约、Submit Token、会话/实时排名等能力。 |
| MySQL | 业务事务无法落库。 | 只可提供静态页面或已缓存的非关键展示；预约、签到、取消、信用分全部停止写入。 |
| RabbitMQ | Outbox 持续积累，预约事务仍可成功。 | 预约结果可返回，但站内信/SSE 异步通知延迟；MQ 恢复后由 Outbox 补发。 |
| Kafka | 事件 Outbox 积压，预约事务仍可成功。 | 预约、签到可完成；实时统计、大屏和分析数据延迟，恢复后重试投递。 |

这体现了依赖分级：库存与数据库是强依赖，通知和统计是可降级的最终一致依赖。

#### 发布出现问题时，如何回滚并确认数据没有损坏？

当前是 Docker Compose 本地部署，尚未实现完整 CI/CD 灰度发布，因此不能宣称有生产级自动回滚。我的可执行步骤是：

1. 发布前备份数据库，并确保 Flyway 迁移采用向前兼容、可回滚的变更策略；不能把“删除列”与应用代码切换放在同一步。
2. 先观察 `/actuator/health`、错误率、P95、Hikari 活跃连接、Outbox 待发送/死信和 RabbitMQ/Kafka 积压。
3. 出现业务异常时停止新版本并切回上一镜像；对于已经执行的 Flyway 变更，优先写新的修复迁移，而不是直接篡改 `flyway_schema_history`。
4. 用 SQL 对账 `room_slot.available_capacity`、有效预约数、候补数和 Redis 库存/用户标记；检查 Outbox 是否存在未发送或失败记录，再补发消息。
5. 对受影响的 `room_slot` 暂时关闭开放状态，完成对账与补偿后再恢复，避免带着不确定库存继续接收预约。

**一句话总结：** 代码回滚不等于数据回滚；预约项目必须额外验证库存、订单、候补和消息 Outbox 四类状态。

## 13. 简历描述逐条追问清单

### 13.1 项目简介与业务建模

#### 1. 为什么学生预约的是名额，而不是整间教室？

学生自习只占用一个座位，教室容量才是可分配资源；若让一个学生独占整间教室，无法解释容量、候补、抢约和签到治理。教师上课、考试或活动才需要整间教室，所以教师申请单独走审批，通过后占用对应时段。

#### 2. `room_slot` 是什么，为什么它是核心表？

`room_slot` 是“一个教室在某日期某时间段的资源实例”，包含总名额、剩余名额、已预约数和开放状态。教室表只描述静态属性，而预约、候补、签到、维护和教师占用都发生在具体时段，因此都应关联 `room_slot`。

#### 3. 管理员为什么直接维护时段，不导入课程表？

第一版优先保证可落地：管理员根据空闲、维护和实际课程安排开放时段，避免依赖排课系统、课程数据质量和复杂冲突处理。二期可以新增 `course_schedule`，由课程表生成占用时段或阻止冲突开放，但不改变 `room_slot` 为核心资源的设计。

#### 4. 教师申请与学生预约冲突怎么办？

教师整间预约需要管理员审批。若目标时段已有学生有效预约，第一版拒绝强制占用；管理员也不能直接关闭或维护已有预约的开放时段。这样避免“管理员操作覆盖学生已确认权益”的数据和业务冲突。

#### 5. 预约状态、候补状态分别如何流转？

预约通常是 `RESERVED -> CHECKED_IN -> FINISHED`，也可从 `RESERVED` 到 `CANCELLED` 或 `NO_SHOW`；候补是 `WAITING -> PROMOTED/CONFIRMED`，或 `CANCELLED/EXPIRED`。状态更新必须带旧状态条件，避免重复取消、重复签到或重复补位。

### 13.2 高并发预约：来自第一条个人工作的追问

#### 6. Submit Token 和 JWT 分别解决什么问题？为什么两者都要？

JWT 是身份凭证，回答“谁在请求”；Submit Token 是一次性幂等令牌，回答“这一次表单提交是否已被消费”。用户已登录仍可能双击、浏览器重试或网络重发，所以 JWT 不能替代 Submit Token。Token 存在 Redis，提交时原子删除，重复提交会被拒绝。

#### 7. Lua 脚本具体做了哪些事情？为什么不能拆成多次 Redis 命令？

脚本同时读取 `stock`、已预约用户集合和用户时间冲突标记：先判断剩余名额，再判断是否预约过该时段、是否已有重叠时段预约；全部通过才扣减名额并写两类用户标记。若拆成多个 Redis 命令，两个并发请求可能都在“判断有库存”后再扣减，从而产生竞态。

#### 8. Redis Key 如何设计？过期时间如何确定？

核心 Key 包括：`reserve:stock:{roomId}:{date}:{timeSlot}`、`reserve:users:{...}`、`reserve:user-time:{userId}:{date}:{timeSlot}` 与一次性 `submit_token:{userId}:{token}`。时段库存和预约标记的 TTL 要覆盖预约时段及必要的补偿窗口；Submit Token TTL 较短且消费即删除。Key 过期不代表业务结束，MySQL 仍是预约事实来源。

#### 9. Lua 已经扣了 Redis 名额，MySQL 条件更新失败怎么办？

MySQL 更新使用 `available_capacity > 0` 条件，若更新失败说明数据库状态与缓存不一致或时段状态变化；代码会同步 Redis 状态或在事务回滚回调中补偿 Redis 名额和用户标记。最终可通过 `room_slot`、有效预约单与 Redis Key 对账。不能仅依赖 Lua 认为预约已成功。

#### 10. MySQL 条件更新与唯一索引各防什么？

条件更新防止数据库层把剩余名额扣到负数；`active_key` 等唯一约束防止应用重试、补偿重放或 Redis 异常时插入重复有效预约。前者解决容量边界，后者解决用户维度的重复和时间冲突，两者不能互相替代。

#### 11. 为什么不用 `synchronized` 或全局 Redisson 锁实现抢约？

`synchronized` 只保护单 JVM，多实例失效；全局锁会让所有教室时段串行。主路径采用 Redis Lua 对单时段数据原子裁决，Redisson 仅用于取消、候补补位等跨 Redis/MySQL 的复杂状态转换，并按用户、订单或时段细粒度加锁。

#### 12. Redis 宕机时为何不直接退化为只写 MySQL？

当前策略是抢约快速失败，不绕过 Redis Lua。虽然 MySQL 条件更新与索引可以保护正确性，但突发热点会直接压向数据库，导致锁竞争和连接耗尽；正确性与可用性需要明确取舍。生产环境应使用 Redis 高可用、限流与对账，而不是在故障时取消并发防线。

#### 13. 同一用户连续请求两个不同教室的同一时间段，如何保证只成功一个？

Redis Lua 写入以用户、日期和时间段组成的冲突 Key；数据库也用 `active_key` 和用户时间索引兜底。若两个请求并发到达，Lua 只会允许第一个写入冲突标记；即使极端情况下缓存补偿导致竞态，数据库唯一约束仍会拒绝重复有效预约。

#### 14. 你说“无超额占用”，怎么证明？

将一个 `room_slot` 的总名额固定为 80，压测结束后核对三类数据：有效预约数必须 `<= 80`，`reserved_count` 必须等于有效预约数，`available_capacity = total_capacity - reserved_count`；再检查有效订单中同一用户是否出现多条，以及 Redis 库存是否与数据库一致。报告中的 HTTP 200 不足以证明无超额占用，必须做数据库核对。

### 13.3 候补、签到与信用治理：来自第二条个人工作的追问

#### 15. 为什么候补第一版选择 FIFO，而不是信用分排序？

FIFO 可解释、易验证且符合先到先得；第一版重点是先保证补位正确性。信用分、等待时长、违约次数可以作为二期 `priority_score`，但一旦引入动态排序，需要明确分数快照、重排时机和公平性规则，复杂度更高。

#### 16. 取消预约后如何避免“释放一个名额，补位两个人”？

取消操作按预约单加锁，先用状态条件更新将订单改为取消，再增加名额并触发同一时段候补补位；候补补位也使用时段/候补锁与状态条件更新。候补从 `WAITING` 转为已补位后不能再被第二个任务选中，数据库唯一约束继续兜底。

#### 17. 候补用户被补位后要不要确认？不确认怎么办？

当前基础流程可直接补位并通知；更完整的设计是 `PROMOTED` 后设置确认截止时间，超时转为 `EXPIRED`、释放名额并继续补下一位。面试时应明确：若代码当前未完整实现确认时限，则把它说为下一步状态机增强，不能说已经具备。

#### 18. 签到窗口如何校验？用户改本地时间有没有用？

后端用服务器当前时间与预约开始时间比较，只允许开始前 15 分钟至开始后 15 分钟签到；前端时间只负责展示，不参与可信判断。用户修改电脑时间不会改变服务端校验结果。

#### 19. 为什么未签到后还可能释放名额？时段都开始了有什么意义？

是否释放取决于运营规则。对于开始后仍允许入场的自习场景，未签到释放名额可让候补用户在剩余时间使用；对于课程或考试场景可以只记爽约而不补位。当前项目将其作为可配置的运营策略，第一版重点验证状态、信用分和通知正确性。

#### 20. 信用分如何防止被刷？分数低了具体限制什么？

信用分变更只由服务端业务事件触发，例如签到奖励、未签到扣分，不暴露直接修改分数接口；每次变动写 `credit_record` 流水。当前以最低预约分数限制普通预约资格；后续可让低分用户降低候补优先级、限制热门时段或限制日预约次数。

### 13.4 Outbox、RabbitMQ、Kafka、SSE：来自第三条个人工作的追问

#### 21. Outbox 是如何避免双写不一致的？

预约事务中同时写预约单和 Outbox；两者同属 MySQL 本地事务，事务失败一起回滚。提交后定时任务扫描待发送记录，投递成功才更新状态，失败按退避重试。这样不会出现“消息已发送但预约单未提交”，也不会因瞬时 MQ 故障丢失待发送事实。

#### 22. Outbox 扫描任务并发执行会不会重复发消息？

可能出现至少一次投递，因此消费者必须幂等。事件 Outbox 有 `event_id` 唯一约束，通知/统计消费应以事件 ID 或业务单号做去重。更严格的实现可为扫描记录增加抢占状态或 `select for update skip locked`，避免多个实例重复扫描；当前单体部署下仍以消费者幂等作为最终保证。

#### 23. RabbitMQ 的 Confirm、Return、重试、死信分别做什么？

Confirm 确认 Broker 是否收到生产者消息；mandatory + Return 处理消息到达交换机却没有路由到队列的情况；Listener 重试处理消费者短暂异常；超过重试次数后进入死信队列，避免毒消息无限阻塞正常消费。Outbox 的重试解决“生产端最终有没有投递成功”，消费者幂等解决“可能收多次”。

#### 24. 为什么 RabbitMQ 和 Kafka 同时使用，是否重复建设？

两者消费同一业务事实但目标不同：RabbitMQ 是需要执行的任务，例如通知和提醒，强调路由、重试、死信；Kafka 是已经发生的事件流，强调保留、回放、消费者组和统计。若只用一个组件也能做部分工作，但职责混杂后会使通知重试和数据分析互相影响。

#### 25. Kafka 消费重复、乱序或积压时，统计会不会错？

Kafka 消费按至少一次处理，统计消费者不能简单 `count + 1` 后就认为正确，应以事件 ID 去重或使用幂等 upsert；同一资源相关事件最好以 `room_slot_id` 或订单 ID 作为 Key 保证分区内顺序。积压时预约主链路不受影响，统计大盘延迟，待消费者恢复后可从 Topic 补消费。

#### 26. SSE 推送失败或用户不在线怎么办？

SSE 只是在线体验层，不是可靠消息通道。通知消费者先持久化到 `tb_notification`，再尝试推送；用户不在线、连接断开或推送失败，消息仍在站内信，用户下次查询即可看到。SSE 客户端可自动重连，但已读状态仍以数据库为准。

### 13.5 缓存与 Elasticsearch：来自第四条个人工作的追问

#### 27. 为什么教室信息做两级缓存，而剩余名额不做？

教室名称、楼栋、容量、设备和热门榜属于读多写少且允许短暂旧数据的信息，适合 Caffeine 降低本机 Redis 网络访问，再用 Redis 支持多实例共享。剩余名额属于并发写状态，若读取本地旧缓存判断可预约，会直接造成名额超额占用，所以只能走 Redis Lua 和 MySQL 条件更新。

#### 28. 更新教室后如何保证 Caffeine 和 Redis 都失效？会不会不一致？

先更新 MySQL，再删除 Redis 和本地 Caffeine 缓存，下次查询回源重建。这是缓存删除而非强一致分布式事务，删除失败仍可能出现短暂旧数据，因此有 TTL 兜底并可补充异步重试。它只影响展示和搜索体验，不影响预约的最终校验。

#### 29. Caffeine 为什么比只用 Redis 更合适？

只用 Redis 每次仍有序列化与网络开销；Caffeine 是进程内高性能缓存，适合热点教室详情和热门榜。代价是每个实例都有一份缓存，更新时必须做失效处理；Redis 作为第二级使多实例间不必各自回源 MySQL。

#### 30. Elasticsearch 索引怎样设计？数据如何同步？

索引以教室为主，包含 `roomId`、楼栋、教室号、容量、设备、标签、用途和可用时段摘要；搜索支持关键词与多条件过滤。当前可采用业务更新时同步写入或定时同步，ES 不可用时降级 MySQL 条件查询。数据规模和多服务写入增大后，再考虑 Canal/CDC 基于 Binlog 同步。

#### 31. 为什么 ES 查询到“有余量”却仍可能预约失败？

ES 索引存在同步延迟，搜索结果只表示候选时段；用户真正提交时，其他人可能已占满名额。因此提交接口必须再次通过 Redis Lua 与 MySQL 校验，ES 绝不能作为成功预约依据。

### 13.6 压测与性能指标：来自第五条个人工作的追问

#### 32. 为什么选择 1000 用户、80 个名额、每批 250 人？

80 用于模拟有限名额热点时段，1000 用户形成明显供大于求，能够同时验证成功预约、候补和并发冲突处理。每批 250 人通过同步定时器制造短时竞争峰值，又避免一次性释放全部线程导致本机压测机、应用和 Docker 容器同时被瞬时打满。`1000 / 250 = 4`，批次整除，不会产生最后一批等待同步器超时的统计失真。

#### 33. JMeter 测试计划到底请求了哪些接口？为什么汇总采样数可能是 3000？

每个虚拟用户通常执行登录、获取 Submit Token、提交预约三个 HTTP 请求，因此总采样数可能为 3000；简历中的“1000 次请求”必须特指标签为 `Reserve Hot Room` 的预约采样器，而不是把登录和 Token 接口混进去。分析报告时要分别查看三个采样器的错误率和响应时间。

#### 34. 平均 324ms、P95 951ms、P99 1.11s、QPS 的含义是什么？

平均值反映整体平均体验，P95 表示 95% 的预约请求不超过 951ms，P99 表示 99% 不超过约 1.11s，尾延迟用于观察热点时的排队与偶发抖动。QPS/吞吐量必须从同一份 JTL 中以预约采样器的样本数除以其时间跨度计算或使用 HTML 报告的 Throughput；不能用总采样数、也不能把 HTTP 失败请求悄悄剔除。

#### 35. 为什么不直接说“支持 1000 并发”？

1000 是总虚拟用户数，不等于 1000 个请求在同一瞬间全部成功进入业务。此测试是 4 批、每批 250 人同步抢约，因此应如实说“模拟 1000 用户、每批 250 人抢约，预约接口零错误”。若要证明 1000 同步并发，需要 `BarrierSize=1000` 的独立报告，并单独说明错误率和环境限制。

#### 36. 压测中错误率为 0，是否说明系统没有问题？

不说明。它只证明该数据规模、机器、配置和时段下预约采样器未出现错误。还要看 P95/P99、CPU、Tomcat 活跃线程、Hikari 活跃连接、Redis 延迟、MySQL 锁等待、RabbitMQ 堆积和 Kafka lag；还要重复三次以上取趋势，而不是只保留一次最好结果。

#### 37. 为什么 P99 比平均响应高很多？如何优化？

热门批次同时到达会造成 Redis、Tomcat、连接池与数据库条件更新的短时排队，少量请求的等待时间拉高 P99。优化要先用指标定位：若连接池等待高，优化 SQL/连接池与数据库；若 Redis 延迟高，检查热点 Key 和网络；若入口排队高，做限流、排队和横向扩容。不能只因为 P99 高就盲目增大线程池。

#### 38. 如何证明候补 920 条与预约 80 条没有遗漏？

核对同一 `room_id + reserve_date + time_slot`：有效预约状态计数为 80，WAITING 候补为 920，两者之和为 1000；再检查重复用户数为 0、`room_slot.reserved_count=80`、`available_capacity=0`。若业务规则允许取消或过期，需要在核对 SQL 中明确哪些状态算“有效”。

### 13.7 Spring Security、工程化与个人贡献追问

#### 39. Spring Security 中认证与授权如何区分？

认证是解析 JWT 并确认当前用户身份；授权是根据角色和接口决定是否允许访问，例如管理员维护 `room_slot`、教师提交整间教室申请、学生查看自己的预约。服务端不能只根据前端菜单隐藏功能，必须在过滤器链、路径或方法权限中校验角色。

#### 40. 为什么使用 Flyway？数据库字段变更怎么上线？

Flyway 将建表、加列、索引等变更作为有序版本 SQL 迁移，避免开发/测试/Docker 环境手工改库后结构不一致。上线变更遵循向前兼容：先加字段/索引、应用兼容读写、确认稳定后再清理旧字段；发生问题时通过新的修复迁移恢复，而不是直接修改迁移历史。

#### 41. Docker Compose 带来的实际价值是什么？

将 MySQL、Redis、RabbitMQ 等依赖的版本、端口、账号和网络声明化，新机器可按同一份配置启动，减少“本机能跑、别人不能跑”的环境差异。Docker 不替代配置管理，密码和生产地址仍应通过环境变量或密钥系统注入。

#### 42. Actuator、Micrometer、Prometheus 分别是什么关系？

Actuator 提供健康和指标端点；Micrometer 是应用内指标门面，把 JVM、HTTP、连接池和自定义业务指标统一为 Meter；Prometheus 定期抓取 `/actuator/prometheus` 并存储时序数据。Grafana 可在此基础上可视化 QPS、P95、线程、连接池和消息积压。

#### 43. 你“独立完成”具体指什么？

我独立完成需求抽象、表结构和状态设计、后端预约/候补/签到主链路、Redis/MQ/Kafka/SSE 接入、前端联调、Docker 环境与 JMeter 测试脚本。面试中可以展示关键代码、Swagger 调试流程、Docker 服务状态、JMeter 报告与压测后的 MySQL 核对 SQL，避免只说“我负责后端”。
