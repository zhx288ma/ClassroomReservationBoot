### 面试说法

> 注册时先根据手机号查询用户是否存在，避免重复注册；密码不明文入库，而是通过 Spring Security 的 `PasswordEncoder` 做加密；数据库层对 `phone` 加唯一索引，防止并发注册绕过服务层校验。入参层面会校验手机号必须是 `1[3-9]` 开头的 11 位手机号，密码不能为空且不少于 6 位，避免脏数据进入用户表。

### 常见追问

**为什么服务层检查了手机号，还要数据库唯一索引？**

服务层校验用于给用户友好提示，但并发情况下两个请求可能同时通过校验；唯一索引是最后一道数据一致性兜底。

**为什么不用明文密码？**

明文密码泄漏风险太大。这里使用 `PasswordEncoder`，生产环境通常用 BCrypt、PBKDF2、Argon2 等带盐、慢哈希算法。

## 2. 登录与 Redis Token 登录态

### 实现链路

```text
POST /auth/login
  -> AuthController.login
  -> AuthServiceImpl.login
  -> UserMapper.findByPhone 查询用户
  -> PasswordEncoder.matches 校验密码
  -> Redis 写入 login:token:{token} -> userId
  -> 返回 token
```

后续请求：

```text
请求 Header 携带 X-Token
  -> AuthInterceptor.preHandle
  -> AuthServiceImpl.getUserByToken
  -> Redis 查询 token 对应 userId
  -> UserMapper.findById 查询用户
  -> UserContext ThreadLocal 保存当前用户
  -> 请求结束 afterCompletion remove
```

### 面试说法

> 我没有继续使用传统 Session，而是把登录态放到 Redis。登录成功后生成随机 token，Redis 保存 `login:token:{token} -> userId` 并设置 TTL。拦截器从 `X-Token` 或 Bearer Token 中读取 token，校验成功后把用户放入 ThreadLocal，方便业务层获取当前用户，请求结束后 remove，避免线程复用导致用户串号。

### 常见追问

**为什么用 Redis 存 token？**

Redis 登录态适合前后端分离和多实例部署，避免 Session 只存在单机内存里。

**ThreadLocal 为什么必须 remove？**

Tomcat 线程会复用，如果不清理，下一次请求可能读到上一个用户的数据，也可能造成内存泄漏。

### 面试说法

> 教室详情是高频读接口，所以我用 Redis 缓存。先查 `cache:classroom:{id}`，命中直接返回；未命中再查 MySQL，并把结果写回 Redis。即使数据库查不到，也会缓存 `"null"`，防止缓存穿透。修改教室后删除缓存，后续查询再回源加载，保证最终一致性。

### 常见追问

**怎么解决缓存穿透？**

查不到的数据也缓存空值，避免恶意请求不存在 ID 一直打到数据库。

**怎么解决缓存雪崩？**

代码里给 TTL 加随机秒数，避免大量 key 同时过期。

**缓存和数据库怎么保持一致？**

写操作先更新数据库，再删除缓存；读请求发现缓存缺失时再加载新值。

## 6. 高并发预约：Redis Lua 预扣库存

### 实现链路

```text
POST /reservations
  -> ReservationController.reserve
  -> ReservationServiceImpl.reserve
  -> Redisson 用户维度锁
  -> 校验一次性提交 token
  -> 校验教室状态
```

### 面试说法

> 热门教室预约本质上类似秒杀。我把 `roomId + reserveDate + timeSlot` 抽象成库存资源。请求进来后先校验预约日期不能早于今天；如果预约今天，则时间段开始时间必须晚于当前时间，且时间段必须符合 `HH:mm-HH:mm` 并落在 `08:00-20:00` 内；再用 Redis Lua 在 Redis 侧原子完成三件事：判断库存、判断用户是否重复预约、扣减库存并记录用户。这样可以把大量并发挡在 Redis 层。随后 MySQL 再通过 `available_capacity > 0` 的条件更新做最终库存兜底，并通过 `active_key` 唯一索引保证一人一约。

### 常见追问

**为什么用 Lua？**

Redis 单条命令原子，但多个命令组合不原子。Lua 脚本能把库存判断、重复预约判断、扣库存、记录用户合并成一个原子操作。

**为什么 Redis 扣了库存，MySQL 还要扣？**

Redis 用来抗高并发和快速失败，MySQL 是最终数据源。双层设计能兼顾性能和最终一致性。

**如果 Redis 扣成功但 MySQL 扣失败怎么办？**

代码会执行 Redis 回滚，把库存加回去，并移除用户预约标记。

## 7. 一人一约与 active_key 幂等兜底

### 面试说法

> 一人一约做了两层保证：第一层是服务层查询同一用户同一时间段是否已有活跃预约，提前返回友好提示；第二层是数据库 `active_key` 唯一索引，防止并发请求绕过服务层校验。取消订单时把 `active_key` 置空，历史订单不影响用户以后重新预约。

### 常见追问

**为什么不用 `user_id + date + time_slot` 直接做唯一索引？**

直接唯一索引会让用户取消后无法再次预约同一时间段。`active_key` 可以在取消时置空，MySQL 允许多个 NULL，历史订单不会阻塞新订单。

## 8. 候补队列

### 实现链路

```text
预约时库存不足
  -> 如果 joinWaitlist = true
  -> joinWaitlist
  -> 检查是否已在候补队列
  -> 插入 tb_reserve_waitlist
  -> RabbitMQ 发送候补成功通知
```

取消预约后：

```text
cancel
  -> 释放库存
  -> 先清理过期候补
  -> promoteWaiter
  -> 找队首候补用户
  -> 检查候补用户是否同时间段已有预约
  -> Redis Lua + MySQL 扣库存
  -> 候补状态 WAITING -> PROMOTED
  -> 创建正式预约单
```

候补退出和过期：

```text
用户点击取消候补
  -> cancelWaitlist
  -> Redisson 锁住候补单
  -> status WAITING -> CANCELED
  -> 发送站内信

定时任务 / 查询候补 / 看板统计 / 补位前
  -> expireExpiredWaitlists
  -> 过期规则：日期早于今天，或今天的时间段已经开始
  -> status WAITING -> EXPIRED
  -> 过期候补不再参与补位，也不再计入 waitingCount
```

### 面试说法

> 候补队列是教室预约场景里的差异化业务。热门教室满了以后，用户可以进入候补队列。有人取消时，系统不会简单库存 +1，而是先清理过期候补，再优先取候补队首用户自动补位。用户也可以主动取消候补，候补过期后会自动转为 EXPIRED，不再参与补位和看板 waitingCount 统计。这样候补不是一个只会增长的“假队列”，而是有完整生命周期的业务对象。

### 常见追问

**为什么候补补位也要扣库存？**

因为取消可能和其他预约请求并发发生。补位也必须走相同库存扣减逻辑，不能绕过库存模型。

**候补队列为什么可以用 Redis ZSet？**

当前版本用 MySQL 表实现，便于持久化和审计；如果要更高性能，可以用 Redis ZSet，以申请时间戳作为 score，用户 ID 作为 member。

> 取消预约不能简单库存 +1。我的流程是先用 Redisson 锁住订单，避免重复取消；再通过状态条件更新把订单置为取消，同时把 `active_key` 置空；然后回滚 MySQL 和 Redis 库存，最后触发候补补位。这样能防止重复取消、重复回滚和资源浪费。

## 22. 当前实现的不足和升级方向

面试中主动说不足，会显得你很清醒：

1. 当前 Redis Lua 只做预扣库存，预约单仍同步落库；后续可以升级成 Redis Stream 异步落库。
2. RabbitMQ 已有发布确认、消费重试和死信队列，但还没有本地消息表；后续可做事务消息或 outbox 模式。
3. 智能推荐当前是规则引擎，不是机器学习；后续可加入用户画像、历史预约偏好和利用率预测。
4. 单元测试目前覆盖基础逻辑，并已新增 Testcontainers 集成测试类，用于拉起 MySQL/Redis/RabbitMQ 验证真实中间件连接。
5. 压测报告目前是模板，需要在装好 JMeter 后生成真实 `result.jtl` 和 HTML 报告。
