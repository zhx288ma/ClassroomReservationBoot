# 教室预约系统组件全景与面试讲法

> 更新时间：2026-05-17  
> 目标：把项目从普通 CRUD 包装成“有并发一致性、缓存、消息可靠性、可观测、工程化测试和前后端角色闭环”的 Java 后端项目。

## 1. 项目现在能怎么介绍

这是一个基于 Spring Boot 的智能教室预约平台，围绕“教室资源检索、预约下单、库存一致性、候补补位、通知投递、运维观测、角色权限”做了工程化升级。

简历可以写成：

> 基于 Spring Boot + MyBatis + MySQL 实现教室预约平台，使用 Spring Security + JWT 完成无状态认证和 RBAC 权限控制；针对预约并发冲突，引入 Redis Lua 原子扣减库存、Redisson 分布式锁和一次性提交令牌，避免超卖、重复提交和一人多单；使用 Caffeine + Redis 构建二级缓存，缓存教室列表、详情、智能推荐和 Redis 运维概览，并在教室变更时主动删除本地与分布式缓存；通过 RabbitMQ + 可靠消息 Outbox 实现预约通知异步投递、失败重试和死信兜底；接入 Micrometer + Prometheus + Grafana 暴露 QPS、延迟、异常、Outbox 积压等指标；使用 Flyway 管理数据库版本迁移，使用 Docker Compose 与 Testcontainers 提升本地部署和集成测试可信度。

## 3. 认证授权：Spring Security + JWT

### 是什么

Spring Security 是 Spring 生态标准安全框架，负责认证、授权、过滤器链和异常处理。JWT 是无状态 Token，服务端不用保存 session，就能从 token 中解析用户身份。

### 为什么这样做

之前项目是自定义拦截器 + 随机 token，能用但不够标准。升级后面试可以讲：

- 登录成功签发 JWT，网关或后端过滤器校验签名和过期时间。
- Redis 保存 token allowlist，用于退出登录和强制失效。
- Spring Security 负责请求是否需要登录，`@RequireRole` 负责业务级角色校验。

### 怎么做

- `SecurityConfig.java:23` 关闭 CSRF、开启无状态会话、放行登录注册和 Swagger，把其他接口设为必须认证。
- `JwtAuthenticationFilter.java:35` 从 `X-Token` 或 `Authorization: Bearer` 取 token，校验后写入 `SecurityContext` 和 `UserContext`。
- `JwtTokenService.java:38` 手写 HS256 JWT 生成逻辑，`JwtTokenService.java:61` 验签、解析、判断过期。
- `AuthServiceImpl.java:62` 登录时生成 JWT，`AuthServiceImpl.java:68` 校验 token 时同时查 Redis allowlist。
- `AuthController.java:41` 退出登录时删除 Redis 中的 token。
- `AuthInterceptor.java:35` 只做 `@RequireRole` 权限判断，不再重复认证。

### 面试说法

> 我把认证从自定义 token 升级为 Spring Security + JWT。JWT 负责无状态身份声明，Redis 保存 token allowlist，既能保持接口无状态，又能支持退出登录和主动失效。权限层面用 Security 过滤链兜底登录态，再用自定义 `@RequireRole` 做管理员接口保护。

## 4. 并发预约：Redisson + Lua + 提交令牌

### 是什么

这是预约主链路的核心：用户提交预约时，需要同时解决库存超卖、重复提交、一人一单和取消释放库存。

### 为什么这样做

普通 CRUD 直接查库再更新，在并发下容易出现两个问题：

- 多个请求同时看到库存为 1，最后插入多条预约单，出现超卖。
- 用户连续点击提交，重复创建预约单。

### 怎么做

- `ReservationController.java:37` 提供 `/reservations/submit-token`，前端先拿一次性提交令牌。
- `ReservationServiceImpl.java:92` 把提交令牌写入 Redis，TTL 5 分钟。
- `ReservationServiceImpl.java:226` 预约时消费令牌，防止重复提交。
- `ReservationServiceImpl.java:100` 使用 Redisson 用户锁，避免同一用户并发下单。
- `ReservationServiceImpl.java:114` 首次预约时把 MySQL 可用容量初始化到 Redis。
- `ReservationServiceImpl.java:47` Lua 脚本检查库存和用户集合，成功时扣减库存并记录用户。
- `ReservationServiceImpl.java:253` 调用 Redis Lua，实现库存扣减原子性。
- `ReservationServiceImpl.java:165` 取消订单时对订单加锁，避免重复取消导致库存多释放。

### 面试说法

> 我的预约接口不是简单 insert，而是先用一次性提交令牌防重，再用 Redisson 用户锁保证一人一单，最后用 Redis Lua 把“判断库存、扣库存、记录用户”放在 Redis 端原子执行。这样并发下不会出现超卖，也不会因为重复点击产生重复订单。

## 5. Caffeine + Redis 二级缓存

### 是什么

二级缓存指：

1. 一级：Caffeine 本地缓存，进程内访问，无网络 IO。
2. 二级：Redis 分布式缓存，多实例共享。
3. 三级：MySQL，缓存未命中时回源。

### 为什么这样做

教室列表、教室详情、推荐结果、Redis 概览都属于读多写少数据。只用 Redis 仍然有网络 IO，只用 Caffeine 多实例不一致。二级缓存能兼顾速度和共享。

### 怎么做

- `TwoLevelCacheService.java:20` 封装 Caffeine + Redis。
- `TwoLevelCacheService.java:40` 读取对象缓存。
- `TwoLevelCacheService.java:44` 读取列表缓存。
- `TwoLevelCacheService.java:49` 读取 Map 缓存。
- `TwoLevelCacheService.java:76` 支持按前缀删除本地和 Redis 缓存。
- `TwoLevelCacheService.java:84` 暴露本地缓存命中、未命中、命中率和淘汰次数。
- `ClassroomServiceImpl.java:35` 教室详情走二级缓存。
- `ClassroomServiceImpl.java:45` 教室列表搜索走二级缓存。
- `AdvisorServiceImpl.java:38` 智能推荐结果缓存 5 分钟。
- `RedisOpsServiceImpl.java:38` Redis 概览缓存 10 秒，避免频繁扫描 key。
- `ClassroomServiceImpl.java:75` 教室新增或修改后删除搜索缓存和推荐缓存。

### 面试说法

> 我把教室查询和推荐结果做成 Caffeine + Redis 二级缓存：请求先查本地 Caffeine，本地未命中再查 Redis，Redis 未命中才回源 MySQL。本地缓存能减少 Redis 网络 IO，Redis 能支持多实例共享。教室资源发生新增或修改时，会同时删除 Caffeine 和 Redis 的相关前缀缓存，保证读写一致性。

## 7. RabbitMQ + Outbox 可靠消息

### 是什么

RabbitMQ 用于异步发送预约通知。Outbox 是可靠消息模式：业务事务里先写本地消息表，再由后台任务投递 MQ，失败可重试。

### 为什么这样做

如果在预约事务里直接发 MQ，可能出现数据库提交成功但 MQ 发送失败，导致通知丢失。Outbox 让“预约单”和“待发送消息”在同一个数据库事务中落库，后续发送失败也能补偿。

### 怎么做

- `RabbitConfig.java:19` 定义 exchange、routing key、主队列、死信队列。
- `RabbitConfig.java:40` 主队列绑定死信交换机，消费失败可进入 DLQ。
- `NotificationOutboxServiceImpl.java:25` 负责创建本地消息、发送 MQ、重试、统计。
- `NotificationConsumer.java:22` 监听 `classroom.reserve.notify.queue`，消费后写站内信。
- `MqOpsServiceImpl.java:26` 暴露 MQ 队列和 Outbox 积压状态。

### 面试说法

> 预约成功后我没有在主链路同步发通知，而是把通知事件写入 Outbox 表，事务提交后异步投递 RabbitMQ。这样即使 MQ 短暂不可用，也不会丢消息，后台可以按状态重试，超过次数进入死信或 dead 状态。运维接口能看到主队列、死信队列和 Outbox 积压。

## 8. 可观测：Micrometer + Prometheus + Grafana

### 是什么

### 怎么做

- `ObservabilityConfig.java:13` 注册业务指标。
- `ObservabilityConfig.java:16` 暴露 `crs.outbox.pending`。
- `ObservabilityConfig.java:19` 暴露 `crs.outbox.retrying`。
- `ObservabilityConfig.java:22` 暴露 `crs.outbox.dead`。

### 面试说法

## 9. Flyway 数据库迁移

## 13. 压测和指标怎么写进简历

先不要编造“15ms 到 2ms”这种数值。正确做法是：

1. 用 JMeter 跑数据库直查版本，记录 QPS、平均耗时、P95、错误率。
2. 用 JMeter 跑 Caffeine + Redis 缓存版本，记录同样指标。
3. 用 `GET /actuator/prometheus` 或 Grafana 看 HTTP 指标。

## 15. Kafka、Elasticsearch 要不要加

当前不建议为了“堆技术”硬加 Kafka 和 Elasticsearch。

原因：

- Kafka 更适合高吞吐日志流、行为流、订单事件流。本项目通知消息量较小，RabbitMQ 更贴合“业务消息 + 可靠投递 + 死信队列”。
- Elasticsearch 适合复杂全文检索和聚合分析。本项目教室筛选维度简单，MySQL 索引已经足够；如果要加，应该围绕“教室名称/设备/楼栋全文搜索 + 热门推荐分析”设计，而不是只配依赖。

可以作为后续增强：

- Kafka：把审计日志、用户行为、预约事件写入 Kafka，做异步分析。
- Elasticsearch：把教室资源和预约日志同步到 ES，支持复杂检索和运营看板。

面试时可以这样回答：

> 我没有盲目堆 Kafka 和 Elasticsearch。当前系统的异步通知更适合 RabbitMQ，因为它强调业务可靠投递、ACK、重试和死信；搜索维度暂时用 MySQL 索引就能满足。后续如果要做行为分析或复杂全文检索，会再引入 Kafka 和 Elasticsearch。
